## 1. Резюме

«ТехМост Скаут» — внутренняя ИИ-система компании «ТехМост» (рабочее название), которая по свободному описанию технологической задачи бизнеса находит и оформляет **5–7 вариантов научно-исследовательских решений на разных стадиях зрелости**: от лабораторной разработки до готовой к внедрению технологии. Система готовит черновой шорт-лист с обязательными ссылками на первоисточники; научный со-основатель валидирует карточки до клиентского качества.

MVP разрабатывается ИИ-агентами под руководством владельца продукта за 4–6 недель, почти без бюджета (API-подписки), и должен быть готов до ворот Фазы 0 (8 декабря 2026).

**Место в стратегии.** Это технологическое ядро услуги «Поиск и проверка» из лестницы услуг компании. Исследование рынка показало: ИИ коммодитизирует сам поиск, а ценность смещается к проверке и сделке — поэтому система прямо спроектирована как «черновик для валидации учёным», а не как замена эксперта. Накопленные запросы, карточки и вердикты валидатора — зачаток главного актива компании (база задач и решений, Фаза 3 дорожной карты).

## 2. Проблема

1. Ручной скаутинг под задачу клиента занимает недели: поиск по публикациям, патентам, грантам и сайтам институтов делается руками и не масштабируется. Это ограничивает и экономику пилота (чек 1,5–4 млн ₽ при 6–8 неделях), и количество параллельных проектов команды из 2–3 человек.
2. Покрытие ручного поиска неполно: релевантные разработки размазаны по десяткам источников (eLibrary, патентные базы, реестры грантов, ЕГИСУ НИОКР, сайты вузов, международные базы), и одиночный аналитик физически не просматривает всё.
3. Для продаж нужен демо-эффект: возможность на встрече с клиентом показать «вводим вашу задачу — система находит варианты» резко усиливает оффер пилота.

## 3. Цели и метрики успеха

**Главный критерий приёмки (зафиксирован интервью):** на 3 реальных запросах из проблемных интервью Фазы 0 система выдаёт шорт-листы, в каждом из которых **не менее 3 карточек научный со-основатель оценивает ≥4 из 5** («годно для показа клиенту после лёгкой правки»), **без выдуманных фактов** (каждое утверждение подтверждено ссылкой), при полном цикле «запрос → провалидированный отчёт» **≤ 24 часов**.

Вспомогательные метрики:

| Метрика | Цель |
|---|---|
| Время работы пайплайна (запрос → черновик) | ≤ 60 минут |
| Стоимость одного запроса (API) | ≤ 1 000 ₽ (~$10) |
| Источников на карточку | ≥ 2 независимых, все утверждения со ссылками |
| Покрытие типов источников на запрос | ≥ 4 (публикации, патенты, гранты, организации) |
| Демо-режим | Показ заготовленного кейса ≤ 5 минут без сбоев |

Явная не-цель: система не принимает решений за эксперта и не отправляет ничего клиенту без валидации.

## 4. Пользователи и роли

| Роль | Кто | Что делает |
|---|---|---|
| Оператор | Кирилл (позже — аналитик) | Вводит запрос, отвечает на уточнения, запускает поиск, редактирует отчёт, экспортирует |
| Валидатор | Научный со-основатель / сдельный эксперт | Смотрит черновые карточки, ставит вердикт: подтверждаю / отклоняю / доработать + комментарий |
| Зритель | Клиент на встрече | Видит демо-режим и финальный отчёт (PDF/DOCX); в систему не входит |

Доступ: единый вход по паролю (basic auth), без личных кабинетов и ролей в MVP — роли разделяются организационно.

## 5. Пользовательские сценарии

**Сценарий 1 — рабочий (ядро ценности).** Кирилл возвращается с диагностики у клиента, вставляет в систему обезличенные заметки о технологической боли. Система задаёт 3–5 уточняющих вопросов (отрасль, ограничения, желаемая стадия готовности, бюджет и сроки внедрения), формирует бриф и показывает его на подтверждение. После запуска агентный пайплайн ищет по источникам и через ~30–60 минут выдаёт черновик: 5–7 карточек + сравнительная сводка. Кирилл отправляет ссылку валидатору; тот выставляет вердикты и комментарии. Кирилл собирает финальный отчёт и экспортирует PDF в фирменном стиле.

**Сценарий 2 — демо на встрече.** На встрече с клиентом Кирилл открывает систему на проекторе, включает демо-режим с заранее прогнанным отраслевым кейсом (нефтегаз / фарма / агро) и за 3–5 минут показывает путь «задача → бриф → карточки → отчёт». При наличии времени — запускает живой запрос по обезличенной задаче клиента и обещает прислать результат завтра.

**Сценарий 3 — валидация.** Учёный получает ссылку, открывает экран ревью: карточки с оценкой уверенности и ссылками на первоисточники. По каждой ставит вердикт и пишет замечание. Его вердикты сохраняются — это и контроль качества, и будущая обучающая выборка.

## 6. Функциональные требования

### Блок A — интейк
- **FR-1.** Ввод запроса свободным текстом (включая вставку заметок с диагностики), поле до 10 000 знаков.
- **FR-2.** Агент-интейк задаёт 3–5 уточняющих вопросов одним экраном; допускается ответ «не знаю».
- **FR-3.** Система собирает структурированный бриф (отрасль, суть задачи, ограничения, целевая стадия зрелости, география, бюджет/сроки — если известны) и показывает его оператору на подтверждение/правку до запуска поиска.
- **FR-4.** Проверка обезличенности: при обнаружении в тексте похожих на названия компаний/брендов сущностей — предупреждение с предложением заменить на нейтральное описание (блокирующего запрета нет).

### Блок B — поиск и отбор
- **FR-5.** Агентный поиск минимум по типам источников: научные публикации, патенты, гранты/проекты, организации и коллективы; каналы: Perplexity Sonar API (живой веб), OpenAlex API, патентный поиск, реестры грантов (РНФ, ФСИ), ЕГИСУ НИОКР (rosrid), сайты институтов и центров трансфера. Приоритизация и способы доступа — в ТЗ.
- **FR-6.** Курируемая витрина: таблица разработок партнёрских институтов (ручной ввод + импорт CSV); совпадения из витрины получают приоритет в выдаче и метку «проверенный партнёр».
- **FR-7.** Международные источники включаются в поиск; у зарубежных решений — пометка о применимости в РФ.
- **FR-8.** Дедупликация кандидатов и скоринг по критериям: релевантность задаче, стадия зрелости, доступность разработчика для контакта, свежесть, полнота данных.

### Блок C — карточки и отчёт
- **FR-9.** Выдача: 5–7 карточек. Обязательные поля карточки: суть решения; стадия зрелости по шкале «лаборатория → прототип → пилот → серия» (+ оценка TRL); разработчик (организация/коллектив, контактные зацепки); чем подтверждено (ссылки на первоисточники); применимость к задаче; ключевые риски; применимые инструменты господдержки (218-ПП, доращивание, вычет — из справочника); рекомендуемый следующий шаг.
- **FR-10.** Каждое фактическое утверждение в карточке имеет ссылку на источник. Если данных нет — поле заполняется «не найдено», выдумывать запрещено (контролируется агентом-верификатором, см. ТЗ).
- **FR-11.** Сводка отчёта: сравнительная таблица вариантов + рекомендация системы (2–3 абзаца) + перечень источников.
- **FR-12.** У каждой карточки — оценка уверенности (высокая/средняя/низкая) с пояснением, что её снижает.

### Блок D — валидация и экспорт
- **FR-13.** Экран ревью для валидатора: вердикт (подтверждаю / отклоняю / доработать) + комментарий по каждой карточке; статус отчёта меняется на «провалидирован», когда вердикты проставлены.
- **FR-14.** Редактирование текста карточек оператором до и после валидации.
- **FR-15.** Экспорт отчёта в PDF и DOCX в фирменном стиле (см. §7); в футере — «Подготовлено системой ТехМост Скаут, проверено [эксперт], дата».
- **FR-16.** Демо-режим: заранее прогнанные кейсы по трём отраслям, воспроизводимые без ожидания пайплайна; переключатель «демо» скрывает служебные элементы.

### Блок E — хранение
- **FR-17.** Все запросы, брифы, кандидаты, карточки, вердикты и отчёты сохраняются; список прошлых запросов с поиском.

## 7. Требования к дизайну (зафиксировано интервью: «премиально, в стиле питч-дека»)

- Палитра фирменной системы: глубокий чернильный `#10163A` (тёмные поверхности), основной синий `#1E2761`, текст `#1B2140`, приглушённый `#6B7699`, золото `#C9A24B` (только акценты), светло-голубой `#CDDCF9`, карточные подложки `#F2F5FC` с волосяными линиями `#E3EAF8`.
- Типографика: Segoe UI (Semibold для заголовков, Regular для текста) с системными fallback; крупные уверенные заголовки, много воздуха.
- Приёмы из дек-системы: карточки с двойной окантовкой, тёмные акцентные блоки, золотые нумерованные точки, мягкие «орбы» на тёмном фоне заставки.
- Движение: плавные переходы состояний (появление карточек, прогресс поиска — живой статус со стадиями «ищу публикации → патенты → гранты…»); никакой резкой смены экранов. Прогресс поиска — главный «вау-момент» демо.
- Тон текстов интерфейса — человеческий русский, без канцелярита и англицизмов.

## 10. Риски и допущения

| Риск/допущение | Митигация |
|---|---|
| Доступ и оплата зарубежных API (Anthropic, Perplexity) из РФ | Допущение: у владельца есть работающий доступ (эта сессия — подтверждение). Резерв: агрегаторы API. Фиксируем как предусловие старта |
| eLibrary/КиберЛенинка без стабильного API, антибот | Не парсим напрямую в MVP: живой поиск через Perplexity + OpenAlex (покрывает значительную часть русскоязычных журналов); прямые адаптеры — v2 |
| Галлюцинации ИИ | Правило «каждый факт со ссылкой» (FR-10), агент-верификатор, оценка уверенности (FR-12), обязательная валидация человеком |
| ЕГИСУ НИОКР: качество открытых данных неизвестно | Этап разведки источников в ТЗ (неделя 1); при недоступности — помечаем и живём без него |
| Витрина партнёров пока мала (этап 0.3 дорожной карты идёт параллельно) | Витрина — приоритетный слой, но система полноценно работает и на открытых источниках |
| Срок 4–6 недель при парттайме руководителя | Этапы ТЗ нарезаны так, что каждая неделя даёт работающий инкремент; буферная неделя 6 |

## 12. Открытые вопросы

1. Кандидатура валидатора на приёмку, если научный со-основатель ещё не подтверждён к моменту M5 (план Б: сдельный эксперт по отрасли первого запроса).
2. Имя продукта в интерфейсе: «ТехМост Скаут» — рабочее, финализировать вместе с названием компании.
3. Нужен ли водяной знак «черновик — не проверено экспертом» на неэкспортированных отчётах (предлагаю: да).
