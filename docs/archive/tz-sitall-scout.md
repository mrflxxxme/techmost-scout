## 0. Как работать с этим ТЗ (инструкция руководителю)

1. Один этап = одна или несколько сессий с ИИ-агентом. Открывайте сессию в папке репозитория и давайте агенту задачу этапа **дословно из этого документа** (раздел 6), добавляя контекст: «см. tz-scout.md и prd-scout.md».
2. Не переходите к следующему этапу, пока не выполнен **DoD (Definition of Done)** текущего, каждый DoD сформулирован так, чтобы вы могли проверить его лично за 10–15 минут без чтения кода.
3. После каждого этапа просите агента: обновить README, прогнать тесты, показать демо-команду. Коммиты, после каждого работающего инкремента.
4. Если агент предлагает усложнение («давайте добавим…»), сверяйтесь с разделом «Вне скоупа» PRD. По умолчанию, нет.
5. Все ключи API храните в файле `.env` (он в `.gitignore`); никогда не вставляйте ключи в чат агенту, агент читает их из окружения.

## 1. Архитектура

```
[Браузер: веб-UI]
      │ HTTPS (basic auth)
[FastAPI backend + статика фронтенда]
      │
[Оркестратор пайплайна (Python)]
  ├─ Агент-интейк ───────────── Claude API
  ├─ Планировщик поиска ─────── Claude API
  ├─ Поисковые адаптеры ─────── Perplexity Sonar API · OpenAlex API ·
  │                              патентный поиск · реестры грантов · rosrid ·
  │                              витрина (локальная БД)
  ├─ Экстрактор кандидатов ──── Claude API (строгий JSON)
  ├─ Дедуп + скоринг ────────── код + Claude API
  ├─ Автор карточек ─────────── Claude API
  └─ Верификатор ────────────── Claude API (проверка ссылок и фактов)
      │
[SQLite (MVP)] ── запросы · брифы · кандидаты · карточки · вердикты · витрина · логи · расходы
      │
[Экспорт PDF/DOCX] · [Демо-режим: сохранённые прогоны]
```

**Стек (зафиксировано):** Python 3.12 + FastAPI; фронтенд, React (Vite) одностраничный, без SSR; SQLite через SQLAlchemy (миграция на Postgres, v2); PDF, печатная версия отчёта через headless-Chromium (playwright), DOCX, python-docx; деплой, Docker Compose на VPS, обратный прокси Caddy (автоматический HTTPS + basic auth).

**Модели ИИ:** оркестрация, экстракция и синтез, Claude (Anthropic API, модель класса Sonnet;連 переключение модели, конфигом). Живой веб-поиск, Perplexity Sonar API (возвращает ответы с цитатами-URL). Прямые API: OpenAlex (открытый, без ключа). Все вызовы, через один модуль `llm.py` / `search.py` с ретраями и учётом стоимости.

## 2. Модель данных (SQLAlchemy; поля обязательны, если не сказано иное)

- **Request**: id, created_at, raw_text, status (`intake` → `briefing` → `searching` → `drafted` → `validated` → `exported`), cost_rub (накопленный), demo_flag.
- **Brief**: request_id, industry, task_summary, constraints (json), target_maturity, geography, budget_hint (nullable), timeline_hint (nullable), confirmed_at.
- **Candidate**: id, request_id, source_type (`publication`|`patent`|`grant`|`org`|`showcase`), title, org, year (nullable), url, snippet, dedup_key, score (json по критериям), status (`found`|`deduped`|`selected`|`rejected`).
- **SolutionCard**: id, request_id, candidate_ids (json), title, essence, maturity_stage (`lab`|`prototype`|`pilot`|`series`), trl_estimate (int, nullable), developer (org, team, contact_leads json), evidence (json: список {claim, url}), applicability, risks, gov_support (json: применимые инструменты из справочника), next_step, confidence (`high`|`medium`|`low`), confidence_note, editor_overrides (json, nullable).
- **Verdict**: card_id, reviewer_name, decision (`approve`|`reject`|`rework`), comment, created_at.
- **ShowcaseItem** (витрина): id, title, org, contact, maturity_stage, description, tags (json), source_note, added_by, created_at.
- **PipelineLog**: request_id, stage, started_at, finished_at, tokens_in/out, cost_rub, sources_hit (json), error (nullable).

Справочник господдержки, статический `gov_support.yaml` (218-ПП, коэффициент 2, гранты доращивания, СПИК 2.0: условия применимости, суммы, ссылки), заполняется на этапе 2 из [market-overview.md](../market-overview.md).

## 3. Источники: приоритет, доступ, риски

| # | Источник | Доступ | Приоритет | Риск/примечание |
|---|---|---|---|---|
| 1 | Витрина партнёров | локальная БД | максимальный, метка «проверенный партнёр» | пока мала, не блокирует |
| 2 | Perplexity Sonar API | REST, ключ | основной живой поиск (RU+EN), 3–6 запросов на бриф | оплата из РФ, предусловие |
| 3 | OpenAlex | REST, без ключа | публикации, авторы, организации | русскоязычное покрытие частичное |
| 4 | Google Patents / Яндекс.Патенты | через Perplexity-запросы с site:-операторами | патенты | прямого API нет, не парсим в MVP |
| 5 | РНФ, ФСИ (Бортника) | страницы проектов через Perplexity | гранты → команды | структура страниц нестабильна |
| 6 | ЕГИСУ НИОКР (rosrid.ru) | разведка на этапе 2: открытые данные/API | реестр НИОКР и РИД | качество неизвестно, по итогам разведки either адаптер, either отказ с фиксацией |
| 7 | Сайты институтов, ЦТТ | через Perplexity | контакты разработчиков |, |

Правило: пайплайн обязан пережить отказ любого источника: отчёт помечает, что источник был недоступен (NFR из PRD).

## 4. Промпт-контракты (ядро качества; файлы в `prompts/`, версионируются)

1. **intake.md**, из raw_text составить до 5 уточняющих вопросов (только то, чего реально не хватает) и черновик брифа. Запрещено спрашивать то, что уже сказано. Выход, строгий JSON по схеме Brief.
2. **planner.md**, из брифа составить план поиска: 3–6 поисковых формулировок на русском и английском под каждый тип источника, с обоснованием. Выход, JSON.
3. **extractor.md**: из сырых результатов источника извлечь кандидатов строго по схеме Candidate. Правило: `url` обязателен; кандидат без URL отбрасывается.
4. **scorer.md**: оценить кандидатов по 5 критериям (релевантность, зрелость, доступность разработчика, свежесть, полнота) 0–10 с однострочным обоснованием каждой оценки.
5. **card_author.md**, собрать карточку SolutionCard из выбранных кандидатов. Жёсткие правила: каждое фактическое утверждение, в `evidence` с URL; чего нет в источниках, «не найдено»; запрещены обобщения без ссылки («широко применяется», «доказанная эффективность»); поле gov_support, только из справочника `gov_support.yaml` по формальным условиям применимости.
6. **verifier.md**: второй проход по готовой карточке: проверить, что каждое утверждение опирается на приложенный URL и что URL правдоподобен (домен соответствует типу источника); понизить confidence и записать confidence_note при сомнениях; пометить карточку `needs_rework`, если найдено утверждение без источника.
7. **summary.md**, сравнительная сводка и рекомендация (2–3 абзаца), тон, деловой русский без канцелярита, в терминологии компании («стадия зрелости», «доращивание», «господдержка»).

Каждый промпт заканчивается блоком «Форматы ошибок»: как отвечать при пустой выдаче, противоречиях, недоступных источниках. Изменение промпта = отдельный коммит с записью в `prompts/CHANGELOG.md`.

## 5. Веб-интерфейс (этап 3; дизайн: §7 PRD)

Экраны (всё: один SPA):
1. **Новый запрос**, большое поле ввода, предупреждение об обезличивании (FR-4, подсветка распознанных названий организаций c предложением заменить), кнопка «Начать».
2. **Уточнения**, вопросы интейка одним списком, поля ответов, «не знаю», допустимый ответ; затем бриф на подтверждение (редактируемый).
3. **Поиск**, живой прогресс по стадиям с анимацией («Ищу публикации… найдено 14 · Патенты… 6 · Гранты… 3»), время и текущая стоимость; это витринный экран для демо, вложиться в плавность.
4. **Отчёт**, сводка + карточки (двойная окантовка, стадия зрелости как шкала с золотой отметкой, уверенность цветом, источники, кликабельные); режимы: редактирование (оператор), ревью (валидатор, кнопки вердиктов + комментарий), просмотр.
5. **История**: список запросов со статусами и поиском.
6. **Витрина**: таблица ShowcaseItem: добавление вручную, импорт CSV.
7. **Демо-переключатель**: воспроизводит сохранённый прогон (включая анимацию прогресса из лога) без реальных вызовов API.

Дизайн-токены вынести в `theme.css` (значения из §7 PRD). Шрифты: `"Segoe UI Semibold", "Segoe UI", system-ui`, без внешних шрифтовых CDN.

## 6. Этапы разработки (задачи для ИИ-агентов)

### Этап 1 (неделя 1): скелет и сквозной прогон
Задачи: репозиторий (структура: `backend/`, `frontend/`, `prompts/`, `docs/`, `docker/`); `.env.example`; модуль `llm.py` (Claude) и `search.py` (Perplexity, OpenAlex) с ретраями и подсчётом стоимости; модели данных §2 + миграции; CLI-команда `scout run "<текст запроса>"`: интейк (вопросы в консоли) → планировщик → поиск только через Perplexity → экстрактор → автор карточек → верификатор → markdown-отчёт в `out/`. Разведка rosrid: 2 часа, результат, заметка `docs/sources.md` (годен/не годен + способ).
**DoD:** руководитель запускает CLI на реальном запросе и получает markdown с 5–7 карточками, где каждый факт со ссылкой; в консоли, стадии и стоимость; тесты `pytest` зелёные.

### Этап 2 (неделя 2): источники, витрина, скоринг
Задачи: адаптеры OpenAlex, патентный и грантовый поиск (через Perplexity-стратегии из §3), rosrid, по итогам разведки; дедуп (нормализованный dedup_key: название+организация) и scorer; витрина: таблица + CSV-импорт + приоритет в выдаче; `gov_support.yaml` и логика применимости в карточках; частичная деградация при отказе источника; сохранение всего в SQLite.
**DoD:** тот же CLI-запрос теперь показывает кандидатов из ≥4 типов источников; при выключенном (замоканном) источнике отчёт формируется и честно помечает пропуск; повторный прогон не плодит дубликатов в БД.

### Этап 3 (неделя 3): веб-интерфейс
Задачи: FastAPI-эндпоинты поверх пайплайна (запрос, ответы на уточнения, статус через SSE/поллинг, отчёт, правки); фронтенд-экраны 1–5 из §5 в фирменном стиле; живой прогресс поиска.
**DoD:** руководитель проходит путь «текст → уточнения → бриф → прогресс → отчёт» в браузере локально; интерфейс соответствует токенам §7 PRD (сверка по чек-листу: палитра, карточки с окантовкой, плавные переходы, русский язык без канцелярита).

### Этап 4 (неделя 4): валидация, экспорт, демо
Задачи: режим ревью с вердиктами и комментариями (FR-13); статусная модель отчёта; экспорт PDF (печатная вёрстка в стиле дека: чернильная обложка, карточки, футер «проверено…») и DOCX; водяной знак «Черновик, не проверено экспертом» до валидации; демо-режим (FR-16) с 1 сохранённым кейсом; экран «Витрина» и «История».
**DoD:** валидатор по ссылке проставляет вердикты со смартфона; PDF открывается корректно и выглядит в фирменном стиле; демо-кейс проигрывается офлайн от начала до конца за ≤5 минут.

### Этап 5 (неделя 5): деплой и приёмка
Задачи: Dockerfile + docker-compose (backend, Caddy с basic auth и HTTPS); инструкция деплоя на VPS в `docs/deploy.md` (провайдер по выбору руководителя, ~500–1500 ₽/мес); бэкап SQLite (cron + копия в объектное хранилище или локально); прогон трёх демо-кейсов по отраслям (нефтегаз, фарма, агро) и их сохранение; **приёмочные испытания по протоколу §7**.
**DoD:** система доступна по домену с паролем; три реальных запроса прогнаны; заполнен протокол приёмки.

### Этап 6 (неделя 6, буфер): доработки
Задачи: правки по замечаниям валидатора из приёмки (типовые ожидания: качество патентных кандидатов, точность стадии зрелости, тон текстов); фиксация версии 1.0; ретроспектива, заметка `docs/retro.md`: что автоматизировалось хорошо, что осталось ручным (вход для методики компании).

## 7. Протокол приёмочных испытаний

1. Взять 3 реальных обезличенных запроса из проблемных интервью Фазы 0 (по одному на отрасль).
2. Прогнать каждый через систему (без ручной помощи пайплайну); зафиксировать время и стоимость.
3. Валидатор оценивает каждую карточку по шкале 1–5 («5, можно показывать клиенту как есть; 4, годно после лёгкой правки; 3, полезно, но требует переработки; 2, слабо; 1, мусор/ошибка») и проверяет 3 случайных факта по ссылкам в каждой карточке.
4. **Приёмка пройдена**, если в каждом из трёх отчётов ≥3 карточек с оценкой ≥4, ни одного неподтверждённого ссылкой факта в проверенных, цикл ≤24 часов, стоимость ≤1 000 ₽/запрос.
5. Результаты: в `docs/acceptance.md` (таблица оценок + комментарии валидатора).

## 8. Правила для ИИ-агентов-разработчиков

1. Файлы не длиннее 500 строк; публичные функции с типами и докстрингами.
2. Каждый этап: тесты: юнит на экстрактор/дедуп/скоринг (на фикстурах, без живых API), смоук на пайплайн с моками.
3. Никаких секретов в коде и коммитах; конфиг: через `.env`/pydantic-settings.
4. Все вызовы внешних API: только через `llm.py`/`search.py` (ретраи, тайминги, учёт стоимости в PipelineLog).
5. Промпты, только в `prompts/`, изменения, через CHANGELOG.
6. README поддерживается актуальным: запуск локально, запуск тестов, деплой.
7. Валидация входа на границах (pydantic-схемы эндпоинтов), санитизация путей файлов.
8. После каждого этапа: работающий инкремент в `main`; ветки на этап, слияние после DoD.
