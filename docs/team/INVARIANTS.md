# Инварианты проекта

Десять правил, которые не нарушаются никогда. Проверяются в каждом ревью, в
каждой верификации и в каждом аудите. Нарушение **блокирует** — оно не
эскалируется и не откладывается «на потом».

У каждого пункта есть колонка «как проверять»: инвариант без способа проверки —
это пожелание, а не инвариант.

| № | Никогда | Почему | Как проверять |
|---|---|---|---|
| 1 | Утверждение о факте в карточке без ссылки на первоисточник | Главный критерий приёмки продукта: эксперт не должен найти ни одного неподтверждённого утверждения. Выдуманный факт в отчёте у клиента дороже пустой карточки. На Э1-2 нарушение прошло гейты именно потому, что проверялся только блок подтверждений, а поле зрелости печаталось без источника | Проверяются **все** поля карточки, а не только блок подтверждений: карточка с пустым `evidence` не печатает ни стадии зрелости, ни TRL — машинная проверка `pytest tests/test_export_markdown.py`; у каждой публикуемой карточки `evidence` непуст; в отчёте нет строки «Подтверждений не приложено»; выборочно 3 факта сверяются по ссылкам |
| 2 | Отчёт уходит клиенту без валидации экспертом | Система не заменяет научного со-основателя, а готовит ему черновик | Пометка «ЧЕРНОВИК» снимается только при `validated=True` и заполненном имени проверяющего; в коде нет пути автоотправки |
| 3 | Секрет в коде, логе, тесте или коммите | Ключи переносятся из чужого проекта и стоят денег | `git log -p` и `grep -rE "sk-|gigachat|Api-Key" backend/ tests/` — ничего; `.env` в `.gitignore`; вывод команд не печатает значения. **Часть значения — тоже значение**: начальные символы ключа в отчёте роли запрещены наравне с полным (случай проверки З-1 волны Э2-Д, вырезано оркестратором). Наличие боевой переменной доказывается её ИМЕНЕМ |
| 4 | Незаполненная подстановка `{{...}}` уходит в модель | Один раз это уже случилось: модель получала метку текстом вместо данных, и проверяющая стадия занижала уверенность всем карточкам | `render_prompt` падает при незаполненной метке; `pytest tests/test_prompts.py` зелёный |
| 5 | Отказ внешнего источника роняет запрос — или скрывается от отчёта | Устойчивость важнее полноты: пять источников из шести — это результат, а падение — нет. Но скрытый отказ хуже видимого: на Э1-2 источник отвечал 429 на каждом запросе трёх прогонов, и ни один отчёт об этом не сообщил, потому что адаптер гасил ошибку в пустой список | Транспортный отказ (HTTP-ошибка, 429, нечитаемый ответ) поднимается как `SearchError`, ловится в `_safe_search` и попадает в `sources_unavailable` — строка «Не ответили источники» в отчёте. Адаптер, гасящий HTTP-ошибку внутри и отдающий пустой успех, — нарушение, а не соответствие. Пустой результат при успешном ответе отказом не считается. Машинные проверки: `pytest tests/test_search_failures.py` и сквозной тест в `tests/test_pipeline_counters.py` |
| 6 | Прямой вызов внешнего API в обход слоёв | Иначе теряются ретраи, учёт стоимости и подмена в тестах | `grep -rln "httpx" backend/app --include='*.py' | grep -vE "backend/app/(llm/|search/|cli_doctor\.py$|pipeline/pipeline_context\.py$|pipeline/pipeline_search\.py$)"` — пусто. Легитимная карта (РЕШ-174, обновлена Д-4 волны Э2-З — `cli.py` раздроблен, httpx-клиент доктора переехал в `cli_doctor.py`): `llm/` и `search/` — сами адаптеры; `pipeline_context.py`/`pipeline_search.py` — httpx-клиент оркестратора для прогона пайплайна; `cli_doctor.py` — клиент доктора для проверки источников |
| 7 | Тест обращается в сеть | Набор должен проходить на машине без ключей и без интернета | `pytest` проходит при выключенной сети; внешние вызовы подменяются через respx или заглушки |
| 8 | Новое поведение без теста | Регрессия, пережившая гейты, — дыра в гейте | В diff есть изменения в `backend/`, значит есть изменения в `tests/`; ревьюер проверяет соответствие |
| 9 | Расширение скоупа за границы MVP | Личные кабинеты, биллинг, мониторинг, интеграции с CRM, английский интерфейс исключены сознательно | Раздел «Вне скоупа MVP» в `docs/SPEC.md` (раздел 2а); ревьюер сверяет diff с задачей из `PLAN.md` |
| 10 | Значение с двоеточием в YAML без кавычек | Случалось трижды: справочник господдержки, шапки команд, шапки ролей. Глазами не видно, ломается разбор | `pytest tests/test_team_docs.py` (шапки через `yaml.safe_load`); повторяющуюся правку делает `scripts/fix_frontmatter_quotes.py` |

## Что делать при нарушении

1. Работа по задаче останавливается — дальше по циклу нарушение не проходит.
2. Нарушение фиксируется в отчёте той роли, что его нашла, с указанием пункта.
3. Исправляет исполнитель задачи, а не тот, кто нашёл.
4. Если инвариант нарушен потому, что он мешает делу, — это повод для разговора
   с владельцем и записи в `DECISIONS.md`, а не для тихого обхода.

## Как добавить инвариант

Инвариант добавляется после реального сбоя, а не из осторожности. Основание —
запись в `JOURNAL.md` с полем «урок». К пункту сразу пишется способ проверки;
без него пункт не добавляется.
