# Конвенции работы команды ИИ-агентов

Единственный источник истины по процессу. Читается целиком один раз в начале
сессии — всё остальное подгружается по мере надобности. Изменения в процесс
вносятся только записью в [DECISIONS.md](../../.planning/DECISIONS.md), а не
устной договорённостью в чате.

правила кода — [CLAUDE.md](../../CLAUDE.md), «никогда» —

## 1. Как устроен цикл

Два вложенных контура. **Цикл этапа** — семь шагов, заканчивается воротами с
подписью руководителя. **Цикл задачи** — внутри этапа, проходит без владельца.
Владелец участвует на воротах, а не на шагах: один осознанный чекпоинт с
измеримыми порогами вместо десятка мелких одобрений.

```
ЭТАП спецификации (Э1-2, Э2-1, Э3-4 …)
  │
  0 ГРИЛЛ ───────── interviewer готовит развилки, спрашивает оркестратор
  │                 снимает открытые вопросы до планирования
  │                 → закрытые вопросы, записи в DECISIONS.md
  │                 ответ владельца — чекпоинт, а не финиш: цикл идёт дальше сам
  │
  1 ПЛАН ────────── planner
  │                 → .planning/PLAN.md, задачи с критериями приёмки
  │                 план закреплён: на ходу не переписывается
  │
  2 РЕАЛИЗАЦИЯ ──── implementer ×1–3, каждый в своём git worktree
  │                 → код + тесты + самопроверка + handoff
  │
  3 РЕВЬЮ ───────── reviewer, не более двух циклов
  │                 → отчёт с находками; блокируют только дефекты и
  │                   нарушения правил, вкусовщина идёт советом
  │
  4 ВЕРИФИКАЦИЯ ─── verifier, бинарно: PASS или FAIL
  │                 → критерии приёмки как проверки + инварианты + доказательства
  │
⭐5 ПОСТ-АУДИТ ──── auditor, адверсариально, две линзы
  │                 → вердикт PASS | PASS-WITH-FIXES | BLOCKED
  │
⭐6 СОСТОЯНИЕ ───── главная сессия (оркестратор)
  │                 → STATE.md, JOURNAL.md, DECISIONS.md, заполнение ворот
  │
  7 ВОРОТА ──────── подпись владельца в .planning/gates/<этап>.md
                    этап закрыт
```

Шаги 5 и 6 отмечены звёздочкой: **этап не закрыт без пост-аудита и без
обновления состояния**. Это не «если успеем» — без них накапливается скрытый
долг, которого при отсутствии постоянного надзора никто не увидит.

## 2. Роли

Шесть определений роли в `.claude/agents/`. Исполнитель разворачивается до трёх
экземпляров одновременно, остальные — по одному.

| Роль | Отвечает за | Вход | Выход |
|---|---|---|---|
| `interviewer` | Найти до планирования решения, которых нет в документах, и довести каждое до развилки с рекомендацией | этап спецификации, список уже принятого, 4–6 файлов | развилки с вариантами и ценой; спрашивает владельца и пишет решения оркестратор |
| `planner` | Разбор этапа на атомарные задачи с критериями приёмки | этап спецификации, STATE, решения | `PLAN.md` (закреплён) |
| `implementer` | Код и тесты строго по своей задаче | одна задача из PLAN, контракты | код, тесты, коммит, handoff |
| `reviewer` | Независимый гейт качества кода | handoff исполнителя, diff | отчёт ревью + вердикт |
| `verifier` | Бинарная приёмка: критерии выполнены или нет | handoff ревьюера, критерии из PLAN | отчёт верификации PASS/FAIL |
| `auditor` | Адверсариальный пост-аудит и инварианты | handoff верификатора, diff этапа | отчёт аудита + вердикт |

**Оркестратор — главная сессия вместе с владельцем.** Отдельного агента-
координатора нет: он множит передачи контекста, не добавляя решений.
Оркестратор же — единственный, кто пишет файлы состояния (см. §6).

Тривиальные механические правки (переименование, опечатка в тексте, версия в
одной строке) делаются инструментом правки напрямую, без агента вообще.

## 3. Независимость проверки

Правило: **кто сделал — не проверяет, кто нашёл — не правит.** Обеспечивается
не обещанием, а инструментами: в определении каждой проверяющей роли записан
запрет на запись в `backend/`, `prompts/` и `tests/`. Ревьюер физически не может
починить то, что нашёл, — он обязан вернуть это исполнителю.

Из этого следуют три запрета, которые нельзя обойти удобством:

1. Один экземпляр агента не выполняет два подряд шага цикла.
2. Исполнитель не запускает сам себе ревью и не объявляет свои критерии приёмки
   выполненными — это работа верификатора.
3. Аудитор не архивирует и не подписывает собственный отчёт.

## 4. Пределы циклов

Циклы без предела — главный способ сжечь бюджет и время.

| Ситуация | Предел | Что дальше |
|---|---|---|
| Ревью нашло, что править | 2 цикла | Третьего нет: разбор с владельцем |
| Правки внутри аудита | 1 цикл | Дальше вердикт BLOCKED |
| Тесты не проходят после починки | 3 попытки | Стоп, эскалация с диагнозом |
| Провал одних и тех же ворот | 2 раза | Стоп, пересмотр подхода с владельцем |
| Стоимость запроса к моделям | лимит из `.env` | Стоп-кран срабатывает сам |

**Именованное исключение из первой строки** (РЕШ-235, по факту этапа 5). Если
находка второго цикла — не новый дефект, а **обратная сторона только что
сделанной починки** («гейт стал слишком хрупок»: тест краснеет на законной
записи вместо того, чтобы ловить подмену), и правка укладывается в одну-две
строки, её вносит оркестратор, а принимает её **другая роль — та, что правку не
писала**. Третий цикл исполнителю при этом не открывается, конвейер не встаёт, и
независимость проверки сохраняется по существу: своё оркестратор не принимает
(§15). Отступление называется в решении и в воротах явно. Всё, что шире
одной-двух строк или меняет поведение продукта, идёт прежним путём — разбором с
владельцем.

## 5. Что блокирует, а что советует

Ревьюер и аудитор различают блокирующие находки и советы. **Блокируют только
дефекты и нарушения правил:**

- ошибка в логике, падающие или отсутствующие тесты на новое поведение;
- факт в карточке без ссылки на источник (главный инвариант продукта);
- секрет в коде, логе или коммите;
- выход за границы задачи или за границы скоупа MVP;
- нарушение любого пункта [INVARIANTS.md](INVARIANTS.md);
- незаполненная подстановка в промпте, необработанный отказ внешнего источника.

**Не блокируют** (пишутся как советы и живут в журнале): стилистические
предпочтения, спор о наименовании без функционального следствия, идеи по
улучшению за пределами задачи, рефакторинг «пока рядом».

## 6. Файлы состояния и кто их пишет

Единственный писатель — оркестратор. Никакой конкурентной записи: это снимает
целый класс вопросов «а кто это переписал».

| Файл | Что в нём | Когда обновляется |
|---|---|---|
| `.planning/STATE.md` | Где мы сейчас, что дальше, задачи владельца. Не больше двух килобайт | после каждого шага цикла |
| `.planning/JOURNAL.md` | Хронология: что сделано, чем подтверждено, **урок** | после каждого этапа |
| `.planning/DECISIONS.md` | Решения: продуктовые развилки и автономные решения агентов | как только решение принято |
| `.planning/PLAN.md` | Закреплённый план текущего этапа | на шаге 1, дальше не трогается |
| `.planning/gates/<этап>.md` | Пороги, доказательства, подпись владельца | заполняется на шаге 6, подписывается на 7 |
| `.planning/evidence/` | Доказательства: вывод команд, отчёты, скриншоты | по мере получения |

Файлов ровно столько, сколько нужно. Каждый — единственное место своей
информации. Дублирующие сущности (отдельная история фаз, отдельный склад
паттернов) сознательно не заводятся: в проектах, откуда взята эта методика, они
за пять фаз остались пустыми, потому что то же самое уже лежало в журнале.

## 7. Формат передачи работы

Каждый агент заканчивает работу блоком handoff. Формат жёсткий: по нему
следующий агент понимает, что делать, не читая транскрипт.

```yaml
handoff:
  from: implementer-1
  to: reviewer
  task: Э2-1            # идентификатор задачи из PLAN.md
  did:                  # что реально сделано, не «работал над»
    - Реализован enrich_by_doi в backend/app/search/openalex.py
    - Тесты tests/test_openalex.py, 4 штуки, подмена ответов через respx
  artifacts:            # файлы обязаны существовать
    - backend/app/search/openalex.py
    - tests/test_openalex.py
  self_audit: pass      # pass | fail — своя проверка по чек-листу роли
  checks:               # чем подтверждено, с фактическим выводом
    - "pytest -q: 52 passed"
    - "ruff check: All checks passed"
  escalate: none        # none | вопрос владельцу
  read_first:           # что открыть следующему агенту
    - docs/SPEC.md (раздел Э2-1)
    - .planning/PLAN.md
  notes: OpenAlex вызывается только lookup по DOI, поиск платный — не трогал
```

Правила проверки блока: `self_audit: fail` вместе с `escalate: none` —
невозможная комбинация; перечисленные артефакты обязаны существовать; в `did`
пишется результат, а не занятие; в `checks` — фактический вывод команды, а не
«тесты прошли».

## 8. Ворота

Ворота — файл `.planning/gates/<этап>.md` с таблицей порогов. Правило:
**порог без ссылки на доказательство не считается пройденным.**

```markdown
# Ворота этапа Э2-1 — обогащение по DOI

| Критерий | Порог | Факт | Доказательство | Статус |
|---|---|---|---|---|
| Тесты проходят | все | 52 passed | evidence/E2-1-pytest.txt | ок |
| Линтер чистый | 0 замечаний | 0 | evidence/E2-1-ruff.txt | ок |
| Обогащение работает | ≥1 карточка с цитируемостью | 3 из 6 | evidence/E2-1-report.md | ок |
| Платный поиск не вызывается | 0 вызовов | 0 | evidence/E2-1-calls.txt | ок |

## Отложено
- DLG-1: живая проверка на ключе OpenAlex — ключа нет. Действие владельца:
  получить ключ (docs/deps-manual.md, п. 5). Без него тест идёт на подменах.

## Подпись владельца
Статус: не подписано
Дата:
```

Подпись не ставит ни один агент — только владелец. Невыполнимая проверка не
исчезает в тексте: у неё появляется идентификатор `DLG-N`, причина и конкретное
действие владельца, и этот идентификатор виден в отчётах верификации и аудита.

## 9. Территория владельца

Агент обязан остановиться и спросить, если решение попадает в один из четырёх
случаев:

1. **Архитектура и скоуп.** Новая зависимость, смена стека, выход за границы
   MVP, изменение схемы данных или контрактов между стадиями.
2. **Деньги и внешние сервисы.** Любая трата, платный API, регистрация,
   публикация чего-либо наружу, превышение лимита стоимости запроса.
3. **Провал ворот дважды подряд.** Не третья попытка, а разбор.
4. **Всё, что увидит клиент.** Текст в отчётах, формулировки промптов, внешний
   вид интерфейса, любые числа в клиентских материалах.

Литмус-тест для всего остального: **будет ли компетентный инженер, знающий этот
проект, всё ещё гадать?** Если нет — решай сам и запиши строкой в
`DECISIONS.md`. Эскалация — исключение, а не форма ревью: спрашивать про всё так
же вредно, как не спрашивать ни про что.

Уже принятое решение не открывается заново. Если оно записано в `DECISIONS.md`
или в спецификации — это не развилка, а данность.

**Формат эскалации** — всегда с вариантами и рекомендацией:

```
Развилка: <вопрос одной строкой>
Вариант А: <что делаем> — <следствие, цена>
Вариант Б: <что делаем> — <следствие, цена>
Рекомендую: А, потому что <причина>
Обратимость: обратимо | необратимо
Блокирует: только задачу Э2-1; остальные задачи продолжаются
```

Блокируется только та развилка, о которой спрашиваем. Независимая работа
продолжается.

## 10. Автономия и её границы

Агент работает **до конца фазы** без участия владельца: внутри фазы он
самостоятельно проходит задачи, ревью, верификацию и аудит, останавливаясь
только на территории владельца (§9) и на пределах циклов (§4).

«До конца фазы» включает и грилл. Ответ владельца на развилку шага 0 — это
чекпоинт внутри прогона: записал решения и сразу идёшь в план, новой команды
не ждёшь. Отдельный запуск `/team-grill` — исключение из §14, а не обычный
порядок. Спрашивает владельца всегда оркестратор: у подагента нет канала к
человеку, поэтому интервьюер возвращает развилки, а не ответы.

Что при этом обязательно:

- каждое автономное решение — строка в `DECISIONS.md`, чтобы автономию можно
  было проверить задним числом;
- вернувшегося агента проверяют инструментами, а не на слово: `git status`,
  прогон тестов, наличие заявленных артефактов;
- при трёх попытках починить одно и то же — стоп и отчёт, а не четвёртая;
- никакой агент не выдаёт себе полномочий: разрешения инструментов, хуки и
  защиту ветки включает владелец сознательно.

## 11. Параллельная работа исполнителей

До трёх исполнителей одновременно, каждый — в отдельном git worktree по своей
задаче. Слияние — последовательное, после ревью и верификации каждой ветки.

Правила, без которых параллельность приносит больше вреда, чем пользы:

- задачи для параллельного запуска не должны трогать одни и те же файлы;
  пересечение файлов — признак, что задачи надо выполнять последовательно;
- изменения в общих контрактах (`schemas.py`, `config.py`, промпты) выполняет
  только один исполнитель, остальные ждут слияния;
- конфликт слияния разбирает оркестратор, а не исполнитель.

## 12. Отладка

Порядок обязателен: **воспроизвести → изолировать → гипотеза и падающий тест до
починки → минимальный фикс с причиной в сообщении коммита.**

Правило, за которое эта система и держится: **регрессия, пережившая гейты, —
это дыра в гейте.** Починить дефект недостаточно; в тот же коммит добавляется
проверка, которая поймала бы его в следующий раз. Так набор тестов растёт по
реальным сбоям, а не по воображаемым.

## 13. Экономика контекста

Порядок чтения в начале любой сессии: `CLAUDE.md` → этот файл →
`.planning/STATE.md` → раздел `docs/SPEC.md` по своему этапу → `PLAN.md`.
Всё остальное — по необходимости.

- Специализированному агенту передаётся его задача и названные файлы, а не
  «прочитай весь проект».
- Роль не читает то, что ей запрещено менять: ревьюер не изучает историю
  переписки, верификатор не разбирает архитектурные решения.
- Handoff содержит поле `read_first` — предыдущий агент называет 4–6 конкретных
  файлов вместо общего правила.
- Отчёты агентов — сжатые: вывод команд обрезается до значимых строк, полный
  вывод складывается в `.planning/evidence/`.
- **Крупный артефакт не читается целиком.** Лог прогона, отчёт, дамп выдачи —
  это десятки килобайт, и агент, открывший подряд несколько таких файлов,
  тратит контекст на то, что ему не нужно. В задаче прямо указывается: такие
  файлы просматриваются точечным поиском по нужной строке, а целиком читаются
  только те, которые агент правит или проверяет по существу. Ограничение
  ставится в задаче заранее, а не после того, как агент захлебнулся.
- **Длинный результат пишется частями.** Агент, собирающий большой документ,
  вносит его разделами по мере готовности, а не одним куском в конце. Обрыв на
  середине тогда стоит одного раздела, а не всей работы.

Оба правила добавлены по факту, а не из осторожности (РЕШ-35). На этапе Э1-2
подряд упали три агента на одном и том же наборе из четырёх отчётов и пяти
логов по 25–37 килобайт: двоих снял сторожевой таймер, третий оборвался на
потоке. Разбор прошёл со второй попытки ровно потому, что в задаче было
предписано искать по логам, а не читать их.

## 13а. Непрерывность конвейера

Добавлено по фактам фазы Э1-2-Ф (РЕШ-44), а не из осторожности: за одну фазу
конвейер вставал шесть раз, и все шесть остановок — из четырёх повторяющихся
причин. Правила ниже закрывают каждую из них. Они обязательны для оркестратора
и вписываются в постановку каждой задачи подагенту.

**1. Результат существует, только когда он зафиксирован.** Исполнитель
коммитит сразу, как проверки стали зелёными, — ДО написания отчёта и handoff.
Коммит дешевле отчёта: агент, умерший после коммита, теряет слова; умерший до
коммита — работу. Два случая за фазу (Ф-6, Ф-8 цикл 2): вся работа была
сделана и висела незакоммиченной, агент умирал молча. То же для оркестратора:
запись решения или доказательства без немедленного коммита не существует для
подагентов (случай РЕШ-34: ревьюер счёл незакоммиченное решение выдумкой).

**Правило распространяется на проверяющие роли, и это оплачено отдельно.**
У исполнителя коммит идёт после кода, а отчёт — последним; у проверяющего
**отчёт и есть результат**, и потому он обязан быть закоммичен, а не только
сохранён файлом. На Э2-В верификатор задачи З-1 написал отчёт в своё дерево и
не закоммитил его: задача слилась без него, ворота подэтапа сослались на
«отчёты верификаций», а одного из них в ветке не было. Обнаружено случайно, при
уборке рабочих копий три волны спустя. **Проверяющий коммитит отчёт сразу после
того, как выписал вердикт, и только потом отвечает оркестратору.**

**Именованное исключение — аудитор** (снимает противоречие, названное аудитом
Э2-Г): по §3 п. 3 он не архивирует и не подписывает собственный отчёт, поэтому
его отчёт коммитит оркестратор — дословно и с пометкой, кем записан. Правило
«проверяющий коммитит сам» относится к ревьюеру и верификатору, у которых
запрет на запись не распространяется на `.planning/evidence/`.

**2. Приёмка по артефакту, а не по сигналу.** Финальное сообщение агента —
это деливерабл: вердикт, отчёт, handoff. Заглушки («OK», «готово», «ждём»)
оркестратор не принимает: работа считается несданной, пока отчёт не получен
или не восстановлен по артефактам (коммит, дифф, файлы) с пометкой
отступления. Проверяющие роли дополнительно отдают результат частями по мере
готовности (§13) — тогда обрыв стоит одного раздела, а не вердикта.

**3. Ожидание всегда ограничено и заканчивается опросом состояния.**
Уведомление о завершении фонового агента может не прийти — это норма, а не
исключение (потерянный сигнал стоил фазе ночи простоя). Оркестратор, ожидая
агента дольше разумного срока его задачи, опрашивает состояние сам: `git
status`/`git log` рабочей копии, наличие ожидаемых файлов. Молчаливое ожидание
без срока запрещено.

**4. Реанимация — один раз.** Агент, вернувший после сбоя заглушку вместо
результата, второй раз не реанимируется: контекст повреждён, пинг-понг дороже
перезапуска. Следующий шаг — свежий агент с плотной постановкой, в которую
внесено всё уже установленное (чтобы не платить за повторную работу), либо
восстановление результата оркестратором по артефактам.

**6. Handoff кладётся файлом до финального сообщения** (РЕШ-153). Исполнитель
и проверяющий пишут `.planning/evidence/<волна>-<задача>-handoff.yaml` тем же
коммитом, что и работу, — потерянное уведомление тогда стоит сводки, а не
отчёта. Оркестратор опрашивает рабочие копии по нормативу задачи, не дожидаясь
сигнала: в волне Э2-Д уведомления не пришли ни от одного из двух исполнителей,
а работа была сдана целиком.

**5. Вердикт подхватывается немедленно.** Пришёл handoff — следующий шаг цикла
запускается тем же ходом, без паузы между шагами. Конвейер останавливается
только на территории владельца (§9), на пределах циклов (§4) и по прямому
распоряжению владельца. Простой между «вердикт получен» и «следующий шаг
запущен» — дефект оркестровки, а не нормальное состояние.

## 14. Как это запускается

| Команда | Что делает |
|---|---|
| `/team-start <этап>` | Весь цикл: грилл → план → реализация → ревью → верификация → аудит → заполнение ворот. Останавливается на территории владельца и на подписи |
| `/team-grill <этап>` | Только шаг 0 отдельно от прогона: догриллить всплывшую развилку, подготовить этап заранее или обновить устаревший грилл |
| `/team-plan <этап>` | Только шаг 1: составить `PLAN.md` |
| `/team-build <задача>` | Одна задача через реализацию, ревью, верификацию, аудит |
| `/team-gate <этап>` | Собрать ворота: пороги, доказательства, отложенности |
| `/team-status` | Где мы, что дальше, что ждёт владельца |

Полный цикл и пофазный запуск не противоречат друг другу: `/team-start`
вызывает те же шаги, что и отдельные команды, просто не спрашивает разрешения
между ними — кроме случаев из §9.

## §15. Оркестратор не проверяет своё

Принято по итогам Э2-В (РЕШ-130), где волна потеряла четырёх исполнителей ролей
и трижды работу подхватывал оркестратор — то есть автор постановки.

**Правило.** Если проверяющая роль потеряна — не сдала отчёт, не откликнулась на
реанимацию, оборвалась, — оркестратор **поднимает свежего агента той же роли**, а
не выполняет проверку сам. Это дороже по времени и всегда дешевле по последствиям.

**Довод числом.** За три подэтапа дефект класса DLG-1 — проверка, зелёная по
неверной причине, — найден **четырнадцать раз**, и лишь однажды его нашёл автор
кода. Все остальные тринадцать нашла следующая роль, обязанная сломать чужое
утверждение своими руками. Независимость проверки — единственное, что этот класс
ловит; совпадение автора и проверяющего гасит её полностью.

**Что оркестратору по-прежнему можно и нужно:** прогонять проверки для себя,
ставить мутации, чтобы понимать положение дел, и подхватывать **производство**
(не проверку), когда исполнитель потерян, — с пометкой отступления. Запрещено
одно: выносить вердикт о работе, постановку которой писал он сам.

**Исключение ровно одно:** свежий агент той же роли потерян дважды подряд. Тогда
оркестратор проверяет сам, помечает отступление и **выносит это владельцу** —
двойная потеря роли подряд означает, что дело не в агенте, а в среде.

*Основано на конвенциях проекта wizor, сокращённых под масштаб этого проекта:
семь шагов вместо девяти, шесть ролей вместо четырнадцати, шесть файлов
состояния вместо восьми. Выброшено то, что в исходном проекте фактически
осталось незаполненным. Сохранено то, что работает независимо от масштаба:
независимость проверки, доказательство вместо заявления, человек на воротах,
пределы циклов, явные границы автономии.*
