# Деплой «ТехМост Скаут» на боевой сервер

Инструкция для **владельца** (РЕШ-226): команда агентов деплой не выполняет —
демона Docker в среде разработки нет, порт 22 закрыт, ключей от сервера у
агентов нет и не будет. Каждая команда ниже — копируемая строка, проверенная
по фактическим `docker/Dockerfile`, `docker/docker-compose.yml` и
`docker/Caddyfile` (не по замыслу, а по тому, что реально лежит в репозитории).

Адрес сервера в репозиторий не пишется: везде ниже стоит плейсхолдер
`<АДРЕС_СЕРВЕРА>`, домен — `<ДОМЕН>`. Подставляйте свои значения по месту.

## 1. Что нужно заранее

- **VPS.** Любой российский провайдер, 2 ГБ оперативной памяти достаточно
  (`docs/deps-manual.md`, п. 10). Публичный IPv4-адрес обязателен — на него
  указывает A-запись домена.
- **Домен** с A-записью, указывающей на IP-адрес сервера. Без домена Caddy не
  сможет выпустить сертификат Let's Encrypt по HTTPS.
- **Значения ключей** из `.env.example` в корне репозитория — получены заранее
  по `docs/deps-manual.md`. Ниже (раздел 3) названы только те, без которых
  система не поднимется или не даст результата.
- **Доступ к репозиторию.** Репозиторий `github.com/mrflxxxme/techmost-scout`
  **приватный** (`docs/remote-setup.md`) — анонимное клонирование по HTTPS не
  сработает, GitHub ответит так, будто репозитория не существует. Способ
  аутентификации подробно описан в разделе 2; заранее нужен только сам факт,
  что доступ к репозиторию у вас есть (аккаунт с правами на чтение
  `mrflxxxme/techmost-scout` или его владелец рядом).
- **`git` на сервере.** На минимальных образах VPS (типично для облачных
  Ubuntu/Debian) `git` не входит в базовый набор пакетов:

  ```bash
  sudo apt-get update && sudo apt-get install -y git
  ```

  (команда для Debian/Ubuntu; на другом дистрибутиве — свой пакетный
  менеджер, `git` в нём есть почти наверняка).
- **Docker с плагином compose.** Официальная инструкция по установке —
  <https://docs.docker.com/engine/install/> (выберите дистрибутив сервера).
  Плагин `docker compose` (без дефиса, вторая версия) входит в стандартный
  набор пакетов Docker Engine с 2022 года и отдельной установки, как правило,
  не требует. Проверить, что всё поднялось, после установки:

  ```bash
  docker compose version
  ```

## 2. Код на сервере

Репозиторий приватный, и обычный `git clone https://github.com/...` без
аутентификации не сработает: неаутентифицированный запрос к приватному
репозиторию GitHub отвечает так, будто его не существует, а логин с паролем
GitHub не принимает с 2021 года. Ниже два рабочих способа, первый —
рекомендуемый.

### Способ 1 (рекомендуется) — SSH deploy-ключ только на чтение

Deploy-ключ привязан к одному конкретному репозиторию и не даёт доступа ни к
каким другим репозиториям аккаунта — в отличие от личного SSH-ключа
пользователя. Генерируется прямо на сервере, никуда, кроме настроек
репозитория, копировать закрытую часть не нужно.

```bash
ssh-keygen -t ed25519 -f ~/.ssh/techmost-scout-deploy -N "" -C "techmost-scout deploy key"
cat ~/.ssh/techmost-scout-deploy.pub
```

Скопируйте вывод второй команды (открытый ключ, начинается с `ssh-ed25519`) и
добавьте его в GitHub: **Settings репозитория → Deploy keys → Add deploy
key** — вставьте значение, галочку «Allow write access» **не включайте**:
ключу для деплоя нужно только читать код.

Клонируйте репозиторий по SSH, явно указав только что созданный ключ, и
закрепите его за репозиторием на будущее — тогда и `git pull` в разделе 8
будет ходить тем же способом без дополнительных флагов:

```bash
GIT_SSH_COMMAND="ssh -i ~/.ssh/techmost-scout-deploy -o IdentitiesOnly=yes" \
  git clone git@github.com:mrflxxxme/techmost-scout.git
cd techmost-scout
git config core.sshCommand "ssh -i ~/.ssh/techmost-scout-deploy -o IdentitiesOnly=yes"
cd docker
```

### Способ 2 — токен доступа в URL (если SSH недоступен, например провайдер блокирует исходящий порт 22)

Создайте в GitHub персональный токен с доступом **только на чтение этого
одного репозитория**: **Settings аккаунта → Developer settings → Personal
access tokens → Fine-grained tokens → Generate new token**, «Repository
access» — «Only select repositories» → `techmost-scout`, «Permissions» →
Repository permissions → Contents → **Read-only**. Подставьте токен в URL
клонирования:

```bash
git clone https://<ТОКЕН>@github.com/mrflxxxme/techmost-scout.git
cd techmost-scout/docker
```

**Токен в открытом виде остаётся в истории оболочки** — та же оговорка, что и
для пароля Caddy (раздел 4): почистите историю после клонирования
(`history -d <номер_строки>` или `history -c`). Токен также сохраняется в
открытом виде в `.git/config` репозитория (адрес `origin` содержит его) — это
не проблема, пока доступ к серверу есть только у вас, но если понадобится
отозвать токен, сначала обновите `origin` без него:
`git remote set-url origin https://github.com/mrflxxxme/techmost-scout.git`
(тогда `git pull` начнёт спрашивать логин и токен заново).

Дальше по тексту подразумевается, что текущий каталог оболочки —
`techmost-scout/docker`.

## 3. Секреты

Скопируйте шаблон и заполните значения:

```bash
cp ../.env.example .env
nano .env
```

Обязательные для боевого окружения значения:

- **`APP_ENV=prod`** — закрывает `/api/docs` и `/api/openapi.json`
  (РЕШ-224): код открывает схему только при значении, буквально равном `dev`
  или `test` — пустая строка, опечатка и любое другое значение уже дают
  закрытую схему. Опасен ровно один случай: переменной нет вовсе — тогда
  умолчание `config.py` подставляет `dev`, и схема открыта кому угодно в
  интернете. Это единственная переменная, которую нельзя оставить как в
  `.env.example` (там умолчание `dev`).
- **`WEB_AUTH_USER`** и **`WEB_AUTH_PASSWORD`** — вход в веб-интерфейс. Смените
  умолчание `change-me`, иначе первый рубеж защиты не работает.
- **`DEEPSEEK_API_KEY`** — без него не работает ни одна стадия конвейера
  (основной провайдер моделей, РЕШ-171).
- **`YANDEX_SEARCH_API_KEY`** и **`YANDEX_CATALOG_ID`** — платный поиск по
  русскоязычному вебу; без обеих переменных источник `yandex_search` не
  собирается вовсе (`backend/app/search/__init__.py`), веб-кандидатов не
  будет.
- **`ROSPATENT_API_KEY`** — источник патентов Роспатента обязателен по ключу
  (с Т-14 режима «без ключа» у него нет): без значения патентных кандидатов не
  будет ни одного.

Файл `.env` остаётся только на сервере, в каталоге `docker/`. В git он не
попадает: шаблон `.env` в корневом `.gitignore` действует на любой глубине, в
том числе на `docker/.env`. Не коммитьте и не публикуйте этот файл никаким
другим способом.

## 4. Caddy

В `docker/Caddyfile` ровно три места, которые заменяются руками при деплое
(контракт этапа, зафиксирован тестом `tests/test_caddyfile.py`):

| Плейсхолдер | На что заменить |
|---|---|
| `scout.example.ru` | боевой домен |
| `admin@example.ru` | почта для уведомлений ACME (Let's Encrypt) |
| `ХЭШ_ПАРОЛЯ_ЗАМЕНИТЬ_ПРИ_ДЕПЛОЕ` | вывод команды хеширования пароля ниже |

Хэш пароля для `basic_auth` получается тем же бинарником, что и в образе
`caddy:2-alpine`, без установки чего-либо на сервер:

```bash
docker run --rm caddy:2-alpine caddy hash-password --plaintext '<ПАРОЛЬ>'
```

**Пароль в открытом виде остаётся в истории оболочки** после этой команды.
После того как хэш скопирован в `Caddyfile`, историю стоит почистить —
например, `history -d <номер_строки>` для конкретной команды или `history -c`
для всей истории текущей сессии.

Заменить плейсхолдеры можно вручную в редакторе или строкой `sed` (не забудьте
подставить свои значения вместо `<ДОМЕН>`, `<ПОЧТА_ACME>` и `<ХЭШ>`):

```bash
sed -i \
  -e 's/scout\.example\.ru/<ДОМЕН>/' \
  -e 's/admin@example\.ru/<ПОЧТА_ACME>/' \
  -e 's/ХЭШ_ПАРОЛЯ_ЗАМЕНИТЬ_ПРИ_ДЕПЛОЕ/<ХЭШ>/' \
  Caddyfile
```

## 5. Сборка и запуск

```bash
docker compose build
docker compose up -d
docker compose ps
```

Явного отдельного шага «сначала соберите образ сервиса `backup`» не нужно:
`backup` в `docker-compose.yml` не имеет своего `build`, а ссылается на тег
`techmost-scout-app:local`, который строит сервис `scout`. `docker compose
build` собирает сервис `scout` первым (единственный сервис с ключом `build` в
файле), и тег становится доступен раньше, чем `docker compose up -d` попытается
поднять `backup`.

**Цена РЕШ-220.** Образ приложения тяжёлый: помимо самого приложения, сборка
ставит Chromium для печати PDF (`playwright install --with-deps chromium` в
`docker/Dockerfile`). На сервере с 2 ГБ оперативной памяти сборке может не
хватить памяти без файла подкачки. Если `docker compose build` падает или
зависает, создайте своп заранее:

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
```

(Чтобы своп переживал перезагрузку, добавьте строку `/swapfile none swap sw 0
0` в `/etc/fstab` — это обычная практика, не специфика этого проекта.)

## 6. Перенос демо-базы (РЕШ-222)

Если на сервер переносится готовая база `scout.db` (например, демо-данные,
подготовленные заранее), важен точный порядок — иначе файл достанется root
внутри тома, а процесс приложения (uid 10001, не root, см.
`docker/Dockerfile`) не сможет в него писать:

```bash
docker compose stop scout
docker compose cp ./scout.db scout:/srv/scout/data/scout.db
docker compose run --rm -u root scout chown scout:scout /srv/scout/data/scout.db
docker compose start scout
```

Если демо-база не переносится, а приложение просто стартует с чистого листа —
этот шаг не нужен: пустая база создаётся сама при первом запуске.

## 7. Проверка деплоя

```bash
docker compose ps
curl -sI https://<ДОМЕН>/health
```

Ожидаемое:

- в `docker compose ps` все сервисы (`scout`, `caddy`, `backup`) в состоянии
  `running`, у `scout` дополнительно `healthy` (проверка встроена в образ,
  `docker/Dockerfile`, `HEALTHCHECK`, опрашивает `/health` каждые 30 секунд);
- `curl -sI https://<ДОМЕН>/health` возвращает код ответа Caddy — `401` без
  логина и пароля `basic_auth` или `200` при их указании (`curl -sI -u
  scout:<ПАРОЛЬ> https://<ДОМЕН>/health`) — оба варианта подтверждают, что
  HTTPS и сертификат Let's Encrypt работают. Если ответа нет вовсе —
  проверьте A-запись домена и раздел 10.

Дальше вручную: вход по паролю в веб-интерфейс (`WEB_AUTH_USER` /
`WEB_AUTH_PASSWORD` из `.env`, а следом — вход Caddy, если он запрошен
браузером отдельно) и открытие `/demo`.

Это та же последовательность, которую владелец присылает по DLG-1 (ворота
Э5-1, `.planning/PLAN.md`): вывод `docker compose ps`, вывод `curl -sI
https://<ДОМЕН>/health` и подтверждение, что вход по паролю и `/demo`
открываются.

## 8. Обновление версии

```bash
git pull
docker compose build
docker compose up -d
```

`git pull` выполняется из любого подкаталога репозитория (`techmost-scout`
или `techmost-scout/docker` — не важно) тем же способом аутентификации, что
и клонирование в разделе 2, без дополнительных шагов: при способе 1
(SSH deploy-ключ) `git config core.sshCommand`, выставленный сразу после
клонирования, сохраняется в `.git/config` репозитория и подхватывается
автоматически; при способе 2 (токен в URL) сам токен уже сохранён в адресе
`origin` в `.git/config` и переиспользуется без повторного ввода.

**Отдельно про справочник господдержки.** Именованный том `scout-data`
наполняется содержимым каталога `/srv/scout/data` из образа (в том числе
файлом `data/gov_support.yaml`) только при **первом создании** тома. Если
новая версия принесла обновлённый `gov_support.yaml`, повторная сборка образа
на уже развёрнутом сервере файл на томе не тронет — том уже существует и
своё содержимое не перезаписывает. Обновить справочник на уже поднятом
сервере нужно вручную, скопировав файл из свежего образа поверх файла на томе:

```bash
docker compose cp scout:/srv/scout/data/gov_support.yaml /tmp/gov_support.yaml
docker compose cp /tmp/gov_support.yaml scout:/srv/scout/data/gov_support.yaml
```

(Первая команда сработает только после того, как контейнер `scout` уже
пересоздан из нового образа — `docker compose up -d` выше — поэтому файл в
контейнере уже новый, а вторая строка кладёт его копию явно на том, поверх
старого содержимого.)

**Если связку поднимали раньше по инструкции без `name` в `docker-compose.yml`,
перед `docker compose up -d` из этого раздела проверьте имена томов** —
`docker volume ls | grep -E "scout|caddy"` (фильтр `grep scout` без `caddy`
пропускает старые тома Caddy — их имена подстроки `scout` не содержат) и
раздел 10, «Тома переименовались после обновления, база пропала». Иначе
`up -d` тихо создаст новые пустые тома, и последствия будут выглядеть как
исчезновение базы.

## 9. Копии базы

Сайдкар `backup` (`docker/docker-compose.yml`) раз в сутки делает горячую
копию `scout.db` через `sqlite3.Connection.backup()` стандартной библиотеки
Python и кладёт её в отдельный том `scout-backups` (не тот же том, что у
рабочей базы, — копия на одном томе с оригиналом не переживает повреждение
этого тома). Старые копии старше 14 дней сайдкар удаляет сам. Наружу, за
пределы сервера, копии не уезжают (РЕШ-223) — это осознанное ограничение MVP,
не забытая настройка.

Посмотреть список копий:

```bash
docker compose exec backup ls -l /backups
```

Восстановиться из копии (том с копиями смонтирован в `backup` на чтение и
запись под `/backups`, а не в сам `scout`, поэтому файл переносится через
хост):

```bash
docker compose stop scout
docker compose cp backup:/backups/scout-<дата-и-время>.db ./scout-restore.db
docker compose cp ./scout-restore.db scout:/srv/scout/data/scout.db
docker compose run --rm -u root scout chown scout:scout /srv/scout/data/scout.db
docker compose start scout
rm ./scout-restore.db
```

Имя файла копии — точная дата и время в UTC, `scout-ГГГГММДД-ЧЧММСС.db` (см.
команду сайдкара в `docker-compose.yml`); подставьте нужное значение из
вывода `ls -l /backups` вместо `<дата-и-время>`.

## 10. Разбор проблем

Первый шаг при любой странности — встроенная диагностика внутри контейнера
приложения:

```bash
docker compose exec scout scout doctor
```

Она печатает по каждому ключу и источнику, настроен он или нет и почему —
без утечки значений секретов.

**Вход в веб-интерфейс работает, а `/health` через Caddy вечно отвечает
`401` с правильным паролем.** Похоже на «забыл пароль», но чаще это раздел 4:
плейсхолдер `ХЭШ_ПАРОЛЯ_ЗАМЕНИТЬ_ПРИ_ДЕПЛОЕ` в `Caddyfile` не заменён на
хэш. Caddy не откажется стартовать из-за буквальной строки на месте хэша —
он просто никогда не примет к ней ни один пароль. Проверьте `Caddyfile` на
сервере: если плейсхолдер всё ещё на месте, повторите раздел 4 и
перезапустите `caddy` (`docker compose up -d caddy`).

**PDF не собирается.** Если печать карточки в PDF падает на отсутствии
браузера (редкий случай — Chromium уже поставлен на этапе сборки образа, но
мог не переехать при ручном вмешательстве в том), доустановите его внутри
контейнера от root, чтобы права на файлы браузера остались корректными:

```bash
docker compose exec -u root scout python -m playwright install --with-deps chromium
```

**Копия базы не идёт или молчит.** Сайдкар `backup` поднимается из того же
образа, что и приложение (общий тег `techmost-scout-app:local`), и делает
копию средствами стандартной библиотеки Python
(`sqlite3.Connection.backup()`) — сети на старте и при перезапуске ему не
нужно, устанавливать нечего (РЕШ-229, отменяет более ранний план с базовым
`alpine` и `apk add sqlite`). Если копия не создаётся, отказ виден в
журнале — сайдкар печатает причину в stderr и продолжает цикл, а не гасит
ошибку молча:

```bash
docker compose logs backup
```

**`backup` вообще не стартует, а `docker compose ps` не пишет про него
ничего похожего на ошибку.** У сайдкара в `docker-compose.yml` задано
`depends_on: {scout: {condition: service_healthy}}` — он ждёт, пока `scout`
пройдёт HEALTHCHECK, и это осознанно (без ожидания первая попытка копии
приходится на ещё не созданный файл базы). Следствие: если `scout` не
доходит до состояния `healthy` (см. раздел «Проверка деплоя»), `backup` так
и останется не запущенным — `docker compose ps` покажет его как не
поднявшийся, а не как упавший с ошибкой, и в `docker compose logs backup`
не будет вообще ничего. Чинить нужно `scout`, не сайдкар: копия базы
зависит от здоровья приложения, а не наоборот.

Отдельно у `backup` стоит `pull_policy: never` — сайдкар никогда не полезет
за образом в реестр (тега `techmost-scout-app:local` там и не существует,
его собирает только `scout`). Если образ ещё не собран, `backup` откажется
стартовать сразу с понятной ошибкой вместо попытки что-то скачать из
интернета. Это ожидаемое поведение, а не поломка: решение — собрать образ
(`docker compose build`), а не искать сеть или реестр.

**Журналы вообще.** У всех трёх сервисов (`scout`, `caddy`, `backup`) в
`docker-compose.yml` задана ротация JSON-логов (10 МБ, 3 файла на сервис):

```bash
docker compose logs -f scout
docker compose logs -f caddy
docker compose logs -f backup
```

Если `caddy` не поднимается — почти всегда одно из двух: A-запись домена ещё
не разошлась по DNS (Let's Encrypt не может подтвердить владение доменом) или
`scout` не прошёл healthcheck (`caddy` ждёт `scout` в состоянии `healthy` по
`depends_on`, раздел «Healthcheck» плана этапа) — проверьте
`docker compose ps` и `docker compose logs scout` в этом случае.

**Тома переименовались после обновления, база «пропала».** В
`docker-compose.yml` задана директива `name: techmost-scout` — она фиксирует
имя проекта, чтобы контейнеры не зависели от имени каталога развёртывания
(без неё compose берёт имя из каталога, обычно `docker`). Следствие: меняются
и имена именованных томов. Раньше (без `name` в файле) они назывались
`docker_scout-data`, `docker_scout-out`, `docker_caddy-data`,
`docker_caddy-config`, `docker_scout-backups`; теперь —
`techmost-scout_scout-data`, `techmost-scout_scout-out`,
`techmost-scout_caddy-data`, `techmost-scout_caddy-config`,
`techmost-scout_scout-backups` (полный список — ключ `volumes` в
`docker/docker-compose.yml`).

Если связку успели поднять по прежней версии инструкции, а затем обновили код
и выполнили `docker compose up -d` из раздела 8 — compose не найдёт тома со
старыми именами и молча создаст новые, пустые. Приложение стартует, база
инициализируется с нуля, и со стороны это выглядит как «после обновления вся
база и все прогоны исчезли», хотя реальные данные лежат нетронутыми в старом
томе.

Проверить, не эта ли причина. Фильтр по `scout` один не годится: старые тома
Caddy (`docker_caddy-data`, `docker_caddy-config`) подстроки `scout` в имени
не содержат и под него не попадут — а «дублирования нет» по итогам такой
проверки будет ложным выводом, и старый том с сертификатами Let's Encrypt
останется незамеченным:

```bash
docker volume ls | grep -E "scout|caddy"
```

Томов у связки всего пять, так что не менее надёжно — вывести список без
фильтра вовсе и свериться глазами:

```bash
docker volume ls
```

Если в списке одновременно есть `docker_scout-data` и
`techmost-scout_scout-data` (или похожая пара для любого из оставшихся
четырёх томов — `scout-out`, `caddy-data`, `caddy-config`, `scout-backups`) —
это она: старый том с данными существует рядом с новым пустым.

Перенести данные из старого тома в новый (на примере `scout-data`; тот же
приём с заменой имён томов и внутреннего пути — для `scout-out`,
`caddy-data`, `caddy-config`, `scout-backups`):

```bash
docker compose stop scout
docker run --rm \
  -v docker_scout-data:/from:ro \
  -v techmost-scout_scout-data:/to \
  alpine sh -c "cp -a /from/. /to/"
docker compose start scout
```

Источник смонтирован `:ro` — это страховка от опечатки в направлении
копирования, а не необходимость: `cp -a` источник и так не меняет.

Шаг смены владельца нужен только для `scout-data` и `scout-out` — это тома
сервиса `scout`, который работает не от root (uid 10001, см.
`docker/Dockerfile`), и после переноса от root файлы окажутся ему
недоступны на запись:

```bash
docker compose run --rm -u root scout chown -R scout:scout /srv/scout/data
```

(Для `scout-out` — то же самое с путём `/srv/scout/out` вместо
`/srv/scout/data`.) Для `caddy-data` и `caddy-config` этот шаг не нужен и
выполнять его не надо: `caddy:2-alpine` работает от root, пользователя
`scout` в этом образе не существует, и команда просто откажет с ошибкой. Том
`scout-backups` тоже без этого шага — он и так принадлежит root, сайдкар
`backup` читает и пишет в него под `user: "0:0"` (`docker/docker-compose.yml`).

Проверьте результат по разделу 7 (вход в веб-интерфейс, история прогонов на
месте) и только после этого удаляйте старый том — до подтверждения, что
данные видны в приложении, его лучше не трогать:

```bash
docker volume rm docker_scout-data
```

Эту процедуру никто не прогонял на реальном Docker (перенос данных между
двумя именованными томами через одноразовый контейнер) — прежде чем
применять на боевом сервере, стоит один раз проверить порядок команд на
тестовом стенде.
