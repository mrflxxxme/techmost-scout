# Исполнимая спецификация «ТехМост Скаут»

Версия 2.1 · 10 августа 2026 · руководитель разработки: Кирилл Уклонский (uklonskiy.k@gmail.com)

Этот документ — рабочее задание для ИИ-агентов и **единственный источник
истины по требованиям** (РЕШ-11). Продуктовые требования перенесены сюда из
PRD (раздел 2а); PRD v1.0 выведен в архив
([docs/archive/prd-scout-v1.md](archive/prd-scout-v1.md)) и требований больше
не содержит — не опираться на него. Правила работы в репозитории — в
[CLAUDE.md](../CLAUDE.md).

По моделям приоритет — качество данных и себестоимость: DeepSeek — основной
провайдер для всех стадий + бесплатные источники, YandexGPT — резерв на
случай его отказа (РЕШ-171, ГигаЧат выпилен из кода). Claude — инструмент
разработки, не часть продукта; Perplexity и Claude API в рантайме не
используются нигде.

## 0. Как пользоваться этим документом

**Руководителю.** Работа ведётся командой агентов по циклу из
[CONVENTIONS.md](team/CONVENTIONS.md): один этап (Э*n*-*m*) проходит грилл, план,
реализацию, ревью, верификацию, пост-аудит и заканчивается воротами с вашей
подписью. Запуск — `/team-start Э2-3`. Не переходи к следующему этапу, пока не
подписаны ворота текущего: проверки написаны так, чтобы вы убедились сами за
10–15 минут, не читая код.

Ручной режим (без команды) тоже работает: дайте агенту задачу дословно из
раздела этапа, добавив «см. docs/team/CONVENTIONS.md и INVARIANTS.md».

**Агенту.** У каждой задачи есть: что делать, где, контракт (входы-выходы,
имена, форматы), проверка (команда и ожидаемый результат) и границы («не
делать»). Задача считается выполненной, когда проверка проходит и её вывод
показан в ответе. Выход за границы — ошибка, даже если код работает.

**Обозначения.** ✅ — сделано в скелете, можно опираться. ⬜ — предстоит.
🔗 — зависит от внешнего ключа или регистрации (см. `deps-manual.md`).

### Грабли, на которые уже наступили — не наступайте снова

1. **Подстановки в промптах.** Промпты содержат метки `{{BRIEF_JSON}}` и
   подобные. Код их не заполнял, и модель получала метку текстом вместо данных.
   Симптом был обманчивым: карточки собирались, но проверяющая стадия писала
   «кандидаты не переданы» и занижала уверенность каждой карточке. Заполнять
   только через `render_prompt`, состав меток закреплён тестом.
2. **Просить модель вернуть входные данные обратно.** Скоринг требовал
   переписать объект кандидата в ответ — ответ на батч из десяти кандидатов не
   влезал в лимит токенов и обрывался. Ссылайтесь на входные элементы номерами.
3. **Щедрость в плане поиска.** Двадцать четыре формулировки — это до сотни
   обращений к внешним API на один запрос бизнеса и обрыв ответа по токенам.
   Восемь точных формулировок работают лучше.
4. **Рассуждающие модели и лимит токенов.** DeepSeek V4-Flash сначала пишет
   `reasoning_content`, потом ответ. Скупой `max_tokens` даёт пустой `content`
   без всякой ошибки. Обрыв JSON лечится не просьбой «исправь», а повтором с
   удвоенным лимитом — это уже делает роутер.
5. **YAML с двоеточием в значении.** `note: Ровно наш сценарий: закрывает…`
   делает `gov_support.yaml` нечитаемым для парсера. Такие значения — в кавычки.
6. **Спасать ответ из рассуждений — только сбалансированный JSON.** Когда
   `content` пуст, в `reasoning_content` лежит проза размышлений, внутри которой
   может быть готовый ответ. Отдавать эту прозу разборщику целиком бесполезно:
   вычленяйте скобочный блок через `extract_json_block` (он учитывает кавычки).
7. **Каждой стадии — свой `max_tokens`, и стандартных 4096 не хватает никому.**
   Интейк — 8000, план поиска — 8000, скоринг — 8000 (батч оценок — 16000),
   извлечение кандидатов — 7000, карточка — 7000, проверка — 6000, сводка —
   14000 (Д-3 волны Э2-З: сводка собирает отчёт по всем отобранным карточкам
   сразу, короткого лимита проверки ей не хватало). Симптом нехватки у
   рассуждающих моделей не «ошибка лимита», а пустой ответ или обрыв JSON на
   середине.

   **Числа проверяются кодом, а не глазом:** `tests/test_stage_token_budgets.py`
   разбирает пакет `app.pipeline` и не даёт завести стадию без явного
   `max_tokens` либо с лимитом ниже 6000. Правя эти числа здесь, проверьте, что
   замок с ними согласен.

   История, чтобы не наступить третий раз. Изначально здесь стояло «стандартных
   4096 хватает интейку, скоринг — 4000». Оба утверждения оказались ложными и
   стоили нам двух дефектов: РЕШ-61 (extractor 4096 → 7000, обнаружен аудитом) и
   РЕШ-65 (скоринг 4000 → 8000, обнаружен живым прогоном — стадия отдавала
   нейтральные оценки всем кандидатам, то есть ранжирование было мертво).
   Интейк жил на умолчании роутера вообще без `max_tokens` и уцелел только
   потому, что реальные брифы короче худшего случая.

## 2. Архитектурные решения, которые не обсуждаются

1. **Модель выбирается по стадии, а не глобально.** ГигаЧат выпилен из кода
   (РЕШ-171): из рабочей среды он физически недоступен, а главное требование к
   LLM сейчас — качество, а не бесплатный тариф. Все восемь стадий считает
   DeepSeek V4-Flash ($0.14 за миллион входных токенов, при кэше префикса — в
   пятьдесят раз дешевле). Измеренная стоимость запроса — 3–5 ₽, экономить
   дальше нечего. YandexGPT — резерв на случай отказа DeepSeek.
   Маршруты в `LLM_STAGE_ROUTES`, меняются правкой `.env` без изменения кода.
   Стадия `extractor` (извлечение кандидатов из сырых выдач) в маршрутах уже
   прописана, но в коде появляется только в задаче Э2-5 — до неё её не
   существует, не опираться.
2. **Системный промпт и справочники всегда в начале сообщения** — так DeepSeek
   кэширует префикс. Порядок сообщений менять нельзя.
3. **Поиск строится на бесплатных источниках.** Crossref (без ключа, 50 запросов
   в секунду) — рабочая лошадка по публикациям; КиберЛенинка через OAI-PMH —
   единственный открытый российский источник; arXiv — препринты; открытые
   данные Роспатента — патенты. OpenAlex поиск разрешён со счётчиком и суточной
   нормой (РЕШ-72): $0,001 за запрос, бесплатно $0,10 в день (сто запросов),
   расход печатается отдельной строкой в `scout run`; обогащение по DOI
   остаётся основным назначением источника.
   Платный веб-поиск (Яндекс) — по необходимости, за ним нет бесплатной замены:
   у Brave бесплатный тариф закрыт в феврале 2026.
4. **Витрина партнёров — приоритетный слой.** При равенстве ключа склейки
   выигрывает запись из витрины: она проверена человеком и у неё есть контакт.
5. **Один процесс.** FastAPI отдаёт и API, и страницы на Jinja; интерактив —
   фрагментами HTML для HTMX. Формы работают и без JavaScript.
6. **Отказ источника не роняет запрос** — попадает в `sources_unavailable`.
7. **SQLite.** Postgres, Redis, очереди — не в этом MVP.

## 2а. Продуктовые требования (перенесены из PRD v1.0, очищены от устаревшего)

Раздел заменяет PRD (РЕШ-11). Упоминаний Perplexity, Claude API в рантайме и
ЕГИСУ НИОКР здесь нет сознательно — эти каналы исключены (§2, deps-manual
«Что НЕ нужно делать»).

### Что это и для кого

«ТехМост Скаут» — внутренняя ИИ-система: по свободному описанию
технологической задачи бизнеса находит и оформляет **5–7 вариантов
научно-исследовательских решений разных стадий зрелости** с обязательными
ссылками на первоисточники. Черновик валидирует научный со-основатель; клиенту
ничего не уходит без валидации.

Роли: **оператор** (Кирилл, позже аналитик) — вводит запрос, отвечает на
уточнения, редактирует отчёт, экспортирует; **валидатор** (научный
со-основатель или сдельный эксперт) — вердикт и комментарий по каждой
карточке; **зритель** (клиент на встрече) — видит демо и финальный отчёт,
в систему не входит. Доступ — один общий вход по паролю, без личных кабинетов.

### Главный критерий приёмки

На 3 реальных запросах из проблемных интервью Фазы 0 система выдаёт
шорт-листы, в каждом из которых **не менее 3 карточек валидатор оценивает
≥4 из 5**, **без выдуманных фактов** (каждое утверждение подтверждено
ссылкой), при полном цикле «запрос → провалидированный отчёт» **≤ 24 часов**.
Протокол — §8.

### Вспомогательные метрики

| Метрика | Цель |
|---|---|
| Время пайплайна (запрос → черновик) | ≤ 60 минут |
| Стоимость одного запроса (API) | ≤ 1 000 ₽ |
| Источников на карточку | ≥ 2 независимых, все утверждения со ссылками |
| Покрытие типов источников на запрос | ≥ 4 из: публикации, патенты, гранты, веб (РЕШ-173); тип `contest` в метрику не засчитывается (РЕШ-85). Предусловие — ключ Яндекс-поиска (РЕШ-13) |
| Демо-режим | показ заготовленного кейса ≤ 5 минут без сбоев |

### Функциональные требования

- **FR-1.** Ввод запроса свободным текстом, поле до 10 000 знаков.
- **FR-2.** 3–5 уточняющих вопросов одним экраном; ответ «не знаю» допустим.
- **FR-3.** Структурированный бриф (отрасль, суть, ограничения и измеримые
  требования (РЕШ-116), целевая зрелость, география, бюджет/сроки)
  показывается на подтверждение и правку до запуска поиска.
- **FR-4.** Проверка обезличенности: предупреждение при похожих на названия
  компаний сущностях, без блокирующего запрета.
- **FR-5.** Поиск минимум по типам: публикации, патенты, гранты/проекты,
  организации. Каналы — из §2: Crossref, КиберЛенинка, arXiv, Semantic
  Scholar, Роспатент, витрина партнёров, Яндекс-поиск (сайты институтов,
  РНФ, ФСИ); OpenAlex — поиск со счётчиком и суточной нормой и обогащение по
  DOI (РЕШ-72).
- **FR-6.** Курируемая витрина (ручной ввод + CSV): приоритет в выдаче и
  метка «проверенный партнёр».
- **FR-7.** Международные источники включаются; у зарубежных решений —
  пометка о применимости в РФ.
- **FR-8.** Дедупликация и скоринг: релевантность, зрелость, доступность
  разработчика, свежесть, полнота данных.
- **FR-9.** Выдача 5–7 карточек. Обязательные поля: суть; стадия зрелости
  «лаборатория → прототип → пилот → серия» (+TRL); разработчик с контактными
  зацепками; чем подтверждено (ссылки); применимость; риски; господдержка из
  справочника (218-ПП, доращивание, вычет); следующий шаг.
  Секция «Ранние разработки и команды» идёт после основных карточек и в
  лимит 5–7 не входит (РЕШ-85).
- **FR-10.** Каждый факт со ссылкой; нет данных — «не найдено», выдумывать
  запрещено (инвариант 1, стадия verifier).
- **FR-11.** Сводка: сравнительная таблица + рекомендация 2–3 абзаца +
  перечень источников.
- **FR-12.** Оценка уверенности (высокая/средняя/низкая) с пояснением.
- **FR-13.** Экран ревью валидатора: вердикт + комментарий по карточке;
  статус «провалидирован» после всех вердиктов.
- **FR-14.** Редактирование карточек оператором до и после валидации.
- **FR-15.** Экспорт PDF/DOCX в фирменном стиле; футер «Подготовлено системой
  ТехМост Скаут, проверено [эксперт], дата».
- **FR-16.** Демо-режим: кейсы трёх отраслей без ожидания пайплайна;
  переключатель «демо» скрывает служебные элементы.
- **FR-17.** Все запросы, брифы, кандидаты, карточки, вердикты и отчёты
  сохраняются; список прошлых запросов с поиском.

### Э2-3 ✅ 🔗 Веб-поиск: оба контура на Яндексе

Два поисковика делят веб по языку и географии: Google — мир, Яндекс — РФ. Оба
отдают `SourceType.WEB` и склеиваются между собой по нормализованному адресу.

**Было (11 августа 2026), файл удалён — `backend/app/search/google_search.py`
(РЕШ-174).** Мировой охват — университеты и институты за пределами РФ,
спин-оффы, англоязычные витрины технологий. Google Programmable Search
(Custom Search JSON API), 100 запросов в сутки бесплатно. Было реализовано:
постраничный обход до 100 ссылок на формулировку, счётчик платных запросов
`queries_used` и оценка стоимости, склейка дублей по нормализованному URL,
мягкая обработка 403/429, язык выдачи намеренно не ограничен.

**Google закрыт не нами (11 августа 2026).** Custom Search JSON API закрыт для
новых клиентов, создание систем в режиме «весь веб» прекращено в августе 2025,
сам API отключается 1 января 2027. Ключ владельца получает 403. Значит мировой
контур ложится на Яндекс — и это делает задачу ниже не «второй половиной», а
единственной.

**Сделано (11 августа 2026): `backend/app/search/yandex_search.py`, оба
контура (РЕШ-21).** Закрывает то, у чего нет API вообще: страницы лабораторий,
центров трансфера, проекты РНФ и Фонда содействия инновациям. Плюс мировой веб.

**Два режима одного ключа** (проверено живым вызовом):
- `SEARCH_TYPE_RU` — российская выдача, сайты вузов и ЦТТ;
- `SEARCH_TYPE_COM` — международная выдача yandex.com. На английском запросе
  вернула репозитории Манчестера, Åbo Akademi, Университета Альберты, Aston,
  PubMed Central, Taylor & Francis, ResearchGate.
  Режим выбирается по `SearchQuery.lang`: `ru` → RU, `en` → COM. Английские
  формулировки в плане поиска и так есть (`Brief.keywords_en`).

**Что реализовано.**
- Ключ `settings.yandex_search_api_key` + `settings.yandex_catalog_id`; без
  обоих значений адаптер не попадает в сборку.
- Асинхронный поиск: POST `searchAsync` → опрос операции → base64-XML. Разбор
  сверен с фактическим ответом, а не с документацией: подсветка запроса живёт в
  `<hlword>` внутри `<title>`, фрагменты — в `<passages>`, дата в `<modtime>`.
- Жёсткий предел шесть платных запросов на прогон, счётчик `queries_used`.
- `raw_id` — общий `normalize_url` из `app/search/base.py`, поэтому страница из
  любых двух веб-источников склеивается в одного кандидата.
- Отказы Яндекса приходят внутри XML (`<error code=…>`), а не кодом HTTP —
  разбираются отдельно и гасят источник, а не прогон.

**Отступление от первоначального контракта, осознанное.** Планировалось сужать
выдачу операторами `site:` по типу источника — `rscf.ru`, `fasie.ru`,
`*.edu.ru`, `*.ras.ru`. Оставлено только для грантов и только в российском
контуре: `site:` ограничивает жёстко, и применение его ко всем запросам убило
бы открытый веб, ради которого источник и заводился. Минус-слова по мусорным
агрегаторам не заводились вовсе — пустой файл в `data/` протух бы раньше, чем
понадобился; вернёмся к этому по итогам Э1-2, когда будет видно, какой мусор
реально приходит.

**Проверка.** Тесты на respx: выбор контура по языку, предел запросов,
сужение до реестров только для грантов в RU, склейка дублей по
нормализованному URL, отказ внутри XML, незавершившаяся операция, ошибка
операции, отсутствие ключей. Живой `scout doctor`:
«ок, мировой контур: ссылок 3, доменов 3, 1 платный запрос».

**Общий предел, который надо честно писать в отчёт.** Ни один поисковый API не
даёт «все сайты мира»: это индекс Яндекса, без закрытых разделов,
содержимого за формой входа и запрещённого в robots.txt. Охват растёт не
постраничным обходом, а числом формулировок в плане поиска.

появляются плавно, видны стадии и стоимость, нет мигания и рывков.

### Э3-5 ✅ Отчёт с карточками

Принято на подменах (respx/фикстуры, без сети); живой прогон через браузер —
на воротах этапа Э3.

**Файлы.** `backend/app/web/routes/report.py`, `backend/app/report_overrides.py`,
`templates/report.html`, `templates/_card.html`

**Что делать.** Страница отчёта: сводка, сравнительная таблица, карточки.

**Контракт.**
- Стадия зрелости — шкалой из четырёх засечек (`.maturity`), активные золотом.
- Уверенность — значком (`.badge`, для низкой `.badge.low`).
- Блок «Чем подтверждено» со ссылками обязателен; при пустом evidence —
  красная плашка «Нельзя показывать клиенту: нет подтверждений».
- До валидации на странице и в экспорте видна пометка «ЧЕРНОВИК».
- Режим правки: поля карточки редактируются, машинный текст сохраняется в
  `editor_overrides`, а не затирается.

**Проверка.** Открыть отчёт по прогону из Э1-2: карточки читаемы, ссылки
кликабельны, пометка «черновик» на месте, правка сохраняется после
перезагрузки страницы.

## 6. Этап 4 — валидация экспертом, выгрузка, демо

### Э4-1 ⬜ Ревью эксперта

**Файлы.** `backend/app/web/routes/`, `templates/review.html`

**Что делать.** `GET /requests/{id}/review` — экран для научного
со-основателя; `POST /cards/{id}/verdict` — вердикт.

**Контракт.**
- Вердикт: `approve | reject | rework`, оценка 1–5, комментарий.
- В форме вердикта — поле имени проверяющего, предзаполненное настройкой
  окружения `REVIEWER_NAME` (РЕШ-197): обычный путь эксперта — без ручного
  ввода, при необходимости поле можно поправить.
- Экран открывается по ссылке и **работает на телефоне** — эксперт смотрит
  между делами. Кнопки не меньше 44 пикселей, карточки в одну колонку.
- Когда по всем карточкам есть вердикт, статус запроса → `validated`, и в
  отчёте пометка «черновик» заменяется на «проверено: имя, дата».
- Оценка 1–5 нужна для протокола приёмки (см. §8) — это не украшение.

**Проверка.** Открыть ссылку на смартфоне, поставить вердикты по всем
карточкам, убедиться: статус стал `validated`, пометка сменилась.

### Э4-2 ⬜ Выгрузка в PDF и DOCX

**Файлы.** `backend/app/export/pdf.py`, `backend/app/export/docx.py`,
`templates/report_print.html`, `backend/app/cli.py`

**Что делать.** PDF — печатью страницы `report_print.html` через playwright
(`page.pdf`). DOCX — через python-docx. В `cli.py` добавить команду
`scout export <request_id> --pdf|--docx` — сейчас её нет (есть только
doctor, run, serve, showcase).

**Контракт.**
- Обложка PDF — чернильная, в стиле питч-дека; карточки — с окантовкой;
  в футере «Подготовлено системой ТехМост Скаут, проверено: имя, дата».
- Шрифт Segoe UI с системным запасным; внешних шрифтовых сетей не подключать.
- Ссылки в PDF остаются кликабельными.
- Раскладка выгрузок (РЕШ-202): PDF доступен и через CLI, и кнопкой «Полный
  текст (PDF)» на странице отчёта; DOCX — только через CLI, без обложки.
- Экспорт черновика (`status != validated`) заперт: без флага `--draft`
  `scout export` отвечает отказом и файла не создаёт; с флагом `--draft`

  обложке и на каждой странице, подпись «проверено» в футере не печатается.
- Зависимости из группы `export` ставятся отдельно: базовая установка не должна
  тянуть браузер.

**Проверка.** `scout export <request_id> --pdf` создаёт файл; открыть и
убедиться: текст не обрезан, ссылки работают, стиль совпадает с деком.

### Э4-3 ⬜ Демо-режим

**Файлы.** `backend/app/web/routes/`, `backend/app/pipeline/demo.py`

**Что делать.** Воспроизведение сохранённого прогона без обращения к API:
события прогресса берутся из `PipelineLog`, исходные пропорции стадий
сохраняются, а общая длительность показа — параметр (РЕШ-201).

**Контракт.**

- Полный показ — не дольше пяти минут.

**Проверка.** Отключить сеть, запустить демо-кейс: прогресс и отчёт

## 7а. Этап 6 - «Рынок» и аналоги (план)

Статус: **план, не задание.** Раздел фиксирует стыки, о которых договорились
на грилле экосистемы 13.10.2026 (РЕШ-238…245). Задачи ниже станут заданиями
после грилла этапа 6 и плана в `.planning/PLAN.md`; до этого код по ним не
пишется. Этап начинается только после ворот Э5 и пройденной приёмки Э5-2
(РЕШ-243).

**Что строим.** Второй режим того же движка (РЕШ-238): «Рынок» - готовые
продукты, поставщики и зарубежные аналоги для предпринимателей, МСБ и
регионов. Режим «Наука» остаётся как есть со всеми тестами и воротами.
Слой аналогов строится по образцу конкурсного класса (`contest_cards`,
РЕШ-85, РЕШ-92): свой тип источника, своя секция отчёта, вне лимита 5-7
основных карточек.

**Что решает грилл этапа, а не этот план.** Пересмотр границ «клиент в систему
не входит», «Вне скоупа MVP» (§2а) и инварианта 9 под публичный фримиум;
величина лимита экспресс-скана на человека; механика оплаты полного отчёта;
набор источников аналогов; нейтральное имя публичного режима (РЕШ-239).

**Процесс.** Э6-4 и Э6-5 - связки с экосистемой, лёгкий режим (один цикл
ревью и короткий ADR, РЕШ-244). Э6-1…Э6-3 и Э6-6 затрагивают качество
выдачи и инвариант 1 - полный цикл CONVENTIONS с воротами.

### Э6-1 ⬜ Вид решения, регион и потребность в брифе

**Файлы.** `backend/app/schemas.py`, `backend/app/models.py`,
`backend/app/web/brief_store.py`, `prompts/intake.md`

**Контракт.**

  стадии; остальные три значения - режим «Рынок».
- `Brief.region_code` - код субъекта ОКАТО, 2 цифры, по справочнику RADAR;
  `Brief.need_id` - стабильный ID потребности из таксономии RADAR. Строка
  `geography` остаётся для текста (РЕШ-242).
- Режим подачи `mode: business | gov` (РЕШ-241) - поле брифа, совпадает с

### Э6-2 ⬜ Слой аналогов

**Файлы.** `backend/app/schemas.py`, `backend/app/pipeline/`,

**Контракт.**
- `SourceType.ANALOG`; в `prompts/planner.md` - тип запроса `analog`.
- `AnalogCard`: страна (ISO 3166-1 alpha-2), бизнес-модель, тяга (traction),

- Закрывает **FR-7** («у зарубежных решений - пометка о применимости в РФ»):

- Источники-кандидаты из разбора: Яндекс-поиск по зарубежной зоне, Wikidata,

**Контракт.** «Бизнес» - весь мир с оценкой переносимости. «Гос» - только

**Проверка.** Отчёт в режиме «Гос» не содержит недопустимой страны ни в
карточках, ни в сводке, ни в PDF, DOCX и JSON; мутация условия в любом
потребителе краснит тест.

**Файлы.** `backend/app/export/markdown.py`, `pdf.py`, `docx.py`,
`backend/app/export/json.py`

**Контракт.**

- `export/json.py` - тот же клиентский вид, что и у печати (видимость

### Э6-5 ⬜ JSON-API и события экосистемы

**Файлы.** `backend/app/web/routes/`, `backend/app/config.py`

**Контракт** (РЕШ-242).

### Э6-6 ⬜ Экспресс-скан режима «Рынок»

**Контракт** (РЕШ-240). Бесплатно, бот и сайт, лимит на человека: 3 решения
без контактов, 2-3 зарубежных аналога с переносимостью в РФ, господдержка.
Следующая ступень - полный отчёт 5-10 тыс. ₽, дальше - консалтинг Кирилла вне

## 8. Протокол приёмки

0. **Предусловия** (без них приёмка не начинается): заведён ключ Yandex Search
   API (`deps-manual.md`, п. 8) — без него недостижима метрика покрытия ≥4
   типов источников (РЕШ-13); назначен валидатор; готовы три обезличенные
   задачи (`deps-manual.md`, п. 12).
1. Взять три реальных обезличенных задачи из проблемных интервью Фазы 0 —
   по одной на отрасль (нефтегаз, фарма, агропром).
2. Прогнать каждую без ручной помощи пайплайну. Зафиксировать время и стоимость.
3. Научный со-основатель оценивает каждую карточку 1–5:
   **5** — можно показывать клиенту как есть; **4** — годно после лёгкой
   правки; **3** — полезно, но требует переработки; **2** — слабо; **1** —
   мусор или ошибка. Дополнительно проверяет по три случайных факта в каждой
   карточке по ссылкам.
4. **Приёмка пройдена, если** в каждом из трёх отчётов не менее трёх карточек с
   оценкой ≥4; среди проверенных фактов нет ни одного неподтверждённого
   ссылкой; в каждом отчёте покрыты не менее 4 типов источников (публикации,
   патенты, гранты, веб — метрика из раздела 2а, РЕШ-173); полный цикл до
   провалидированного отчёта — не больше суток; стоимость машинной
   обработки — не больше 1000 ₽ на запрос.
5. Заполнить `docs/acceptance.md`: таблица оценок, комментарии эксперта,
   фактические время и стоимость.

Если приёмка не пройдена, вероятные причины в порядке частоты: слабый скоринг
(правится Э2-4), плохие патентные кандидаты (Э2-2), промпт карточки требует
более жёстких правил (правка `card_author.md` с записью в CHANGELOG).
