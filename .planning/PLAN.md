# План этапа

Закреплённый план текущего этапа. Составляется на шаге 1 цикла агентом
`planner`, дальше не трогается (§6 `docs/team/CONVENTIONS.md`): исполнители,
ревьюер и верификатор сверяются с одним и тем же текстом, иначе критерии приёмки
можно подогнать под то, что получилось.

Менять план на ходу нельзя. Если по ходу этапа выяснилось, что план неверен, —
это остановка и новый прогон шага 1 (`/team-plan <этап>`) с записью причины в
`.planning/DECISIONS.md`. Файл перезаписывается целиком при переходе к новому
этапу; прежний план не архивируется, его след — запись в `JOURNAL.md`.

Состояние задач (закрыта, в работе, не начата) отслеживается в
`.planning/STATE.md`, а не правкой этого файла.

## Структура задачи

У каждой задачи семь полей, все обязательны. Ниже — пример заполнения, а не
задача к исполнению.

### Э2-1 · Обогащение через OpenAlex по DOI

- **Исполнитель.** implementer-1
- **Зависимости.** нет. Ключ `OPENALEX_API_KEY` — задача владельца
  (`docs/deps-manual.md`, п. 5); без ключа задача выполняется на подменах, живая
  проверка уходит в отложенность `DLG-N`
- **Файлы.** `backend/app/search/openalex.py`, `tests/test_openalex.py`. Общие
  контракты не трогаются, поэтому задача пригодна для параллельного запуска
- **Критерии приёмки.**
  1. `enrich_by_doi(dois) -> dict[str, dict]` возвращает цитируемость, тип
     работы, аффилиации авторов и признак открытого доступа;
  2. запросы только вида lookup по DOI, батч по 50, пауза 0.2 с между батчами;
  3. без ключа метод возвращает пустой словарь и пишет в лог «обогащение
     пропущено», не поднимая исключение;
  4. существующие непустые `snippet` и `org` не перезаписываются;
  5. метод `search` остаётся нереализованным намеренно.
- **Способ проверки.** `pytest tests/test_openalex.py -v` — внешние ответы
  подменены через respx, обращений в сеть нет (инвариант 7); `scout doctor`
  показывает openalex «нет» без ключа; `grep -n "api.openalex.org/works"
  backend/app/search/openalex.py` — только адрес lookup, ни одного обращения к
  search-эндпоинту (РЕШ-10)
- **Предел циклов.** ревью — 2, правки в аудите — 1, починка падающих тестов —
  3 попытки, дальше стоп и эскалация (§4)

## Параллельность

Строкой ниже планировщик указывает, какие задачи идут одновременно, а какие
последовательно, и почему. До трёх исполнителей, каждый в своём git worktree, и
только при непересекающихся наборах файлов. Задачи, меняющие общие контракты
(`backend/app/schemas.py`, `backend/app/config.py`, `prompts/`), выполняются по
одной; остальные ждут слияния (§11).
