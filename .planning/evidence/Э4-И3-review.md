## Инварианты (все десять)

1. **Факт без ссылки** — задача не трогает сборку карточек и `evidence`;
   не применимо, нарушений нет.
2. **Ключевой.** `validated` выставляется только когда `all_cards_reviewed`
   возвращает True по строкам `solution_cards` **обеих** секций
   (`review.py:187`, тест `test_статус_validated_считает_обе_секции`).
   Строка `verdicts` не появляется без непустого имени (`REFUSAL_EMPTY_NAME`,
   `review.py:159-161`, тест `test_пустое_имя_отклоняется`, мутация 1 выше).
   Автоотправки клиенту нет — маршрут только пишет в БД и возвращает HTML-
   фрагмент оператору/эксперту. **Гонка двух конкурентных POST на последнюю
   карточку** оценена по коду (живой конкурентный тест не заводился, по
   инструкции не обязателен): SQLite-движок (`aiosqlite`, `db.py`) допускает
   только одного активного писателя одновременно — вторая транзакция INSERT
   ждёт коммита первой (либо повторяется драйвером). Каждый запрос читает
   `card_ids`/`effective` **после** своей записи в той же, ещё не
   зафиксированной транзакции — заново из БД, но за пределы своей транзакции
   не видит; когда первая транзакция коммитится, вторая (стартующая или
   продолжающая запись после снятия блокировки) читает уже актуальное
   состояние, включая первую вставку. Двойной установки статуса не
   происходит (само присвоение `RequestStatus.VALIDATED` идемпотентно), и
   потери перехода в `validated` тоже не происходит — просадка возможна
   только если строки вставляются вне транзакционных гарантий SQLite, чего в
   коде нет. Риск теоретический и не специфичен для этой задачи (общее
   свойство `AsyncSession`/SQLite во всём проекте), для потолка нагрузки
   продукта («десятки запросов в месяц», CLAUDE.md) он не материален.

## Разбор по пунктам задания

- **Каждый вердикт — новая строка.** `session.add(VerdictRow(...))` — только
  `add`/`flush`, ни одного `UPDATE`/`DELETE` по `Verdict` в файле (грепом
  подтверждено). Два вердикта подряд по одной карточке дают две строки
  (`test_вердикт_пишет_новую_строку_дважды`, действующий — последний по
  `created_at`/`id` через `effective_verdicts`, эта функция не в этой
  задаче — она сдана и принята в Э4-И1).
- **Отказ 400 при пустом имени / оценке вне 1–5 / неизвестном решении**,
  **404 при несуществующей карточке** — все четыре ветки в коде на месте
  (`review.py:155-169`), два первых — с тестами, два — без (см. инвариант
  №8 выше, не блокирует).
- **`exported` не понижается** — явная проверка `if ... != EXPORTED`
  (`review.py:190`), тест `test_exported_не_понижается_до_validated` проходит.
- **Предзаполнение имени `settings.reviewer_name`** — `review.html:40`,
  `context={"reviewer_default": get_settings().reviewer_name, ...}` в
  `show_review`; тест проверяет `value="Мария Петрова"` в разметке.
  Литералов `"reject"` в Python-коде задачи нет — единственное вхождение
  строки `reject` во всём diff это значение опции `<option value="reject">` в
  `review.html` (HTML-атрибут, не сравнение строк в бизнес-логике); в
  `submit_verdict` решение всегда конструируется через `VerdictDecision(decision)`
  и сравнивается как `schemas.Verdict`.
- **44px** — правило `.verdict-form select, .verdict-form input[type="text"],
  .verdict-form textarea, .verdict-form button { min-height: 44px; }`
  (`theme.css:396-402`) покрывает **все** интерактивные элементы формы
  вердикта: выпадающие списки решения и оценки, текстовое поле имени,
  комментарий и кнопку отправки — соответствует формулировке SPEC «кнопки и
  поля не меньше 44 пикселей», а не только кнопкам.
  `rg "grid two|grid three" review.html` — пусто, карточки в одну колонку.
- **Экран без фильтра reject** — сознательное решение, задокументировано в
  докстроке модуля и обосновано: эксперт должен видеть и пересматривать свои
  прежние отклонения, в отличие от клиентского вида. Согласуется с РЕШ-198
  («вердикты видны оператору на экране ревью») и с контрактами плана, где
  `build_export_view` перечислен только для потребителей клиентского вида
  (страница отчёта, PDF, DOCX, `scout export`) — экран ревью в этот список не
  входит.
- **Overrides оператора на экране ревью.** Экран читает `report_json` через
  `pipeline.persistence.load_report` **напрямую**, без
  `report_overrides.apply_overrides`. Если оператор до открытия ревью правил
  карточку через `POST /cards/{id}/edit`, эксперт увидит **необлагороженный**
  (исходный, сгенерированный моделью) текст поля, а не тот, что реально уйдёт
  клиенту после наложения правки в `build_export_view`. Формально это не
  нарушает ни один из десяти инвариантов и не входит ни в критерии приёмки,
  ни в «Файлы»/«Что делает» задачи Э4-И3 (`export/view.py` и
  `report_overrides.py` не в списке файлов этой задачи, в «Читать первым»
  задачи они тоже не упомянуты — в отличие от `verdicts.py`). Это стык между
  Э4-И2 (правки, `build_export_view`) и Э4-И3 (экран ревью), который план не
  развёл явно ни в одну, ни в другую сторону. **Не блокирую** приёмку этой
  задачи: она сделана строго по контрактам плана, но пункт выношу как
  совет/эскалацию ниже — решение нужно от владельца или на аудите волны 1,
  а не от исполнителя этой задачи в одиночку.
