## 1. Часть А+Б — платформы по классам

### 1.1. Хакатоны

#### Devpost — самая большая витрина хакатонных решений, и она закрыта условиями

**Машинный доступ.** `https://devpost.com/api/hackathons?page=1` → **200,
`application/json`, 9661 Б** [замер 17.08.2026]. Отдаёт список хакатонов:
`id`, `title`, `displayed_location`, `open_state`, `thumbnail_url`, `url`,
`time_left_to_submission`. Это каталог **событий**, а не решений.

**Решения через API не достаются.** `devpost.com/software/search?query=catalyst&format=json`
→ **202, тело 0 байт** [замер]. Тот же адрес без `format=json` → **202, 0 байт**
[замер]. 202 с пустым телом — это отложенная отдача/бот-фильтр, а не выдача.
Публичного API по проектам (`/software`) я не нашёл. **[НЕ УСТАНОВЛЕНО]**,
существует ли неофициальный путь — искать его не стал, см. следующий абзац.

**Юридическая чистота — здесь стоп.** Условия Devpost прямо запрещают
автоматический доступ. Дословно из Code of Conduct:

> «Uses manual or automated software, devices, scripts robots, or other means or
> processes to access, "scrape," "crawl" or "spider" the Site, User Content
> (including User Profiles and Team Pages), or any related data or information»

[док: `info.devpost.com/legal/terms-of-service`]. При этом `robots.txt` для
`User-agent: *` содержит пустой `Disallow:` (то есть формально разрешает всё),
но отдельными строками закрывает `/` для `anthropic-ai`, `GPTBot`, `CCBot`,
`ChatGPT-User`, `Google-Extended`, `Bytespider`, `FacebookBot`, `Omgilibot`
[замер]. **Противоречие robots и ToS разрешается в пользу ToS** — ровно та же
логика, по которой мы отказались от скрейпа Google (РЕШ-55).

**Статус ИС — лучший из всех, что я видел.** Дословно:

> «Makers have and shall retain sole and exclusive title and ownership of all
> Software and Submissions, and all Intellectual Property Rights relating
> thereto, unless: (a) the Official Rules of a Hackathon state clearly that the
> Maker will be required to transfer property of the Submission…»

[док, там же]. То есть по умолчанию права у команды, **но каждый конкретный
хакатон может это переопределить своими Official Rules** — а значит,
проверять придётся хакатон за хакатоном, автоматически это не решается.

**Объём.** **[НЕ УСТАНОВЛЕНО]** живым замером — счётчик проектов недоступен без
обхода 202. Порядок величины по заявлениям площадки — сотни тысяч проектов,
но собственной цифры у меня нет, поэтому в отчёт её не ставлю.

**Полнота полей.** По каталогу хакатонов — название, место, статус, ссылка,
срок. По решениям — не проверено. **Русскоязычное покрытие:** мизерное,
площадка англоязычная; российские команды встречаются, но контент на английском.

#### Major League Hacking (MLH)

`mlh.io/robots.txt` → **200**, `Allow: /`, закрыты `/graphql`, `/v4/`,
`/admin/`, приглашения [замер]. **Открытого API нет** — `/graphql` явно
запрещён роботам. MLH — это календарь студенческих хакатонов, сами решения
живут на Devpost. **Как источник решений самостоятельной ценности не имеет.**

#### HackerEarth

`www.hackerearth.com/robots.txt` → **403** [замер]. Закрыт даже robots.txt —
на входе бот-защита. По РЕШ-55 обход не строим. **Отпадает.**

#### Devfolio

`api.devfolio.co/api/hackathons` → **422 Unprocessable Entity** [замер].
Эндпоинт существует и что-то ждёт от нас в параметрах, но публичной схемы API
я не нашёл. **[НЕ УСТАНОВЛЕНО]** — можно докопаться, но это уже реверс-инжиниринг
непубличного API, и вопрос условий использования остаётся открытым.

#### Kaggle

`www.kaggle.com/api/v1/competitions/list` → **401** [замер]. API официальный,
задокументированный, ключ — **бесплатный токен из личного кабинета**
(регистрация разрешена РЕШ-55 п. 3). Отдаёт соревнования, датасеты, ноутбуки
(kernels) — то есть **и решения тоже, в виде кода**.

**Оговорка, которая важнее доступа:** Kaggle — это соревнования по машинному
обучению на предоставленных данных. Для отраслевого запроса промышленника
(«катализатор для гидроочистки», «покрытие от коррозии») там нет ничего.
Ценность появляется только на узком классе задач: прогноз отказов
оборудования, компьютерное зрение в контроле качества, оптимизация режимов.
**Русскоязычное покрытие:** интерфейс и контент английские.

### 1.2. Открытые инновации и призовые конкурсы

#### XPRIZE — зрелые решения, но закрытые по условию

`www.xprize.org/robots.txt` → **200**, `Allow: /`, запрещены `/form/` и
`/graphql` [замер]. **Открытого API нет.** Каталог соревнований и финалистов —
это обычные страницы сайта; сбор возможен только веб-поиском (наш контур
Яндекса, Э2-3) плюс точечное чтение страниц.

**Статус ИС — команда сохраняет всё:** «All teams maintain full ownership of
their intellectual property, both IP that was brought to the competition and
developed in pursuit of the XPRIZE»; «XPRIZE claims no interest in any team's
Intellectual Property» [док: Competition Guidelines / Competitor Agreement,
`xprize.org`].

**И здесь же ловушка для нас.** По тем же guidelines: «All details relating to
team technology, innovations, or methods submitted to XPRIZE at the submission
deadlines will remain strictly confidential». То есть **техническая суть решения
в открытый доступ не попадает** — публично есть название команды, страна,
общее описание и место. Для карточки этого мало: `essence` будет рекламным
абзацем, а не техническим содержанием. **XPRIZE ценен не как источник описаний,
а как источник имён команд, до которых можно дотянуться.**

#### InnoCentive / Wazoku Crowd — здесь ИС уходит заказчику

**Машинный доступ:** публичного API не нашёл; каталог челленджей —
страницы `innocentive.com/challenges/…`. **[НЕ УСТАНОВЛЕНО]**, есть ли выгрузка.

**Статус ИС — критично для нашей патентной чистоты.** По документации площадки:
«Theoretical IP Transfer Challenges require Solvers to transfer all rights to
the Intellectual Property (IP) for which they are awarded»; «Depending on the
Challenge requirements, Solvers are required to either transfer or license the
IP in their solutions to the Seeker»; «Solvers that do not win retain the rights
to their solution after the evaluation» [док: `support.wazoku.com/types-of-challenges`,
`innocentive.com/participating-in-innocentive-challenges/`].

**Следствие для продукта:** победившее решение InnoCentive **больше не
принадлежит команде** — оно у корпорации-заказчика, чаще всего непубличной.
Такая карточка вредна: мы приведём клиента к разработчику, который уже не
вправе распоряжаться разработкой. **Это первый класс источников, где статус ИС
меняет саму пригодность записи, а не только примечание к ней.**

#### HeroX

`www.herox.com/robots.txt` → **200**, `Crawl-delay: 1`, закрыты
`/message/`, `/protected/`, служебные параметры сортировки; контент разрешён
[замер]. Формальных препятствий вежливому обходу нет. **Открытого API
не нашёл.** Условия по ИС **[НЕ УСТАНОВЛЕНО]** — `herox.com/terms` отдал 404
при попытке чтения; HeroX работает и по модели «права у решателя», и по модели
передачи заказчику, зависит от конкретного челленджа. Проверять нужно
поштучно.

#### Topcoder, NineSigma, yet2

`api.topcoder.com/v5/challenges` → **404** [замер] — по этому адресу API v5
не отвечает; **[НЕ УСТАНОВЛЕНО]**, где актуальная точка входа. NineSigma и
yet2 — брокеры технологий, работающие по закрытым запросам; открытых витрин
решений у них нет по модели бизнеса. **Как источник для нас — маловероятны.**

### 1.4. Студенческие и отраслевые

#### iGEM — единственный источник этого класса, который сегодня работает без ключа

**Машинный доступ.** `https://api.igem.org/v1/teams` → **200,
`application/json`** [замер 17.08.2026]. `?year=2024` → **200** [замер].
`https://api.igem.org/v1/teams/5033` → **200**, карточка команды [замер].

**Полнота полей** (по факту ответа, а не по документации):
`id`, `name`, `slug`, `region`, `country`, `city`, `lat`, `lng`,
`institutions` (массив: `name`, `city`, `country`, `website`, `department`),
`organiserType` (`higher-education`), `section` (`overgrad`), `program`,
`status` (`accepted`), `year`, `isRemote`, `applicationDate`,
`competitionUUID`, `village UUID`.

**Что это значит для нас — важное:** API отдаёт **команды и организации, но не
описания проектов**. Описание проекта iGEM живёт на вики команды
(`YYYY.igem.wiki/<slug>`), а `slug` в ответе API есть — то есть **связка
«API → адрес описания» собирается**. Реферат/аннотация по API
**[НЕ УСТАНОВЛЕНО]**, других эндпоинтов я не проверял.

**Объём.** Точной цифры живым замером не снял (ответ постраничный, до конца не
листал). Годы в выдаче — от **2014** до **2024** [замер: записи с `year:2014` и
`year:2024`]. Порядок — тысячи команд за все годы.

**Статус ИС.** iGEM построен на **открытом Registry of Standard Biological
Parts** — сдача частей в реестр обязательна и они публичны. **[НЕ ПРОВЕРЕНО]**
дословной формулировкой, но модель принципиально открытая, в отличие от
корпоративных челленджей. Это делает iGEM **самым чистым источником класса
с точки зрения патентной проверки** — и одновременно означает, что
запатентовать оттуда нечего, всё уже раскрыто (что для промышленного заказчика
скорее плюс: свобода использования).

**Русскоязычное покрытие:** есть российские команды (МГУ, МФТИ и др.),
но вся документация на английском.

«Победитель хакатона: права на цифровое решение остались за нами»
(`habr.com/ru/articles/514224/`) — то есть **единого правила нет, читать нужно
положение каждого конкурса**.

**ФСИ («Старт», «УМНИК») — здесь наоборот всё хорошо:** права на РИД
регистрируются **на грантополучателя**, то есть остаются у разработчика
[док, вторичные источники; **дословной цитаты из положения Фонда не снял**].
Но ФСИ — это гранты, а не конкурс решений; этот слой уже стоит в плане Э2-3
как «РНФ / ФСИ через Яндекс», отдельным источником его заводить незачем.

## 2. Часть В — три вопроса, которые важнее объёма

### 2.1. Статус интеллектуальной собственности

Разброс по площадкам оказался **шире, чем разброс по любому другому признаку**,
и он не коррелирует ни с географией, ни с размером:

| Модель | Кто владеет решением | Площадки |
|---|---|---|
| **Права у команды по умолчанию** | Команда | Devpost (с оговоркой «unless the Official Rules… state clearly»), XPRIZE («XPRIZE claims no interest») |
| **Права уходят заказчику при выигрыше** | Корпорация-постановщик | InnoCentive/Wazoku (Theoretical IP Transfer, RTP), российские корпоративные хакатоны (типовая формулировка об отчуждении партнёру) |
| **Обязательное раскрытие** | Никто, всё публично | iGEM (Registry of Standard Biological Parts) |
| **Права у грантополучателя** | Разработчик | ФСИ («Старт», «УМНИК») |
| **Не установлено** | — | HeroX, challenge.gov, Topcoder, Devfolio |

**Вывод, который я считаю главным по всей разведке:** для этого класса
источников **статус ИС — не примечание к карточке, а условие её пригодности**.
У публикации автор известен и права на статью не мешают лицензировать
технологию. У решения корпоративного хакатона права могли уйти третьему лицу
ещё до того, как мы про решение узнали — и тогда карточка ведёт клиента
в тупик: разработчик найден, а распоряжаться разработкой он не вправе.

**Практический вывод.** Определять это автоматически нельзя: правило живёт
не на платформе, а в положении конкретного конкурса. Значит, у карточки этого
класса нужен **явный статус ИС из трёх значений** — `у команды` /
`передано организатору или заказчику` / `не установлено` — со ссылкой на
положение. При `не установлено` карточка **не должна выходить клиенту как
готовое предложение**: это лид на проверку, а не решение.

### 2.2. Зрелость — как класть в нашу шкалу без завышения

Наша шкала — `lab → prototype → pilot → series`, плюс `trl_estimate` 1–9
(`MaturityStage`, `schemas.py`). Честное отображение:

| Что за источник | `maturity_stage` | `trl_estimate` | Почему так |
|---|---|---|---|
| Решение хакатона выходного дня (Devpost, «Цифровой прорыв», Codenrock) | `prototype` **потолок**, по умолчанию `lab` | **2–3, не выше 4** | 24–48 часов работы. Даже победитель — демонстрация замысла, а не образец |
| Kaggle-соревнование | `lab` | **2–3** | Модель на чужом датасете; на реальных данных заказчика не проверялась |
| iGEM | `lab` | **2–3** | Студенческий проект за лето, лабораторный стенд |
| InnoCentive Theoretical | `lab` | **2–3** | По определению площадки — «not yet a proof of concept» |
| InnoCentive RTP | `prototype` | **4–5** | По определению — «a prototype that proves an idea», требуется валидированное решение или физический образец |
| XPRIZE, финалист/победитель | `prototype`→`pilot` | **5–7** | Испытания на площадке организатора по регламенту, с независимым замером |
| Up Great (НТИ) | `prototype`→`pilot` | **5–6** | Технологические барьеры с натурными испытаниями |
| ФСИ «Старт» | `prototype` | **4–5** | Грант на НИОКР с требованием коммерциализации |

**Правило, которое я предлагаю зафиксировать: `maturity_stage` для этого класса
никогда не выставляется моделью по тексту описания.** Описание хакатонного
проекта пишет команда, и оно всегда звучит как готовый продукт («система
предиктивной диагностики для промышленных предприятий»). Модель, читая такой
текст, поставит `pilot`. Поэтому стадию должен ставить **код, по типу источника
и типу конкурса**, а не модель по описанию — так же, как `pdf_urls` заполняет
код, а не модель (`SolutionCard`).

**И второе:** призовое место **не повышает зрелость**. Первое место на хакатоне
означает, что решение лучше остальных за те же 48 часов, а не что оно ближе
к внедрению. В скоринге место уместно как признак `relevance`/`completeness`,
но не `maturity`.

### 2.3. Живость команды — здесь у этого класса главное преимущество

По нашим весам `accessibility` стоит 0.20 — наравне со зрелостью
(`ScoredCandidate.total`). И вот по этому признаку решения конкурсов **лучше
публикаций**, что стоит проговорить владельцу отдельно:

- у публикации есть аффилиация первого автора (`_first_affiliation` в
  `crossref.py`) — организация, но не человек, и часто пятилетней давности;
- у решения конкурса есть **имена участников команды, год, часто ссылка на
  репозиторий и на демонстрацию**.

**Признаки живости, которые снимаются машинно:**

1. **Год конкурса** — есть у всех площадок. Решение старше 3 лет без
   продолжения — почти наверняка мёртвое.
2. **Ссылка на репозиторий** — если он есть, дата последнего коммита читается
   через GitHub API без ключа и это **самый честный признак: жив проект или
   заброшен**. Это, на мой взгляд, самая ценная возможность всего класса.
3. **Организация** — у iGEM `institutions[].name` и `website` приходят прямо
   в API [замер]; вуз никуда не девается, даже если команда разошлась.
4. **Повторное участие** — команда, которая заявлялась три года подряд, живее
   разовой.

**Чего нет.** Прямых контактов (почта, телефон) **ни одна площадка в открытом
доступе не отдаёт** — и не должна, это персональные данные. Значит,
`contact_leads` для этого класса — это **организация + имена + репозиторий**,
то есть зацепки, а не контакты. Ровно то, что поле и означает по описанию
в `schemas.py`.

## 4. Вопросы владельцу

Шесть развилок, которые я не могу закрыть сам. У каждой — варианты, цена
и моя рекомендация.

### В-1. Что подключаем первым — и подключаем ли вообще в MVP

Из всего класса **машинно доступен без ключа ровно один источник — iGEM**
(`api.igem.org/v1/teams` → 200 [замер]). Всё остальное либо закрыто условиями
(Devpost), либо закрыто бот-защитой (HackerEarth), либо не имеет API вовсе
(XPRIZE, HeroX, все российские площадки).

| Вариант | Цена | Что получаем |
|---|---|---|
| **А.** Адаптер iGEM | ~1 день, ключа не надо | Тысячи команд, но **только синтетическая биология** — для нефтепереработки и машиностроения бесполезно |
| **Б.** Kaggle по бесплатному токену | ~1–2 дня + регистрация (разрешена РЕШ-55 п. 3) | Соревнования и ноутбуки; полезно **только на ИИ-задачах** заказчика |
| **В.** Отдельный контур Яндекс-поиска по конкурсам (`site:` по списку площадок), поверх готового Э2-3 | ~1 день, ключ уже есть | Покрывает **все площадки сразу, включая российские**, ценой качества — выдача сырая, идёт в extractor Э2-5 |
| **Г.** Ничего в MVP, вернуться в версии 2 | 0 | Класс не покрыт |

**Моя рекомендация — В, и только В.** Причина: у нас продукт для промышленного
заказчика в РФ, а два единственных API этого класса (iGEM, Kaggle) отраслево
узкие и англоязычные. Вариант В использует уже построенный и оплаченный канал,
даёт русскоязычное покрытие, которого владелец требует, и не создаёт нового
источника отказа. iGEM я бы держал в бэклоге как приятное дополнение —
это один день работы, но он окупится только на биотех-запросе.

### В-2. Что делать с решением, у которого статус ИС неясен

Это главная находка разведки (§2.1). У InnoCentive права **уходят
корпорации-заказчику** при выигрыше; у российских корпоративных хакатонов —
типовое отчуждение партнёру; у Devpost зависит от Official Rules каждого
хакатона. Автоматически это не определяется.

| Вариант | Цена | Риск |
|---|---|---|
| **А.** Пускать в карточки, статус ИС не указывать | 0 | **Худший.** Мы приводим клиента к разработчику, который не вправе распоряжаться разработкой. Репутационный удар по первому же кейсу |
| **Б.** Пускать со статусом `ИС не установлена` в `risks` + строкой в `confidence_note` | ~0.5 дня | Клиент видит риск, но карточка всё равно занимает одно из 5–7 мест |
| **В.** Не пускать в карточки вовсе; выводить отдельным блоком «лиды на проверку» после основной выдачи | ~1 день (новая секция отчёта) | Основная выдача остаётся чистой; лид не теряется |
| **Г.** Отбрасывать молча | 0 | Теряем ровно тот пласт, ради которого всё затевалось |

**Моя рекомендация — В.** Решение конкурса с неясной ИС — это не решение,
а зацепка: «вот команда, которая делала похожее, статус прав надо выяснять
переговорами». Смешивать её с валидированной карточкой на основе статьи —
значит обесценивать обе. Отдельный блок честно называет вещи своими именами
и при этом ничего не выбрасывает.

**Что мне нужно от вас:** согласны ли вы, что этот блок вообще уходит клиенту,
или он только для оператора?

### В-3. Прототип хакатона — это решение наравне со статьёй?

У нас жёсткая рамка: **5–7 карточек** (FR-9), валидатор должен оценить
**не менее 3 из них на ≥4 из 5** (главный критерий приёмки). Каждое место
в шорт-листе дорогое.

| Вариант | Цена | Что происходит |
|---|---|---|
| **А.** Наравне: конкурируют за те же 5–7 мест по общему скорингу | 0 | Хакатонный прототип с TRL 2–3 будет проигрывать по `maturity` и почти никогда не попадёт в выдачу. То есть источник подключим, а эффекта не будет |
| **Б.** Квота: не более 1–2 карточек этого класса из 5–7 | ~0.5 дня в оркестраторе | Гарантированное присутствие, но за счёт вытеснения зрелого решения |
| **В.** Отдельная секция отчёта «Ранние разработки и команды» после основных карточек, вне лимита 5–7 | ~1 день | Лимит не трогаем, критерий приёмки не размывается, пласт виден |

**Моя рекомендация — В, и она смыкается с В-2** (это может быть один и тот же
блок). Причина арифметическая: при весах `ScoredCandidate.total` решение с
`maturity` 2–3 проигрывает статье с `maturity` 6 около половины балла, и в
шорт-лист попадёт только при заметно более высокой релевантности. Вариант А
означает «сделали и не заметили». Вариант Б портит главный критерий приёмки:
валидатор будет ставить прототипу низкие оценки — справедливо, но за наш счёт.

### В-4. Нужен ли новый `SourceType` в схеме

Сейчас `SourceType` = `publication`, `patent`, `grant`, `org`, `showcase`,
`web` (`schemas.py`). Решение конкурса формально ложится в `web`.

| Вариант | Цена | Последствия |
|---|---|---|
| **А.** Класть в `web` | 0 | Не отличим от любой найденной страницы. Ни квоту дать, ни зрелость по типу проставить (см. §2.2), ни в отчёте отделить |
| **Б.** Новый `SourceType.CONTEST` | ~0.5 дня + правки промптов планировщика и скорера, миграция БД | Тип виден на всех стадиях; код может ставить `maturity_stage` по типу; метрика FR-«покрытие ≥4 типов» получает новый тип |
| **В.** `web` + отдельное поле-признак в `Candidate` | ~0.5 дня | Полумера, ломает симметрию `source_type` |

**Моя рекомендация — Б**, но **только если В-1 закрывается вариантом В или иным
подключением**. Заводить тип под ненаписанный адаптер незачем. Отдельно
обращаю внимание: новый тип **влияет на метрику «покрытие типов источников
≥4 на запрос»** — если `contest` начнёт засчитываться в это число, метрика
станет достигаться легче, чем задумывалось. Это надо решить сознательно.

### В-5. Devpost: их условия запрещают роботов — а каталог отдаёт JSON

Ситуация ровно как с Google в РЕШ-55, только зеркальная. `robots.txt` Devpost
для `User-agent: *` пуст (то есть разрешает), а Code of Conduct дословно
запрещает «automated software, devices, scripts robots… to access, "scrape,"
"crawl" or "spider" the Site, User Content». При этом `devpost.com/api/hackathons`
отдаёт **200 и валидный JSON без ключа** [замер].

| Вариант | Цена | Чем рискуем |
|---|---|---|
| **А.** Не трогать Devpost вовсе | 0 | Теряем самую большую витрину хакатонных решений мира |
| **Б.** Брать только `/api/hackathons` (каталог событий), решения — никогда | ~0.5 дня | Формально всё равно автоматический доступ к Site. Каталог событий сам по себе решений не даёт — ценность близка к нулю |
| **В.** Devpost только через Яндекс-поиск (`site:devpost.com`) — то есть читаем то, что поисковик уже проиндексировал | 0 сверх варианта В-1 | Мы не роботим их сайт; читаем чужой индекс. Остаётся вопрос, считается ли это обходом их запрета |
| **Г.** Написать в Devpost и спросить разрешение | ваше время, срок ответа неизвестен | Единственный полностью чистый путь к их данным |

**Моя рекомендация — В как рабочий режим, Г параллельно, если этот пласт для
вас стратегический.** Вариант Б я не рекомендую: он несёт тот же юридический
риск, что и полный обход, а пользы не даёт.

**Прошу решить прямо:** распространяется ли на Devpost та же граница, которую
вы провели по Google в РЕШ-55 (не строим обход защиты и не нарушаем условия),
или вы считаете чтение поискового индекса допустимым исключением?
