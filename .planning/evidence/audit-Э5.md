## Блокирующее

**Б1. Образ не соберётся: `docker compose build` падает на шаге `RUN chmod -R a+rX /ms-playwright`.**
`docker/Dockerfile`, строки 16–24. `ENV PLAYWRIGHT_BROWSERS_PATH=/ms-playwright` объявлен **после**
`RUN … playwright install --with-deps chromium`. Инструкции выполняются по порядку: в момент установки
переменной нет, playwright кладёт браузер в каталог по умолчанию, и `/ms-playwright` не появляется
никогда. Следующий `RUN chmod` завершается кодом 1 — сборка обрывается.

Чем подтверждено (проектным бинарём, без демона):

```
$ env -u PLAYWRIGHT_BROWSERS_PATH HOME=/root .venv/bin/python -m playwright install --dry-run chromium
  Install location:    /root/.cache/ms-playwright/chromium-1234      ← без переменной
$ PLAYWRIGHT_BROWSERS_PATH=/ms-playwright .venv/bin/python -m playwright install --dry-run chromium
  Install location:    /ms-playwright/chromium-1234                   ← с переменной, читается на установке
$ chmod -R a+rX <несуществующий_каталог>; echo $?
  chmod: cannot access ...: No such file or directory
  1
```

Второе следствие, которое переживёт даже «починку» chmod: в рантайме переменная указывает на пустой
`/ms-playwright`, а браузер лежит в `/root/.cache/ms-playwright`, куда uid 10001 не войдёт. Кнопка
«Полный текст (PDF)» не заработает на сервере, при этом весь набор тестов останется зелёным —
playwright в тестах не запускается.

Почему прошло ворота: ревью Э5-И1 прочитало «порядок `pip install` → `playwright install` → `chmod`»
и признало его верным — сверялся порядок трёх `RUN` между собой, а не положение `ENV` относительно них.
План (Э5-И1, п. 1) перечисляет `ENV` после установки той же прозой — исполнитель следовал букве.

Мутация, доказывающая слепоту стража: перестановка `ENV` и `chmod` местами (M7) — **10 passed**,
ни один тест не заметил.

Правка (один цикл): поднять `ENV PLAYWRIGHT_BROWSERS_PATH=/ms-playwright` выше `RUN pip install`;
добавить в `tests/test_docker_image.py` тест «индекс строки `ENV PLAYWRIGHT_BROWSERS_PATH` меньше
индекса строки с `playwright install`», иначе регрессия вернётся молча.

## Корректность

1. **[правка] Сайдкар копии базы: первая копия появится только через сутки.** У `backup` нет
   `depends_on` — на чистом развёртывании он стартует одновременно с приложением, база ещё не создана,
   и цикл уходит в `time.sleep(86400)`. Воспроизведено прогоном тела скрипта: `копия базы не выполнена:
   unable to open database file`, том пуст. Владелец, следуя `docs/deploy.md` §9, сутки видит пустоту.
2. **[правка] Отказ после `sqlite3.connect(dest)` оставляет файл-пустышку с именем годной копии.**
   `docker-compose.yml:89` создаёт целевой файл до копирования; при обрыве в томе остаётся
   `scout-<дата>.db` нулевого размера. Инструкция §9 велит выбирать копию по дате — восстановление из
   такого файла обнулит базу. Воспроизведено: `0 байт` рядом с тремя валидными по 5 206 016 байт.
   Лечится записью во временное имя и `os.rename` после успеха, плюс `dst.close()` в `finally`.
3. **[правка] `src.backup(dst)` ждёт снятия блокировки без таймаута.** При удерживаемой exclusive-
   транзакции проход зависает: >100 секунд до принудительного обрыва. Контейнер `running`, в журнале
   пусто, копий нет — тихий пропуск того класса, ради которого заведён инвариант №5.
4. **[ок] Ротация удаляет только свои файлы.** Чужой файл с mtime −20 суток уцелел.
5. **[ок] Работа с базой из сайдкара безопасна.** `pragma journal_mode` боевой базы = `delete`, не WAL.
6. **[ок] Права на тома.** `chown -R scout:scout /srv/scout` стоит до обеих директив `VOLUME`.
7. **[ок] Схема API закрыта настоящей сборкой.** `build_app("prod")` + `TestClient`: `/api/docs`,
   `/api/openapi.json`, `/redoc` — 404. Второго признака «мы в бою» не появилось.
8. **[ок] `caddy` ждёт живости приложения**; мутация на `service_started` поймана.
9. **[ок] Совместимость `--with-deps` с базовым образом**: в playwright 1.62 перечислены debian11/12/13.
