## Находка исполнителя (потолок 0.99) — проверена мутациями

`ProgressBroker.subscribe` закрывает поток на `event.stage == "done"` **или**
`event.fraction >= 1.0` (`progress.py:115`). Без потолка `intermediate_cap =
0.99` в `build_playback` суммарная доля трёх реальных стадий (0.1+0.2+0.7 в
float-арифметике даёт `1.0000000000000002`, при округлении `min(...,1.0)`
ровно `1.0`) достигла бы `1.0` на последней реальной стадии — поток закрылся
бы до публикации `done`, зритель не увидел бы финального события.

Проверено вручную двумя мутациями кода (правки временные, после проверки
файл восстановлен из git, `git diff` пуст):

1. Убрал `intermediate_cap` (`fraction=cumulative` вместо
   `fraction=min(cumulative, intermediate_cap)`) →
   `test_only_final_done_step_reaches_full_fraction` (чистая функция) **и**
   `test_start_publishes_events_stream_gets_stage_message_fraction`
   (настоящий `ProgressBroker` через ASGI/SSE) оба упали:
   `AssertionError: assert 'scorer' == 'done'`. Находка подтверждена на
   настоящем брокере, как и заявлено в handoff.
2. Подменил число в `_search_message` на выдуманное («42» вместо суммы
   `sources_hit`) → `test_search_message_uses_real_sources_hit_numbers_not_invented`
   упал. Инвариант №1 в показе действительно проверяется тестом, а не
   декларацией.

## Межзадачный риск (для аудита/журнала, не блокирует)

Исполнитель честно задокументировал долг `ProgressBroker`: каналы не
освобождаются после `done`, брокер общий на процесс синглтон. Свой риск он
закрыл корректно (id с 80 000 в `tests/test_web_demo.py`, докстрока
`_make_request` объясняет причину). Бомба для будущих тестов остаётся:
любой новый тестовый файл, который создаст запрос с маленьким `id` (1, 2, …)
и будет слушать тот же `ProgressBroker` в одном процессе pytest, рискует
получить чужой буферизованный `done`/событие от `test_web_demo.py`,
`test_web_flow_e2e.py` или будущих демо-тестов — то есть источник
интерференции не устранён, только обойдён с двух сторон точечно. На
практике сейчас коллизий нет (проверено двумя прогонами полного набора и
изолированным прогоном `test_web_flow_e2e.py`), но это везение по диапазонам
id, а не структурное решение. Стоит вынести отдельным пунктом в
`DECISIONS.md`/аудит волны: либо очистка каналов брокера по `done`
(отложена как РЕШ-191, Э5-1), либо общее соглашение по диапазонам id для
тестов, использующих реальный брокер, — иначе следующий исполнитель наступит
на те же грабли без объяснения в докстроке.

## Советы (не блокируют)

1. `backend/app/web/routes/demo.py` заводит `log = logging.getLogger(__name__)`,
   но нигде не вызывает `log.*` — либо мёртвый код, либо забытая защита.
   В `run.py` (`_run_pipeline`) для аналогичной фоновой задачи есть
   `try/except Exception: log.exception(...)` вокруг корутины и `finally` со
   страховкой на случай, если задача не прислала `done` (комментарий
   `run.py:196-198` — «ревью цикла 1, совет 2» по той же болезни в живом
   прогоне). В `start_demo` фоновая задача `asyncio.create_task(demo.play(...))`
   ничем не обёрнута: практический риск сейчас низкий (`play()` не делает
   I/O — только `broker.publish`, который сам гасит `QueueFull`, и `sleep`),
   но при любом будущем усложнении `play()` необработанное исключение в
   фоновой задаче будет молча проглочено asyncio, лог не получит записи, а
   зритель увидит зависший прогресс без единого сообщения об ошибке. Стоит
   либо убрать неиспользуемый `log`, либо (лучше, для симметрии с `run.py`)
   обернуть тело задачи в try/except с `log.exception` и страховочным
   финальным событием.
2. Список клиентских фраз в handoff собран для основных сообщений (
   `DONE_MESSAGE`, `STAGE_MESSAGES`, `REQUEST_NOT_FOUND`, `REFUSAL_NO_LOG`,
   кнопка «Показать», заголовки `demo.html`), но не перечисляет отдельно текст
   вводного абзаца и пустого состояния списка кейсов
   («Показ проигрывает уже сохранённый журнал прогона — без обращения к
   моделям и источникам, без сети и без единого потраченного рубля.»;
   «Демо-кейсов пока нет — разметку ставит оператор на воротах этапа.»).
   Формально это тоже новые клиентские фразы для визы владельца — стоит
   дописать при сборке общего списка фраз этапа оркестратором.
