# Ревью И-2 · цикл 1
Вердикт: ПРИНЯТЬ (блокирующих 0, советов 3)

## Разбор

Мост «синхронный хук → асинхронная очередь» устроен корректно: `hook_for`
возвращает синхронную функцию, которую `PipelineContextMixin._notify`
(`backend/app/pipeline/pipeline_context.py:76-82`) вызывает из корутины
пайплайна на том же event loop; `ProgressBroker.publish` использует
`queue.put_nowait` без await между чтением `channel.subscribers` и
регистрацией подписчика — гонок нет, потому что вся синхронная часть
выполняется одним шагом event loop без точек переключения. `call_soon_threadsafe`
не нужен, т.к. потоков в архитектуре пайплайна нет (АИ-11 планирует
`asyncio.create_task`, не отдельный поток).

Контракт плана выполнен: `subscribe` сначала отдаёт буфер (регистрация в
`channel.subscribers` — после наполнения очереди буфером, без гонки),
`done`/`fraction >= 1.0` закрывает генератор, keepalive работает через
`asyncio.wait_for(..., timeout=keepalive_interval)` без реальных пауз,
события `request_id` изолированы отдельными каналами в `dict`.

Инвариант №5 (устойчивость к отказу подписчика/переполнению) закрыт тремя
разными тестами: отключение подписчика, переполнение очереди подписчика,
переполнение общего кольцевого буфера — во всех трёх публикация не падает.

## Советы (не блокируют)

1. `_channels: dict[int, _RequestChannel]` в `ProgressBroker` не чистится
   никогда — запись на каждый `request_id`, для которого хоть раз вызвали
   `hook_for`/`subscribe`, живёт до перезапуска процесса. Сам буфер и очередь
   ограничены (`_BUFFER_SIZE`/`_QUEUE_SIZE` = 200), но количество каналов —
   нет. При десятках запросов в месяц утечка практически неощутима, но нигде
   не названа явно (докстрока объясняет только потерю прогресса при
   рестарте, не рост `_channels`). Стоит либо добавить комментарий,
   осознанно принимающий это как приемлемую цену при таком масштабе, либо
   запланировать очистку канала после `done` с задержкой (например, в И-11,
   где уже есть реестр фоновых задач и естественная точка «прогон завершён»).
2. Опечатка в докстроке `hook_for`: «пайпларну» → «пайплайну»
   (`backend/app/web/progress.py`, докстрока метода `hook_for`).
3. Часть тестов-генераторов (`test_subscriber_receives_events_in_order`,
   `test_late_subscriber_sees_buffered_events`, `test_events_of_different_requests_do_not_mix`)
   собирают события через `[... async for ...]` без обёртки в
   `asyncio.wait_for`, в отличие от `test_done_event_closes_stream` и
   `test_keepalive_on_silence`. Сейчас это не создаёт проблемы, но при
   регрессии в закрытии потока по `done` (см. мутацию 3 выше) такой тест не
   упадёт чисто, а зависнет — без `pytest-timeout` в проекте это способно
   зависить весь прогон CI. Не блокирует (описанная выше мутация всё равно
   даёт понять о поломке, просто дороже), но стоит выровнять на паттерн
   `wait_for`, если модуль будет дорабатываться в И-11.
