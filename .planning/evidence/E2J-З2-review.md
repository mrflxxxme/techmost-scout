## Разбор кода (backend/app/search/cyberleninka.py)

Диф чистый и точечный: докстрока адаптера, докстрока `search()`, стоп-словарь
и константы, разбор ответа вынесен в `_parse_articles`, `_found_count`,
`_shorten_query`. Логика повтора:

```python
payload = await self._fetch(text, size=size)
found = _found_count(payload)
candidates = self._parse_articles(payload)

short_text = _shorten_query(text)
if found == 0 and short_text and short_text != text:
    short_payload = await self._fetch(short_text, size=size)
    ...
    return candidates[:limit]

log.info("cyberleninka: «%s» → found=%s", text, found)
return candidates[:limit]
```

**Условия РЕШ-70 не смягчены.** Темп: повтор идёт через тот же `_fetch`,
который безусловно вызывает `self._throttle()` перед сетевым обращением —
ровно тот же путь, что и первый запрос, никакого обхода. `User-Agent` не
меняется между попытками (`USER_AGENT` — общая константа, честная строка с
почтой, без признаков браузера — `Mozilla`/`Chrome` в заголовках нет,
проверено тестом и глазами). Заголовки повтора — те же три (`User-Agent`,
`Accept`, `Content-Type`), никакой маскировки не добавлено. Отказ HTTP
(на первой попытке и на повторе одинаково) поднимается как `SearchError` из
`_fetch` и не перехватывается внутри `search()` — пропагирует наружу до
`_safe_search` оркестратора и, соответственно, в `sources_unavailable`;
пустой успешный ответ (`found=0`) как был, так и остался обычным пустым
списком, не отказом. Ретрай запускается **только** при `found == 0` на
успешном ответе — если первый `_fetch` кинул `SearchError`, до строки с
`short_text` управление не доходит вовсе (исключение уже пробросилось), то
есть повтор на отказе не выполняется — это соответствует контракту, а не
факту, который явно проверен отдельным тестом «повтор только при
found=0, не при отказе», но логически неизбежен по структуре кода и
подтверждён тестом `test_отказ_источника_поднимает_searcherror` (нет
`short_text` в теле запроса при мокнутом единственном 500-ответе).

**Укорачивание.** `_shorten_query`: токенизация по `\S+`, фильтр по
маленькому стоп-словарю (более полусотни предлогов/союзов/частиц,
захардкожен в модуле — не файл данных, не обращение к модели — граница
задачи соблюдена), первые `SHORT_QUERY_WORDS = 4` содержательных слова,
порядок исходной формулировки сохранён. Детерминированность и порядок
проверены тестом и лично мной (два вызова `_shorten_query` с одним и тем же
текстом дают идентичный результат, мутация «перемешать слова» ловится этим
тестом — см. ниже).

Краевые случаи по коду:
- **формулировка целиком из стоп-слов** — `if not content: content = tokens`,
  то есть в этом (маловероятном) случае берутся первые 4 токена исходного
  текста без фильтрации; корректно и честно задокументировано в докстроке
  функции;
- **формулировка короче 4 слов** — `content[:SHORT_QUERY_WORDS]` просто берёт
  меньше слов, чем есть; если после фильтрации получается ровно тот же набор
  слов, что и в исходном тексте, `short_text == text` и условие
  `short_text != text` не даёт повтору выполниться — **дубликат запроса не
  уходит на источник**, ровно то, что требовалось. Проверено юнит-тестом
  `test_укорачивание_короткого_запроса_не_меняет_его` на функции; на уровне
  `search()` отдельного интеграционного теста «короткая формулировка + found=0
  → ровно один сетевой вызов» нет — логика тривиально следует из проверенной
  функции и проверенного условия, но явного теста именно этого пути нет (см.
  советы).

## Кэш

Ключ кэша — SHA-256 от `body`, а `body` включает `q` дословно
(`cyberleninka.py:262`):

```python
body = json.dumps({"from": 0, "mode": SEARCH_MODE, "q": text, "size": size}, ensure_ascii=False, sort_keys=True)
...
raw = self._read_cache(body)
```

То есть длинная и короткая формы физически не могут попасть в один файл кэша:
разный `q` → разный `body` → разный SHA-256. Тест
`test_укорачивание_повторяет_запрос_при_нулевой_выдаче` не проверяет сам себя:
он гоняет ДВА вызова `adapter.search()` с одной и той же длинной
формулировкой и проверяет, что второй вызов не идёт в сеть повторно
(`route.call_count == 2` после обоих вызовов — то есть кэш сработал на оба
тела), а результат второго вызова идентичен первому. Это честная проверка
через фактический счётчик сетевых обращений respx, а не проверка внутреннего
состояния адаптера.

## Советы (не блокируют)

1. `_shorten_query(text)` вызывается безусловно на каждый поиск, даже когда
   `found > 0` и результат не понадобится — не влияет на корректность и цену
   (чистая строковая операция без сети), но можно перенести внутрь ветки
   `if found == 0:` для более прямого чтения кода.
2. Краевой случай «короткая форма совпадает с исходной формулировкой»
   (запрос короче `SHORT_QUERY_WORDS` содержательных слов) корректно не
   уходит на повтор — проверено юнит-тестом на `_shorten_query`, но нет
   интеграционного теста уровня `search()`, который бы явно фиксировал:
   «found=0 на уже короткой формулировке → ровно один сетевой вызов, не
   два». Логика тривиально следует из уже проверенного условия
   `short_text != text`, но явный тест закрыл бы этот путь от случайной
   поломки при будущем рефакторинге.
3. Теоретический краевой случай: если исходная формулировка содержит двойные
   пробелы (маловероятно для планировщика, но не исключено), а после
   фильтрации стоп-слов остаётся то же количество токенов, что и в исходном
   тексте, `_shorten_query` вернёт строку с нормализованными (одинарными)
   пробелами, которая формально не равна `text` (`.strip()`, но не
   `.split()`-нормализации) — тогда произойдёт один лишний сетевой запрос с
   семантически идентичной, но текстуально другой формулировкой. Не
   наблюдалось в тестах и не нарушает темп/лимит повторов (повтор всё равно
   один), просто небольшая трата запроса впустую. Не блокирует.
