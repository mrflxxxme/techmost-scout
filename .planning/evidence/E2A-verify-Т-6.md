## Критерий 2 — проверка оркестратора по коду

> **Поправка к отчёту верификатора.** В обоснование критерия 2 верификатор
> сослался на «строку 304» — это место в `stages.py`, относящееся к
> обезвреживанию меток, а не к адаптеру Яндекса. Ссылка неверная. Существо
> критерия при этом установлено независимо, тремя способами, и оркестратор
> перепроверил главный из них сам:

```
yandex_search.py:128  async def search(...)          — сужение search_raw
yandex_search.py:132  async def search_raw(...)      — единственная точка входа
yandex_search.py:154      raw = await self._run_search(...)   ← ОДИН вызов
yandex_search.py:199  async def _run_search(...)
yandex_search.py:212      self.queries_used += 1              ← счётчик растёт здесь
yandex_search.py:259  def _root(raw)                 — разбор XML один раз
yandex_search.py:281  def _to_candidates(root, ...)  — по готовому дереву
yandex_search.py:324  def _raw_records(root, ...)    — по тому же дереву
```

На один `search_raw` приходится ровно один сетевой вызов и ровно одно
увеличение счётчика; кандидаты и сырые записи собираются из **одного и того же
разобранного дерева**. Критерий выполняется по построению, а не по
договорённости.

Три независимых подтверждения: (а) трассировка кода ревьюером; (б) убитая
мутация М1 исполнителя («сырые записи берутся вторым `_run_search`»);
(в) настоящий тест, проверяющий `started.call_count == 1` и `queries_used == 1`.

**Существенно:** ревью установило, что старый `test_предел_платных_запросов_на_прогон`
удвоение **не поймал бы** — при двух запросах на формулировку счётчик всё равно
упрётся в предел 6, просто обслужено будет втрое меньше формулировок. То есть
критерий 2 держится именно новым тестом, и его качество критично.

## Проверка по существу

**«Адаптер без флага стадию не вызывает».** `YandexSearchAdapter` имеет
`needs_extraction = True` (`yandex_search.py:107`), остальные получают `False`
по умолчанию из `base.py`. Оркестратор зовёт стадию только при флаге; закрыто
тестом. Первая версия теста пропускала мутацию — проверялось «модель не
вызвана», а этого мало: структурированный источник мог пройти лишний вызов и
всё равно не дойти до модели. Закрыто защитой в заглушке (коммит `a4317c9`).

**Инвариант №4 — обезвреживание меток.** Сырой текст выдачи прогоняется через
`neutralize_placeholders` **перед** `render_prompt`: фигурные скобки со
случайной веб-страницы иначе уронили бы сборку промпта **уже после оплаченного
запроса**. Функция схлопывает сдвоенные скобки в одиночные — содержание,
уходящее в модель, не портится.

**Стоп-кран.** Проверен мутацией оркестратора (`E2A-T6-cycle2-mutation.txt`):
при удалении проброса тест даёт `DID NOT RAISE`, а в логе видно
«израсходовал 0.01 ₽ при лимите 0.01 ₽ — беру разбор адаптера». Тест ловит
именно ту регрессию, ради которой написан.

## Развилка «замена против дополнения»

Подтверждено по `dedup_key()`: у кандидата из разбора адаптера ключ — адрес
(`raw_id = normalize_url(url)`, всегда непустой), у кандидата из стадии `raw_id`
обычно пуст, поэтому ключ — нормализованное название. Это разные пространства
ключей для одной страницы: сложение протащило бы её в отбор дважды под разными
личинами. Замена верна.
