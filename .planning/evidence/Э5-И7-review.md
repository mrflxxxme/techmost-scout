## Блокирующие

1. **Неисполнимая команда: клонирование приватного репозитория без
   аутентификации.** `docs/deploy.md:39`:

   ```
   git clone https://github.com/mrflxxxme/techmost-scout.git
   ```

   Репозиторий приватный — подтверждено запросом к GitHub API
   (`"private": true` для `mrflxxxme/techmost-scout`) и явно зафиксировано в
   `docs/remote-setup.md:21` («Опубликовано в приватный
   `github.com/mrflxxxme/techmost-scout`»). Такой `git clone` по HTTPS без
   токена/ключа на чистой машине завершится отказом GitHub (для
   неаутентифицированного запроса приватный репозиторий отвечает как
   несуществующий) — либо интерактивным запросом логина/пароля, которого
   GitHub с 2021 года не принимает (нужен personal access token или SSH-ключ).
   Ни в `docs/deploy.md`, ни в разделе 1 «Что нужно заранее» нет ни слова про
   получение доступа к репозиторию — только про домен, ключи API и Docker. Ни
   в одном другом документе репозитория (`docs/remote-setup.md`,
   `.planning/DECISIONS.md`) тоже нет инструкции, как клонировать приватный
   репозиторий на новый сервер. Это первая же исполняемая команда раздела 2,
   и её отказ останавливает всю инструкцию в самом начале — именно тот класс
   находки, ради которого это ревью прогоняет команды буквально, а не читает
   их как описание действия. Нужен явный шаг: либо PAT в URL
   (`https://<ТОКЕН>@github.com/...`), либо SSH-клон с добавленным
   deploy-ключом сервера в настройки репозитория, с той же оговоркой про
   секрет в истории оболочки, что уже сделана для пароля Caddy.

## Советы (не блокируют)

1. Раздел 1 «Что нужно заранее» не упоминает, что на многих минимальных
   образах VPS (Ubuntu/Debian cloud) `git` не установлен по умолчанию — стоило
   бы добавить `apt-get install -y git` рядом с `git clone`, это тривиально,
   но раз документ уже настолько буквален в остальном, лучше не оставлять и
   этот шаг на «само собой понятно».
2. В разделе 7 фраза «Caddy отвечает `HTTP/2 401`… или `200` при указании
   логина и пароля прокси» — уточнение «HTTP/2» зависит от согласования ALPN
   и не критично для проверки; можно было написать нейтральнее («успешный
   код ответа»), но это не меняет исполнимость команды.
