## Советы (не блокируют)

1. **Тест на инвариант №1 не сверяется с экспортёром напрямую.** Докстрока
   `test_new_card_fields_persist_without_loss` заявляет «читаются из базы ровно
   теми, что печатает markdown-отчёт», но тест проверяет только круговой ход
   через БД. Паритет сейчас держится на ручной сверке ревьюера плюс
   `tests/test_export_markdown.py`. Тест, который рендерит ту же карточку и
   сверяет, что строки из отчёта восстановимы из строки БД, закрыл бы этот
   класс регрессий машинно. Не блокирует: состав и форма полей фактически
   совпадают (проверено построчно, см. «Проверено»).
2. **`default=list` — питонья умолчалка SQLAlchemy, а не DDL DEFAULT.**
   `test_new_columns_default_to_empty_list_on_bare_insert` вставляет строку
   через ORM, то есть проверяет умолчание SQLAlchemy, а не значение колонки в
   схеме. Сырой `INSERT` мимо ORM по-прежнему дал бы NULL. Это ровно то же
   поведение, что у соседних JSON-колонок (`candidate_urls`, `risks`,
   `gov_support`), и задача просила «как у соседних», так что менять нечего —
   но название теста («bare insert») читается шире, чем то, что он покрывает.
3. **Отказ записи на устаревшем файле базы виден только в логе.** Докстрока про
   отсутствие миграций добавлена верно, но следствие стоит держать в голове:
   `persist_run` гасит исключения (`log.warning`), поэтому прогон против
   старого `data/scout.db` без трёх колонок отработает «успешно» и молча ничего
   не запишет. Предусловие 2 подэтапа (коммит `e0c9486`, файл переименован в
   `.bak`) эту дыру уже закрыло для текущего состояния; на будущее — отдельная
   задача, не эта.
4. **`maturity_stage` пишется в БД безусловно, а markdown печатает его только
   при непустом `evidence`** (`markdown.py:79-85`, правка Ф-4). Формально это
   остаток того же класса «в базе увереннее, чем в отчёте». Сейчас он инертен:
   ни один код не читает `solution_cards` для показа (в `web/` из БД рендерится
   только витрина `ShowcaseItem`), и `evidence` в строке лежит рядом, так что
   правило гейта восстановимо. Трогать в Т-5 нельзя — это выход за границы
   задачи; уместно на этапе 3 (РЕШ-40), когда таблица начнёт читаться.
5. **Третий помощник сборки карточки в наборе тестов.** `_card()` в
   `tests/test_persistence.py` соседствует с `_make_card()` в
   `tests/test_export_markdown.py`. Функционального следствия нет, объединение —
   рефакторинг «пока рядом».

### Сверка состава полей с экспортёром (главная проверка задачи)

Пройден `backend/app/export/markdown.py:76-153` поле за полем и сопоставлен с
`_write` (`persistence.py:106-130`):

| Печатается в markdown | Колонка в `solution_cards` | Пишется в `_write` |
|---|---|---|
| `title`, `essence`, `applicability`, `next_step` | есть | да |
| `maturity_stage`, `trl_estimate` (под условием непустого `evidence`) | есть | да (см. совет 4) |
| `developer_org`, `developer_team`, `contact_leads` | есть | да |
| `requirement_checks` | **добавлена** | **да**, `model_dump(mode="json")` |
| `risks`, `gov_support` | есть | да |
| `confidence`, `confidence_note`, `evidence` | есть | да |
| `unsourced_claims` | **добавлена** | **да**, `list(...)` |
| `pdf_urls` | **добавлена** | **да**, `str(url)` |

Полей, которые печатаются в отчёте и не доезжают до базы, после правки не
осталось. Обратный перекос (`candidate_urls` в базе есть, в отчёте не
печатается) существовал и до правки и инвариант не нарушает — база не
«увереннее», а полнее.

**Сериализация.** `RequirementCheck` не имеет алиасов, `model_dump(mode="json")`
даёт ровно `requirement / status / evidence_url / note`, `HttpUrl | None` уходит
строкой либо `None` — тест закрепляет обе ветки, включая `evidence_url: None` у
неподтверждённого пункта. `pdf_urls` и `evidence_url` кладутся через `str()`, а
экспортёр подставляет `HttpUrl` в f-строку, то есть вызывает тот же `__str__` —
нормализация pydantic на обеих сторонах одинаковая, расхождения быть не может.
Порядок элементов сохраняется списком, тест сверяет список целиком, а не
множество.

**Пустой список вместо NULL** — покрыт на обоих путях: карточка без трёх полей
через `persist_run` и строка `SolutionCardRow`, собранная вообще без этих
колонок. Оба дают `[]`.

**Слои.** `_write` остаётся внутри `pipeline/persistence.py`, стадии не
трогались, запись по-прежнему вызывается только оркестратором через переданную
фабрику — правило CLAUDE.md «стадии чистые, работа с БД в оркестраторе» не
нарушено.
