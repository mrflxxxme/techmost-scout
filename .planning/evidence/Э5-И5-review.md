## Число ruff — подтверждено, системная находка

Воспроизвёл лично:
```
$ which -a ruff
/root/.local/bin/ruff
/usr/local/bin/ruff
$ ruff --version
ruff 0.15.8
$ /home/user/techmost-scout/.venv/bin/ruff --version
ruff 0.16.4
$ cd <рабочая копия> && ruff format --check .        # PATH, 0.15.8
173 files already formatted
$ /home/user/techmost-scout/.venv/bin/ruff format --check .   # бинарь проекта, 0.16.4
208 files already formatted
```
Подтверждаю дословно объяснение исполнителя: в среде действительно
установлены два `ruff` разных версий, и голая команда `ruff` в PATH
резолвится в **чужой** (0.15.8), который не форматирует питоновские блоки
в Markdown, — отсюда заниженное число 173 в первом прогоне. Проектный
бинарь `.venv/bin/ruff` (0.16.4) даёт 208, и это число совпадает с
самостоятельным прогоном ревьюера в цикле 1. Оба прогона дают «0
замечаний» — реального дефекта не было, только неверное число охвата.

**Это касается всех задач этапа, не только Э5-И5**: любая проверка,
запущенная командой `ruff …` без явного пути к `.venv/bin/ruff` или без
`python -m ruff`, в этой среде получает версию 0.15.8 и заниженный охват
(в частности, не проверяет Markdown-блоки в `.claude/agents`, `docs/`,
`prompts/`, `CLAUDE.md`, `README.md`). Тем задачам, где заявленное число
`ruff format --check .` не совпадает с ожидаемым (упомянутые оркестратором
210 у параллельной задачи и 207 «до волны 2»), стоит перепроверить тем же
способом — версией из `.venv/bin/`, а не той, что резолвится первой в PATH.
Рекомендую записать это как долг окружения (закреплять команду для всех
задач как `.venv/bin/ruff` или `python -m ruff`), а не разбирать по одной
задаче за раз.
