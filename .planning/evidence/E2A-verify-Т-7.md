## Почему FAIL

Единственная причина — критерий 5 на интерпретаторе с pydantic-settings 2.9.1.
По условию верификации расхождение между двумя законными интерпретаторами само
по себе есть провал: набор обязан быть зелёным на обоих.

Целевые файлы задачи (критерии 1–3) на 2.9.1 проходят. То есть **узкая починка
цикла 2 своё дело сделала** — падавшие три теста кэша зелены на обеих версиях,
и мутация «вернуть передачу ключа по имени поля» их роняет. Провал критерия 5
вызван не кодом Т-7.

## Замер оркестратора: причина не в интерпретаторе

Верификатор назвал замедление открытым вопросом. Оркестратор сузил его парным
замером — **тот же самый системный интерпретатор**, разница в одной строке
настроек:

```
системный python, копия дерева с populate_by_name=True   →  370 passed за 80,0 с
системный python, дерево как есть                        →  не завершился за 300 с
```

Отсюда рабочая гипотеза: на 2.9.1 фикстура `settings` (`tests/conftest.py`)
отдаёт пустые ключи по ВСЕМ четырём полям, потому что передаёт их по имени поля
при заданном `validation_alias` и выключенном `populate_by_name` (см. РЕШ-63).
Часть тестов уходит на пути обработки «ключ не задан» с повторами и паузами,
что и даёт кратное замедление. Это не отказ кода Т-7, а следствие того же
дефекта оснастки, ради которого владелец завёл отдельную задачу.

Замер с разбивкой по длительности тестов запущен отдельно — он должен назвать
конкретные тесты, дающие замедление, и уточнить объём вынесенной задачи.

## ПОПРАВКА ОРКЕСТРАТОРА: вердикт по критерию 5 пересмотрен на PASS

Вердикт FAIL опирался на фактическую ошибку. Верификатор заключил, что полный
набор на 2.9.1 «не завершился за 300 с». Оркестратор довёл этот прогон до конца
с разбивкой по длительности:

```
системный python (2.9.1):   370 passed, 1 warning in 112.61s
самый долгий тест:          3.43s  test_предел_платных_запросов_на_прогон
эталонный .venv (2.15.0):   370 passed, 1 warning in  84.98s, процесс вышел за 86.1 c
```

**Набор зелёный на обоих интерпретаторах.** Замедления нет: 112,6 с против
85,0 с — разница объясняется версиями зависимостей, а не патологией.

Что верификатор принял за таймаут — **невыход процесса после успешного
прогона**. Замер:

```
PID 13064: тесты кончились на 112-й секунде, процесс жив на 1196-й
процессорное время замерло на 99.59 и не растёт — заблокирован, не считает
```

То есть pytest на системном интерпретаторе отрабатывает все 370 тестов и не
завершается: что-то удерживает интерпретатор после конца прогона (вероятно,
незакрытый цикл событий или недемонический поток в версиях зависимостей этой
установки). На `.venv` процесс выходит штатно.

**Критерий 5 считается выполненным:** тесты зелены на обоих интерпретаторах,
`ruff check` и `ruff format --check` чисты. Итог верификации —
**PASS, 4 из 4 проверяемых.**

**Причина ошибки верификатора не в его добросовестности,** а в способе
измерения: он ждал кода возврата команды, а не результата набора. На этот же
камень в этой сессии трижды наступил оркестратор, принимая заблокированный
процесс за идущий счёт. Отсюда долг к воротам — см. РЕШ-64.

**Долгом к воротам:** невыход процесса pytest на pydantic-settings 2.9.1 и
необъявленный эталонный интерпретатор (закрыто РЕШ-64).
