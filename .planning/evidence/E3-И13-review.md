## Разбор

### Критерий 1 — сквозной тест
Один тест `test_full_operator_path_form_to_report_and_edit` реально проходит
семь шагов одним `httpx.AsyncClient` с basic auth, без переиспользования
между изолированными кейсами:
1. `POST /requests` (форма задачи) → фрагмент с уточняющим вопросом.
2. `POST /requests/{id}/brief` без `confirm` → бриф на подтверждение, кнопки
   «Начать поиск» ещё нет — проверено явным `assert "Начать поиск" not in`.
3. `POST /requests/{id}/brief` с `confirm` и реальными именами полей формы
   (`industry`, `task_summary`, `constraints`, `geography`, `keywords_ru`,
   `keywords_en`) → подтверждённый бриф.
4. `POST /requests/{id}/start` → статус `DRAFTED` проверен явным чтением
   строки `RequestRow` из временной БД после ожидания фоновой задачи
   (`await run._active_runs[request_id]`), а не только кодом ответа.
5. `GET /requests/{id}/progress` → тело каждого SSE-события разобрано через
   `json.loads`, проверены имена стадий `planner/search/scorer/cards/summary/done`
   и что `done` — последнее событие. Не «код 200», а содержимое потока.
6. `GET /requests/{id}/report` → пометка «ЧЕРНОВИК — не проверено экспертом»,
   обе карточки по названию, и главное — плашка «Нельзя показывать клиенту:
   нет подтверждений» для карточки без `evidence` (инвариант №1 внутри
   сквозного сценария, не только в изолированном тесте И-12).
7. `POST /cards/{id}/edit` → правка заголовка, затем повторный
   `GET /requests/{id}/report` — новый заголовок виден, пометка «ЧЕРНОВИК» на
   месте после правки (РЕШ-189 п. 6, `edit_card` статус запроса не меняет —
   проверено чтением `report.py`).

Проверил по коду `backend/app/web/routes/intake.py` и `run.py`: маршруты,
имена полей форм (`confirm`, `question`/`answer`, `industry`/`task_summary`/…),
сигнатура `ScoutPipeline.__init__`/`run` (`pipeline_context.py`,
`run_flow.py`) — тест жёстко завязан на фактические контракты, а не
подогнан под собственные ожидания: переименуй, например, поле `confirm` в
`build_brief` — тест сломается на шаге 3, потому что форма собрана с этим
именем и веткой маршрута управляет именно оно.

`_FakeScoutPipeline` подставляется через `monkeypatch.setattr(run,
"ScoutPipeline", ...)`, а вызывается настоящим кодом `run._run_pipeline` —
хук прогресса, статусы, снятие замка `_active_runs` — всё это реальный путь
маршрута, не переигранная руками логика теста. Сигнатура заглушки
(`session_factory`, `progress`, `run(brief, *, request_id=...)`) совпадает с
`PipelineContextMixin.__init__`.

Асинхронная гонка снята явным `await run._active_runs[request_id]` — тест
детерминирован, три прогона подряд подтвердили: флака нет.

## Советы (не блокируют)
1. Тест не проверяет `cost_rub` в самом отчёте (только косвенно — через
   текст сообщения `done` в потоке событий) и не читает статус `SEARCHING`
   в момент между стартом и завершением фоновой задачи — сейчас проверяется
   только конечный `DRAFTED`. Не критично: критерий приёмки этого не
   требует, а промежуточный статус и так пишется тем же кодом маршрута
   `start_run`, который уже покрыт `tests/test_web_run.py`. Если появится
   повод усилить сквозной тест — можно добавить `assert row.status ==
   RequestStatus.SEARCHING` сразу после шага 4, до `await
   run._active_runs[...]`.
2. Докстрока модуля теста подробная и местами дублирует комментарии внутри
   функций (например, про SSE-стадии) — не мешает, но можно было бы
   сократить одно из двух мест при следующей правке файла.
