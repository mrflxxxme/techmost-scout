## Блокирующие

Нет. Ниже — разбор четырёх мест, на которые оркестратор указал отдельно, с
фактическим результатом проверки по коду.

**1. `_pick_top` вызывается ровно один раз — подтверждено по коду.**
`stages.py:426-434`: `select_top` считает `eligible`, один раз вызывает
`_pick_top(eligible, limit=limit)`, передаёт **тот же объект** `picked` в
`log_relevance_calibration` и **его же** возвращает. Второго вызова и второй
копии логики отбора в модуле нет: `_pick_top` встречается ровно дважды —
определение (437) и единственный вызов (429). Колонка «среди отобранных»
считается `_cut_by_relevance(picked, t)` по возвращаемому составу. Расхождение
выдачи и журнала, из-за которого Т-10 подбирал бы порог по несуществующему
составу, невозможно.

**2. Строка калибровки печатается всегда — проверено прогоном, а не чтением.**
Между `_pick_top` и `log.info` нет ни раннего возврата, ни ветвления, ни
исключения. Единственный теоретический риск — падение `_pick_top`; но она
сортирует по `ScoredCandidate.total` (`schemas.py:151-161`), это чистое
свойство из пяти валидированных `int` 0–10, исключений не поднимает.
Фактический вывод на четырёх входах:

```
=== смешанный вход, порог 5 ===
калибровка relevance: кандидатов 16, оценок модели 12, min/медиана/max по оценкам модели 1/3.5/9, порог 5, отсечено 7; отсеклось бы по всему списку при 4: 6, при 5: 7, при 6: 7, при 7: 8; среди отобранных 9 (лимит 12) ниже порога 4: 0, 5: 0, 6: 0, 7: 1; нейтральных оценок 4 (не отсекаются никогда)
=== пустой вход, порог 0 ===
калибровка relevance: кандидатов 0, оценок модели 0, min/медиана/max по оценкам модели нет оценок, порог 0, отсечено 0; ...
=== порог 0, нулевая отсечка ===
калибровка relevance: кандидатов 3, оценок модели 3, min/медиана/max по оценкам модели 7/8/9, порог 0, отсечено 0; ...
=== только нейтральные, порог 6 ===
калибровка relevance: кандидатов 4, оценок модели 0, min/медиана/max по оценкам модели нет оценок, порог 6, отсечено 0; ... нейтральных оценок 4
```

Строка есть в каждом случае: порог 0, нулевая отсечка, пустой вход, полностью
отказавший батч. Плейсхолдеров в шаблоне десять, аргументов десять.

**3. Колонки не путаются — ни для теста, ни для человека.** Элементы первой
колонки несут префикс `при ` (`при 4: 6`), элементы второй — нет (`4: 0`). Ни
один тест не цепляется за подстроку, встречающуюся в обеих: прежние тесты
проверяют `"при 4: 1"`, `"при 6: 0"`; новые — полный прогон вместе с меткой.
Асимметрия защиты остаётся — совет 1.

**4. Структурная пометка — решение по существу верное, дыру не воспроизводит.**
`_has_neutral_score` (`stages.py:347`) — это `isinstance(...) OR notes ==
NEUTRAL_SCORE_NOTE`. Логически это **дизъюнкция**, поэтому множество
распознаваемых как нейтральные только расширяется: запасной путь не может
отнять признак у кандидата, которому его дал тип. Дыра П-4 (дрейф текста у
производителя → нейтральные молча под отсечку) закрыта тестом
`test_neutral_mark_survives_change_of_note_text`.

Коллизия с текстом от модели при запасном пути сохраняется — проверено и
подтверждено: кандидат с `relevance` ниже порога, которому модель дословно
написала в `notes` строку `NEUTRAL_SCORE_NOTE`, отсечку не пройдёт.
**Блокирующим это не является:** это не новый дефект, а единственный механизм,
действовавший до правки; он прошёл ревью цикла 1 и верификацию, и пост-аудит
его не называл. По §5 ни под один пункт не подходит. Цена срабатывания
ограничена одним кандидатом и двумя счётчиками; вероятность — дословное
воспроизведение моделью 46-символьной фразы.

контракт между стадиями не изменён; сериализации `ScoredCandidate` в пайплайне
нет, наружу подкласс не протекает.

**6. Границы цикла соблюдены.** `prompts/scorer.md`, `prompts/CHANGELOG.md`,
