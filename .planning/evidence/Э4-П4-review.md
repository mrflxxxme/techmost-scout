## Проверено по задаче (PLAN.md, «Э4-П4»)

Критерии приёмки — все четыре закрыты тестами, каждый проверен мутацией:

1. `EA0000026963B1` → `EA26963B1`, `RU0002812345C1` → `RU2812345C1`.
   Тест `test_ведущие_нули_снимаются_у_числовой_части` (параметризован) +
   сквозной `test_ссылка_на_документ_строится_по_нормализованному_номеру`
   (через `search()` на respx-фикстуре). Мутация «вернуть `f"{country}{digits}{kind}"`
   без `lstrip`» — оба теста краснеют. Мутация «строить URL из исходного `number`
   в обход `_normalize_document_number`» — краснеет сквозной тест.
2. `RU2812345C1` (без ведущих нулей) не меняется —
   `test_номер_без_ведущих_нулей_не_меняется`, отдельный от п.1 случай.
3. Нераспознанный формат отдаётся как есть — `test_нераспознанный_формат_номера_отдаётся_как_есть`,
   4 варианта параметризацией (`""`, `"не-номер"`, `"2020130881"`, `"EA0000026963"`
   — последний специально без кода вида документа, самый близкий к боевому
   случаю промах мимо регэкспа). Мутация «в ветке `if not match` вернуть `''`
   вместо `number`» — 3 из 4 параметров краснеют (пустая строка совпадает
   сама с собой, это ожидаемо и не маскирует дефект — остальные три ловят).
4. Сети в тестах нет — `respx.mock` на все HTTP-вызовы адаптера, прямой вызов
   `_normalize_document_number` в модульных тестах сети не требует.

## Точечная проверка регэкспа (сверх формальных критериев)

Ручной прогон `_normalize_document_number` на пограничных значениях
(в своей копии, к тестовому набору не относится, просто аудит формулы):

```
RU2000123C1     -> RU2000123C1     # внутренний ноль не в ведущей позиции — не тронут
RU0000000000A1  -> RU0A1           # числовая часть из одних нулей — защитный `or '0'`
                                    #  не даёт получить пустую числовую часть (не 404,
                                    #  а просто маловероятный кейс, живых патентов
                                    #  с нулевым номером не бывает)
WO2020123456A1  -> WO2020123456A1  # обычный случай, без нулей — не тронут
RU2812345C1U1   -> RU2812345C1U1   # буквенная серия в конце kind — не тронут
```

Значащие нули внутри числовой части не съедаются (стрипается только
`lstrip('0')`, то есть исключительно ведущие). Кейс «числовая часть из одних
нулей» не входит ни в один из четырёх критериев приёмки и в реальных данных
Роспатента не встречается — блокирующим не считаю, но эту защиту стоило бы
одной строкой упомянуть в докстроке (см. советы).

## `raw_id` и `dedup_key`

Не тронуты: `raw_id=number` в `_to_candidate` использует исходный, не
нормализованный `number` (строка 275 после патча) — нормализации подвергается
только аргумент `DOCUMENT_URL.format(...)`. Дедупликация между источниками
по этому полю не пострадает. Исполнитель явно зафиксировал это решение в
`notes` handoff — совпадает с тем, что видно в diff.

## Язык и стиль

Докстрока `_normalize_document_number` и комментарий к `_PUBLICATION_NUMBER`
по-русски, объясняют ловушку внешнего API (Google Patents отвечает 404 на
номер с нулями) и то, почему не нормализуется `raw_id` — не пересказ кода.
Тесты используют кириллические имена функций, единообразно с остальным
файлом.

## Советы (не блокируют)

1. В докстроке `_normalize_document_number` не помешала бы фраза про
   `digits.lstrip('0') or '0'` — что это защита от пустой числовой части на
   гипотетическом номере из одних нулей, а не часть основной логики
   критерия 3. Без неё следующий читающий может решить, что это лишняя
   строчка, и убрать её.
2. `patents_view.py` (заготовка Э2-6, не реализована) в докстроке описывает
   такую же схему сборки URL Google Patents без нормализации номера — когда
   адаптер будет реализовываться, стоит унаследовать `_normalize_document_number`
   или его аналог. Вне границ этой задачи, отдельная будущая работа.
