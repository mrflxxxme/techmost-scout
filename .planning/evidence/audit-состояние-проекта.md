# Аудит состояния проекта · 23 августа 2026

Внеплановый разбор по просьбе владельца, после подписи ворот Э2-Е и до начала
этапа 3. Пять линз: целостность, связанность, консистентность, соответствие
требованиям, оптимальность. Проводил оркестратор; каждое утверждение здесь
получено командой или запросом к базе, без «выглядит нормально».

**Правки по итогам аудита не вносились** — граница задачи: владелец просил
разбор, а не работу (CLAUDE.md, «не расширяй скоуп по своей инициативе»).
Предложения собраны в конце в порядке, в котором их стоит закрывать.

Каркас держится: слои не протекают, инварианты соблюдены, деньги под

## Линза 1. Целостность

**Что проверено.** Схема базы против кода; публичные функции без вызова;
таблицы против записи; журнал стадий против фактического прогона.

| Проверка | Результат |
|---|---|
| Прямой вызов модели мимо `LLMRouter` | нет |
| Работа с БД внутри стадий пайплайна | нет |
| Функции модульного уровня без вызова в продукте | 7, из них 5 — обработчики маршрутов (их зовёт FastAPI) |
| Ключи в коде, тестах, истории | нет; `.env`, `.env.*` в `.gitignore`; база и `out/` не отслеживаются |
| Нумерация решений | 1–169 без дыр и дублей (`РЕШ-59 (продолжение)` — не дубль) |

**Ц-1. Две функции измерителя без потребителя в продукте.**
`metrics.max_relevance` и `metrics.silent_sources_share` вызываются только из
тестов и доказательств. Это не мусор — их писали под воротные измерения, — но
в коде продукта они не участвуют, и это стоит либо назвать в докстроке, либо
перенести к доказательствам.

**Ц-2. Пустые таблицы.** `briefs` — 0 строк (РЕШ-156, знаем), `verdicts` — 0
строк (этап 4, обработчик поднимает `NotImplementedError` и это записано),
`showcase_items` — 0 строк при живом адаптере, CLI-команде и маршруте.
`pipeline_logs.tokens_in/tokens_out` всегда нули — так задумано (`CostTracker`
копит рубли, не токены; сказано в `cli.py:118`), но две колонки существуют
только чтобы хранить ноль.

**Ц-3. Веб создаёт строки, которые никуда не ведут.** `POST /requests`
сохраняет `RequestRow(status="intake")` и показывает заглушку этапа 3. Главная
страница выводит последние пять запросов — то есть каждое нажатие на форму
оставляет след, который никогда не станет прогоном. До этапа 3 безвредно,
на этапе 3 это первое, что увидит оператор.

## Линза 2. Связанность

**Что проверено.** Границы слоёв, проводка промптов, маршруты стадий,
согласие между `SPEC`, `DECISIONS`, `PLAN`, `STATE` и кодом.

**Держится:**

* восемь промптов — метки `{{...}}` и `EXPECTED_PLACEHOLDERS` теста сходятся
  один в один (инвариант 4);
* содержательное — в системном сообщении, данные — в пользовательском
  (проверено на `scorer`: `load_prompt("scorer")` в `system`, кандидаты в
  `user`), кэш префикса сработал на 45 вызовах из 46;
* активные параметры прогона печатаются до первой платной стадии и включают
  оба порога, маршруты, резервный порядок и имена моделей.

**С-1 (существенно). Инвариант 6 разошёлся с кодом.** Способ проверки записан
как «`grep -rn "httpx" backend/app` — только в `llm/`, `search/` и
оркестраторе». Фактически `httpx` создаётся ещё и в `cli.py:243` (доктор
строит общий клиент для проверки источников) и в `pipeline_context.py` /
`pipeline_search.py` — файла «оркестратор» после дробления З-10 не существует
вовсе. Проверка в нынешнем виде даёт ложное срабатывание на здоровом коде.
Инвариант, срабатывающий ложно, перестают проверять — а этот стережёт учёт
стоимости и подмену в тестах.

**С-2. Рабочий порог отсечки живёт вне кода.** `Settings.relevance_min` по
умолчанию **0** — отсечка выключена. Рабочая тройка (РЕШ-162) есть только в
`docs/remote-setup.md` и в окружении прогона. При деплое (Э5-1) забытая
переменная означает тихо выключенную отсечку: отчёт соберётся, карточки
поедут из кандидатов с релевантностью 0–2. Смягчает то, что значение
печатается в строке параметров, — но заметить его должен человек.

**П-1 (существенно). Правило 500 строк проверяется только там, где кто-то
написал тест.** Машинные стражи есть у `backend/app/pipeline/` (задачи

|---|---|
| `backend/app/cli.py` | **683** |
| `backend/app/search/openalex.py` | **593** |
| `backend/app/search/yandex_search.py` | **544** |

Три файла продукта сверх лимита, и ни один тест их не считает. Это тот же

**П-2. Про тесты правило не сказано ничего.** Десять тестовых файлов длиннее
500 строк (максимум — `test_stages.py`, 1653). Либо лимит на них
распространяется, либо в CLAUDE.md пишется, что правило про код продукта.
Сейчас формулировка «файлы до 500 строк» читается как «нарушено десять раз».

**П-3. Поручение владельца выпало из видимого состояния.** РЕШ-68 (16 августа,
дословно: «найти альтернативы киберленинке и поднять доступ к fips.
Русскоязычная база обязательно должна быть!») содержит три части. Часть про

к воротам, а работа» — и в результате не видно нигде.

## Линза 4. Соответствие требованиям (SPEC §2а)

**Т-1 (критично). SPEC противоречит коду по OpenAlex.** Спецификация объявлена
единственным источником требований (РЕШ-11) и говорит в трёх местах:

* §2 п. 3 — «используется **только для обогащения по DOI**, никогда для
  поиска»;
* §2а FR-5 — «OpenAlex — только обогащение по DOI»;
* Э2-1, раздел «Не делать» — «Не вызывать search-эндпоинт OpenAlex ни при
  каких условиях».

Код ходит в платный поиск OpenAlex: воротный прогон 23 августа сделал
2 поисковых запроса ($0.002, оба вернули 429). Это не самовольство — РЕШ-72
прямо отменил прежний запрет и завёл счётчик с суточной нормой. Но SPEC не
обновлён, и любая роль, читающая его как истину, обязана признать код
нарушением — либо «починить» код обратно. Расхождение живёт с 17 августа.

**Т-2 (критично). Метрика покрытия недостижима по построению.** Вспомогательная
метрика SPEC: «покрытие типов источников на запрос ≥ 4 (публикации, патенты,
гранты, организации)». В коде `SourceType` объявляет `GRANT` и `ORG`, но
**ни один адаптер их не выставляет**: гранты по замыслу приходят как `web` с
грантовой формулировкой (`prompts/planner.md`, правило 9). Значит четвёрка
из формулировки метрики не набирается никогда.

Факт последнего прогона: `publication` 165, `web` 113, `contest` 96,
`patent` 48 — покрытие **3** (конкурсы в метрику не входят, РЕШ-85).
Либо метрика переписывается под фактические типы, либо стадия размечает
грантовые и организационные кандидаты отдельно.

**Т-3. Что из функциональных требований работает сегодня.** Пайплайн (FR-1,
FR-3 частично, FR-5, FR-7…FR-12) — да, проверено живым прогоном: 8 карточек,
каждое утверждение со ссылкой, «Сверка с требованиями задачи» и «Ограничения
этого поиска» заполнены, пометка ЧЕРНОВИК на месте (инвариант 2). Экранные
требования (FR-2, FR-13…FR-16) — заготовки с описанными контрактами, это
этап 3–4 и так и запланировано. FR-17 «сохраняются брифы и отчёты» —
не выполнено: `briefs` пуст, отчёт живёт файлом; закрывается РЕШ-146 в этапе 3.

**Т-4. Источники: три из восьми дали результат.** Последний воротный прогон:

| Источник | Итог |
|---|---|
| crossref | 40 кандидатов |
| yandex (ru + com) | 67 кандидатов |
| rospatent | 1 кандидат |
| cyberleninka | 0, без ошибки |
| showcase | 0 (таблица пуста) |
| arxiv | **403 Forbidden**, 0 |
| openalex | 429 (платный поиск), 0 |
| semanticscholar | 429 (нет ключа, общий пул), 0 |

Инвариант 5 соблюдён — отчёт честно пишет «Не ответили источники: arxiv,
openalex, semanticscholar». Но **403 у arXiv не записан нигде**: ни в
решениях, ни в журнале, ни в долгах, а повторяется на всех трёх воротных
прогонах подряд (Э2-Д ×2, Э2-Е). arXiv — один из четырёх бесплатных
источников, на которых по SPEC стоит поиск.

КиберЛенинка на этой задаче даёт ноль трижды, но источник не мёртв: на других
задачах он приносил кандидатов (РЕШ-140: статью КиберЛенинки принесла
конкурсная формулировка). Это не «сломан», это «не покрывает свиноводство».

## Линза 5. Оптимальность и лишние усложнения

**О-1. Двухпровайдерная экономия сейчас не работает.** Замысел: массовые
стадии — на бесплатный ГигаЧат, качественные — на дешёвый DeepSeek. Факт
последнего прогона по журналу стадий:

```
search (extractor)   deepseek   3,344 ₽
scorer               deepseek   2,644 ₽
cards                deepseek   2,618 ₽
contest_cards        deepseek   1,778 ₽
planner              deepseek   0,433 ₽
intake               deepseek   0,425 ₽
summary              deepseek   0,036 ₽
```

Все 46 вызовов ушли на платного провайдера, включая `intake` и `extractor`,
ради которых бесплатный и заводился: ГигаЧат недоступен из среды (авторизация
на порту 9443, прокси умеет только 443). Цена всё равно 1 % от потолка, так
что денежной проблемы нет — но роутер, маршруты стадий, резервный порядок и
три адаптера моделей сейчас обслуживают путь, которым никто не ходит.
Развилка для владельца: вернуть ГигаЧат (это вопрос среды, не кода) или
признать DeepSeek основным и упростить конфигурацию.

**О-2. Склейка дублей работает вхолостую.** `diversity.py` (231 строка) держит
`merge_duplicate_groups` с порогом 0.65, при котором, по измерению РЕШ-152,
не склеивается ничего: максимум сходства настоящих дублей — 0.571. Машинерия
исправна и засторожена тестами, пользы не даёт до семантического признака.

**О-3. Витрина партнёров — четыре места кода при нуле данных.** Адаптер
(254 строки), команда `scout showcase`, таблица, маршрут и шаблон. FR-6
требует витрину, поэтому это не лишнее — но пока в таблице ноль строк,
источник участвует в каждом прогоне и всегда отдаёт пусто.

**О-4. `google_search.py` — 301 строка кода, который не может исполниться.**
Google закрыл Custom Search JSON API для новых проектов (РЕШ-21), адаптер в
сборку не попадает («выключен: нет настроек google_api_key, google_cse_id»).
Решение сохранить его записано; стоит назвать срок пересмотра, иначе он
останется навсегда.

**О-5. Мелочи.** `demo_mode_default` не читается нигде (ждёт Э4-3);
`google_lang_restrict` — единственное обращение; две колонки токенов всегда
нулевые.

**О-6. Соотношение тестов к коду 1,7 : 1** (17 880 строк против 10 624).
Само по себе это не порок — цена дисциплины «новое поведение без теста не
проходит». Но 749 тестов идут 43 секунды, и это уже заметно в цикле; если
рост продолжится теми же темпами, к концу этапа 3 набор перевалит за минуту,
и его начнут гонять реже. Стоит хотя бы измерять.

## Что в хорошем состоянии

Перечисляю отдельно, потому что аудит, который называет только плохое, врёт
не меньше того, который называет только хорошее.

* **Слои не протекают.** Ни одного вызова модели мимо роутера, ни одной
  работы с БД внутри стадий. Разделение «чистые стадии / оркестратор» пережило
  дробление обоих больших файлов.
* **Три инварианта подтверждены на живом материале, а не по описанию:** каждый
  факт в отчёте со ссылкой (1), пометка ЧЕРНОВИК на месте (2), отказ источника
  виден в отчёте и не роняет запрос (5).
* **Деньги под контролем.** 11,28 ₽ за прогон при потолке 1000 ₽; стоп-кран
  печатается и не отключался; расход назван после каждого запуска, включая
  испорченный.
* **Записи связны.** 169 решений без дыр, каждое с причиной; ворота трёх
  подэтапов подписаны с доказательствами; журнал ведёт уроки, а не хронику.

## Поправка от 23 августа (вечер), найдена при планировании Э2-Ж

Пункт **П-3** сформулирован сильнее фактов: часть поручения РЕШ-68 про
альтернативы КиберЛенинке **выполнена** — задача Т-16 переписала адаптер с
мёртвого OAI на её собственный `/api/search` (условия РЕШ-70 соблюдены, это
видно в докстроке `backend/app/search/cyberleninka.py`). Невыполненной
остаётся часть про ФИПС (отложена наблюдением к РЕШ-70) — и именно ноль
кандидатов на живом прогоне при живом API создал впечатление «не сделано».

Причина нуля установлена контрольными вызовами: формулировки модели слишком
длинные для полнотекстового поиска КиберЛенинки (8 слов → `found=0`,
«супоросность свиноматок УЗИ» → `found=21`, контроль «гидроочистка дизельного
топлива» → `found=720`). Лечится в З-2 плана Э2-Ж. Урок для аудитора: «нигде
не упоминается» проверяется грепом по всем написаниям и по коду, а не только
по журналу решений.
