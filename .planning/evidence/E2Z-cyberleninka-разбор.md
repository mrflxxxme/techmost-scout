# Д-2 · Разбор «21 кандидат КиберЛенинки без карточек» (прогон 1, Э2-Ж)

База: коммит `48144af` (HEAD ветки волны Э2-З после подписи Э2-Ж), рабочая
копия `agent-a27b984b8f4c506fb`, ветка `worktree-agent-a27b984b8f4c506fb`.

Источники фактов: `out/E2J-gate-run-1.log` (целевой прогон, свиноводство,
греп по `cyberleninka`), `out/report-20260823-232350.md` (итоговый отчёт
того же прогона), `.planning/gates/Э2-Ж.md` («Долги, добавленные аудитом» и
«Инцидент прогонов»), `backend/app/search/cyberleninka.py` (машинерия
укорачивания, из которой выводится состав короткой формы), `backend/app/
config.py` (`max_candidates_per_query`), `backend/app/pipeline/scoring.py`
(что именно логируется на стадии скоринга).

## Граница задачи: почему разбор не по БД

`data/scout.db` данных прогона 1 не содержит. Запись прогона в БД упала на
`pipeline_logs.tokens_in NOT NULL` (живая база несла старую схему), и вся
транзакция откатилась целиком — накопление этого прогона потеряно, отчёт и
лог целы (`.planning/gates/Э2-Ж.md`, раздел «Инцидент прогонов»).
Починка ALTER-ом случилась уже после прогона 1, а сам прогон не повторялся:
критерии ворот были доказуемы отчётом и логом, повтор пробил бы бюджет.

Из этого следует прямое ограничение разбора: **ничего на уровне отдельного
кандидата** (заголовок, URL, конкретная оценка `relevance` модели) для этих
21 записей КиберЛенинки восстановить нельзя — ни из БД (её нет), ни из лога
(стадия скоринга логирует только агрегаты, см. ниже). Разбор ниже честно
делит выводы на **доказанное по логу и коду** и **гипотезу, для проверки
которой нужен следующий прогон**.

## Шаг 1 — сколько запросов ушло в КиберЛенинку и что вернулось

Грепом по `out/E2J-gate-run-1.log`:

```
cyberleninka: «нейросетевой анализ ультразвуковых изображений свиноматок»
  → found=0; повтор укороченной «нейросетевой анализ ультразвуковых изображений»
  → found=1000
cyberleninka: «deep learning sow ultrasound non-pregnancy detection»
  → found=0; повтор укороченной «deep learning sow ultrasound» → found=1
...
[search] Найдено кандидатов — arxiv: 0, crossref: 40, cyberleninka: 21,
rospatent: 1, showcase: 0, yandex-com: 16, yandex-ru: 78
```

Оба лога печатаются уже машинерией укорачивания З-2 (обе строки — это
`log.info` из `CyberLeninkaAdapter.search`, показывающий обе формы и оба
`found`): **обе формулировки этого прогона сами по себе дали `found=0`** —
укорачивание сработало по назначению, вопрос не «почему укорачивание не
сработало», а «почему укороченная форма всё равно не довела ни одного
кандидата до карточки».

`pipeline_search.py:149` маршрутизирует запросы по `source_type`, не по
`lang` (проверено чтением), а `CyberLeninkaAdapter.source_types =
(SourceType.PUBLICATION,)` без фильтра языка (в отличие от `arxiv`, который
русский запрос вообще пропускает) — поэтому источник получил **обе**
формулировки плана, русскую и английскую, а не одну.

Итог по числам: `max_candidates_per_query = 20` (`config.py:103`) режет
`found=1000` до 20 кандидатов; `found=1` даёт 1 кандидата без обрезки.
`20 + 1 = 21` — ровно то число, что попало в `[search] Найдено кандидатов`.
Совпадение точное, не оценочное.

## Шаг 2 — что такое короткая форма по факту, а не по намерению

`_shorten_query` (`cyberleninka.py`) берёт первые `SHORT_QUERY_WORDS = 4`
содержательных слова формулировки, в порядке исходного текста, без модели.
Применяя эту же детерминированную функцию к обеим исходным формулировкам
прогона:

* RU: «нейросетевой анализ ультразвуковых изображений **свиноматок**»
  (5 содержательных слов, стоп-слов нет) → первые 4 = «нейросетевой анализ
  ультразвуковых изображений». **Слово «свиноматок» — единственный
  видоспецифичный термин формулировки — обрезано укорачиванием.** Оставшаяся
  фраза («нейросетевой анализ ультразвуковых изображений») — это общая
  формулировка для любой предметной области, где применяется анализ УЗИ
  нейросетью (медицина человека, ветеринария любых видов, техническая
  дефектоскопия и т. п.), а не именно для свиноводства.
* EN: «deep learning **sow** ultrasound non-pregnancy detection» (6
  содержательных слов) → первые 4 = «deep learning sow ultrasound».
  Видоспецифичное слово («sow») в этой форме **сохранено**, но задача
  диагностики («non-pregnancy detection») обрезана — и главное, КиберЛенинка
  преимущественно русскоязычный репозиторий: запрос на английском языке в
  ней структурно ищет меньше, чем тот же запрос на русском.

Это объясняет форму цифр, а не только их наличие: `found=1000` на широкой
обезличенной русской формулировке — ожидаемо (общая тема встречается
многократно шире, чем узкая «свиноматки»); `found=1` на английской —
ожидаемо для преимущественно русскоязычного индекса. Оба наблюдения выведены
из кода адаптера и текста формулировок в логе, без обращения к БД —
**доказано**.

## Шаг 3 — куда делись эти 21 кандидат дальше по конвейеру

Дальше по логу того же прогона:

```
[dedup] дедупликация убрала 2 дублей из 156 → После склейки дублей осталось 154
[scorer] калибровка relevance: кандидатов 421, оценок модели 421,
  min/медиана/max по оценкам модели 0/1/7, порог 3, отсечено 402
[scorer] Отобрано вариантов для карточек: 5
```

Итоговый отчёт (`out/report-20260823-232350.md`): 5 карточек основной секции
+ 3 конкурсных, источники всех восьми карточек — `pure.jbnu.ac.kr`,
`pmc.ncbi.nlm.nih.gov` (дважды), `doi.org/10.3390/...`, `researchgate.net`,
`cm.asiae.co.kr`, `pt.2035.university`, `kaiksin.ru`, `pig333.ru`. Ни один
URL `cyberleninka.ru` в отчёте не встречается (проверено грепом по всему
файлу). **Факт «0 из 21 дошло до карточки» доказан текстом отчёта**, не
предположением.

Дальше — граница доказуемости. `калибровка relevance: кандидатов 421` — это
**не** 21 кандидат КиберЛенинки этого прогона, а весь пул request'а после
накопления по нормализованному тексту (третье поколение, тот же текст задачи
шёл в Э2-Д и Э2-Е — `.planning/gates/Э2-Ж.md`, шапка прогона 1). Лог печатает
только агрегатную статистику по всему пулу (`min/медиана/max`, число
отсечённых), а не построчную оценку по кандидату и источнику: прочитан весь
`backend/app/pipeline/scoring.py` — единственные `log.info`/`log.debug` в
файле про отдельного кандидата — это строка про нейтральную оценку при
пропуске батча (никакого лога вида «кандидат X от провайдера Y получил
оценку Z» в коде нет ни на одном уровне). Даже если бы прогон записался в
БД, разбор по логу без БД был бы невозможен — узнать разбивку `421` по
источникам и по кандидатам можно **только** запросом к `candidates.score`
(колонка есть, `models.py:129`), а не из журнала.

## Вывод

**Доказано** (лог + код, без БД):

1. 21 кандидат КиберЛенинки этого прогона — это `20` (укороченная русская
   форма, срезана до лимита `max_candidates_per_query=20`) `+ 1` (укороченная
   английская форма) — точное совпадение с числом в логе.
2. Укорачивание в обоих случаях сработало по коду ровно как задумано (один
   повтор, found=0 → repeat), но укороченная русская форма потеряла
   единственное видоспецифичное слово «свиноматок» — механическое следствие
   лимита в 4 слова на формулировке из 5 содержательных слов, а не сбой кода.
   Английская форма запрашивала преимущественно русскоязычный источник не на
   его основном языке.
3. Ни один из 21 кандидатов КиберЛенинки не вошёл ни в одну из 8 карточек
   итогового отчёта (5 основных + 3 конкурсных) — по прямому сравнению
   источников отчёта со списком URL.

**Не доказано без следующего прогона** (граница честно называется, а не
замалчивается): было ли отсеивание кандидатов КиберЛенинки скорингом
результатом действительно низкой релевантности (правдоподобная гипотеза —
разбавленная общая формулировка на 20 кандидатах, языковой промах на 1)
или чем-то ещё на пути дедупликации/группировки — по доступным артефактам
(лог агрегирует, БД для этого прогона не существует) заголовки, `url` и
персональная оценка `relevance` каждого из 21 кандидата недоступны.

## Что нужно от следующего прогона, чтобы закрыть вопрос

1. Прогон обязан **успешно записаться в БД** (схема уже поправлена ALTER-ом
   после инцидента Э2-Ж — риск исчерпан, но стоит подтвердить перед разбором).
2. После прогона — прямой запрос к живой базе (только чтение,
   `?mode=ro`, по образцу `E2J-rospatent-разбор.md`):
   `select title, url, score from candidates where request_id = <id> and
   provider = 'cyberleninka' order by json_extract(score, '$.relevance') desc;`
   — даст точную оценку каждого из кандидатов КиберЛенинки и подтвердит или
   опровергнёт гипотезу шага 2 численно.
3. Если гипотеза подтвердится (разбавление общей формулировкой = низкая
   релевантность у большинства из 20), кандидат следующей волны — понизить
   `SHORT_QUERY_WORDS` для случаев, где укорачивание срезает единственное
   видоспецифичное слово, либо не резать по фиксированному числу слов, а
   сохранять последнее существительное формулировки отдельно от остальных.
   Это уже правка эвристики укорачивания, а не разбора, и она за границей
   задачи Д-2 (только чтение + доказательство).

## Наблюдение в ворота волны

Занесено как наблюдение (не критерий, доказательства для критерия
недостаточно без следующего прогона): 21 кандидат КиберЛенинки прогона 1
Э2-Ж не дал ни одной карточки; правдоподобная, но не подтверждённая числами
причина — потеря видоспецифичного слова при укорачивании русской формы и
языковой промах английской формы на преимущественно русскоязычном
источнике. Подтверждение — прямым запросом к БД следующего успешно
записавшегося прогона.
