## Находки

Блокирующих нет. Четыре находки уровня «совет», но три из них **поправляют
утверждения ревью**, а не добавляют пожеланий.

### Н-1 · Паритет «поле карточки → колонка БД» не защищён ни одной машинной проверкой

**В чём дефект.** Ничто в наборе тестов не связывает состав полей
`schemas.SolutionCard` с составом колонок `models.SolutionCard`. Поле можно
добавить в карточку, напечатать в клиентском отчёте и не довезти до базы —
гейты этого не увидят. Это ровно тот механизм, которым три поля прошли фазу
Э1-2-Ф и породили Т-5.

**Чем доказано.** Добавлено `funding_note` в `schemas.SolutionCard` и его печать
в `markdown.py`, `models.py` и `_write` не тронуты. Полный набор на копии:

```
базовая линия копии   5 failed, 197 passed, 1 warning in 61.89s
после мутации M9      5 failed, 197 passed, 1 warning in 63.67s
```

Изменений нет вообще. Пять падений — `tests/test_team_docs.py`, следствие
исключения `.planning` и `.omc` при копировании дерева; в рабочей копии тот же
файл даёт 35 passed. Новое поле карточки, доехавшее до клиентского отчёта и не
доехавшее до базы, **не роняет ни одного теста**.

**Почему набор зелёный без замка.** `tests/test_export_markdown.py` проверяет
только печать; `tests/test_persistence.py` — только поля, перечисленные в нём
поимённо. `grep -n "model_fields|__table__|columns\.keys|inspect\(" tests/` —
**ни одного совпадения** во всём каталоге тестов.

**Как выглядел бы замок.** Две строки в `tests/test_persistence.py` — файле,
который Т-5 и так правит:

```python
assert set(SolutionCard.model_fields) <= set(SolutionCardRow.__table__.columns.keys())
```

Сегодня зелёный: 18 полей карточки, 22 колонки, разность пуста. Второй строкой
закрывается случай «колонка есть, а `_write` её не пишет» — разбором AST
установлено, что `SolutionCardRow(...)` получает 20 kwargs (18 полей +
`request_id` + `position`), и `model_fields - kwargs` пусто.

**Почему это пропустили ревью и верификация.** Ревью назвало это советом 1, но
сформулировало сослагательно и тут же смягчило: «не блокирует: состав и форма
полей фактически совпадают». Верификация закрыла инвариант №1 **ручной
сверкой** `export/markdown.py:100–152` с `persistence.py:126–128`, записав его
как «подтверждён». Это урок Э1-2 в чистом виде: способ проверки инварианта сам
подлежит сомнению. Ручная сверка верна на сегодня, ничего не измеряет завтра и
молча устаревает — а «завтра» здесь уже наступало, и его следствием стала эта
самая задача.

**Класс находки.** По §5 — совет, не блокирующее: три пункта «Что делать» Т-5
выполнены, оба критерия приёмки взяты. Но растворять её в списке советов
нельзя: это единственная находка аудита с ценностью на длинной дистанции.
Рекомендуется отдельная задача.

### Н-2 · Совет 2 ревью опирается на неверную посылку — схема держит инвариант жёстче

**Что утверждало ревью.** «`default=list` — питонья умолчалка SQLAlchemy, а не
DDL DEFAULT. Сырой `INSERT` мимо ORM по-прежнему дал бы NULL». Первая половина
верна, вывод — нет.

**Фактический DDL:**

```
CREATE TABLE solution_cards (
        ...
        candidate_urls JSON NOT NULL,
        requirement_checks JSON NOT NULL,
        unsourced_claims JSON NOT NULL,
        pdf_urls JSON NOT NULL,
        editor_overrides JSON NOT NULL,
        PRIMARY KEY (id),
        FOREIGN KEY(request_id) REFERENCES requests (id)
)
```

`PRAGMA table_info`: у всех трёх новых колонок `notnull=1, default=None` — ровно
как у соседних `risks` и `candidate_urls`.

**Сырой `INSERT` мимо ORM без трёх новых колонок:**

```
IntegrityError: NOT NULL constraint failed: solution_cards.requirement_checks
```

**Что это значит.** DDL DEFAULT действительно нет — ревьюер прав. Но
`Mapped[list]` без `| None` даёт `NOT NULL`, поэтому сырой `INSERT` не кладёт
NULL, а **падает**. Инвариант «пустой список, а не NULL» гарантирован схемой, а
не только ORM. Правки не требуется — наоборот, снимается сомнение ревью.

**Почему пропустили.** Ревьюер рассуждал о семантике `default=list` по памяти и
не посмотрел на сгенерированный DDL. Верификатор читал значения сырым SQL, но
только у строк, **уже вставленных через ORM**, — он проверял содержимое, а не
ограничения схемы.

### Н-3 · Совет 4 ревью недосчитал одно поле — и именно то, которое `INVARIANTS.md` называет явно

Гейт `markdown.py:81-85` прячет за `if card.evidence` **два** поля сразу:

```python
if card.evidence:
    maturity = MATURITY_RU.get(card.maturity_stage, card.maturity_stage.value)
    trl = f" (TRL ≈ {card.trl_estimate})" if card.trl_estimate else ""
    lines.append(f"**Стадия зрелости:** {maturity}{trl}")
```

`INVARIANTS.md`, пункт 1, колонка «Как проверять», дословно: «карточка с пустым
`evidence` не печатает **ни стадии зрелости, ни TRL**». Оба поля названы
поимённо. `_write` пишет безусловно оба (`persistence.py:113-114`). Ревью
назвало только `maturity_stage`; `trl_estimate` не упомянут ни разу.

Обе посылки ревью подтверждены независимо. *Инертен* — да: `SolutionCardRow`
встречается только в `pipeline/persistence.py` и в объявлении модели; ни `web/`,
ни `cli.py` карточки из БД не читают. *Вне границ* — да, но точнее: вне границ
**текста задачи**, а не **списка файлов** — правка легла бы в `persistence.py`.
В задачу этапа 3 (РЕШ-40) надо записать **два** поля, иначе остаток закроют
наполовину.

**Почему пропустили.** Ревьюер заметил условие в таблице, но при разборе
остатка сослался только на первое поле. Верификатор сосредоточился на трёх
**новых** полях — остаток по старым в его критерии приёмки не входил.

### Н-4 · Совет 3 ревью недооценил цену отказа: против устаревшей базы теряется весь прогон

**Что утверждало ревью.** «Прогон против старого `data/scout.db` без трёх
колонок отработает „успешно" и молча ничего не запишет».

**Чем замерено.** База собрана `create_all`, три новые колонки удалены
`ALTER TABLE ... DROP COLUMN` (sqlite 3.49.1), выполнен `persist_run` новым
кодом с полностью заполненной карточкой:

```
LOG WARNING app.pipeline.persistence: запись прогона в БД не удалась — отчёт сохранён без неё
  exc_info: sqlite3.OperationalError: table solution_cards has no column named requirement_checks
persist_run returned: None (исключение наружу не вышло)
rows in requests:        0
rows in solution_cards:  0
```

**Что это значит.** `_write` падает на вставке карточки; фабрика сессий
откатывает транзакцию **целиком** (`session_scope`: `except Exception: await
session.rollback(); raise`), поэтому пропадает и уже вставленная строка
`requests`, и журнал стадий. Не «три поля пустые» и не «карточка не
записалась» — **прогона в базе нет вовсе**. Для системы, где `models.py:3-6`
называет накопленные запросы и вердикты «будущим главным активом компании», это
дороже, чем прозвучало в ревью.

**Смягчение, названное честно.** `cli.py:30-31` конфигурирует логирование
уровнем INFO, так что `log.warning` с трейсбеком в терминале **виден** —
«молча» в буквальном смысле неверно. Но код возврата и текст успешного
завершения прогона не меняются.

**Границы.** Т-5 требовала по этому поводу ровно одну строку в докстроке
`persistence.py` — она на месте и точна. Задача выполнена. Замок (громкая
сверка `Base.metadata` с `PRAGMA table_info` при `init_db`) — отдельная задача.
Предусловие 2 подэтапа закрыло дыру для текущей машины, но не для
восстановления из резервной копии и не для второй машины.

**Почему пропустили.** Ревьюер вывел следствие рассуждением из кода
`persist_run` и не выполнил прогон против устаревшей схемы. Верификатор работал
строго по критериям приёмки, а сценария «база старая» ни в одном критерии нет.
