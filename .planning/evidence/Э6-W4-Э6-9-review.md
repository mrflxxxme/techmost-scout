## Блокирующие

1. **[дефект логики, соседи edge-Caddy] `merge_sites` / `top_level_blocks` не видит адресов,
   перенесённых на следующую строку после запятой.** `scripts/deploy_server.py:235-254`: адреса
   берутся только из строки, которая кончается на `{`. Воспроизведено (probe на копии скрипта,
   хэш и хосты фиктивные):
   вход `neighbor.example,\nscout.x.example {\n    respond ok\n}\n` при первом прогоне (прежний
   немаркированный блок) даёт `addresses == ["scout.x.example"]`, блок считается «только нашим» и
   принимается в маркеры, а строка `neighbor.example,` остаётся висеть над областью Скаута. После
   пропуска комментариев Caddy склеивает её с первым блоком области: `neighbor.example,
   scout.x.example { basic_auth … reverse_proxy techmost-scout:8000 }`. Сосед молча уходит на
   Скаут под пароль. `caddy validate` проходит, а проверка «коды соседей» пропускает 401
   (диапазон 1xx-4xx). Ровно тот случай, который код пытается запретить («наш хост рядом с чужим
   адресом — отказ»), в этой форме записи не срабатывает. Ожидается: заголовок блока собирается
   по всем строкам, пока последняя не-комментарная строка кончается запятой; либо любая
   верхнеуровневая строка, кончающаяся на `,`, — отказ «разберите вручную». Нужен тест на оба
   порядка (сосед первым и нашим первым). Однострочный блок `scout.x.example { respond ok }` не
   распознаётся вовсе: файл получит дубль сайта, `validate` покраснеет, откат сработает — это
   безопасный отказ, но сообщение будет невнятным (совет).

2. **[проверка зелёная по неверной причине] шаг «Проверка scout doctor» не может покраснеть из-за
   самого `doctor`.** `backend/app/cli_doctor.py:91-200` и `cli.py:93`: `scout doctor` нигде не
   делает `typer.Exit` — код выхода 0 при «Ни одна модель не отвечает», при «Схема базы
   разошлась с моделями», при красных источниках (`grep typer.Exit backend/app/cli*.py` — только
   `cli_export`, `cli_run`). Шаг деплоя `docker compose … exec -T scout scout doctor` (workflow.yml
   :252-262) и всё действие `doctor` («проба здоровья», один платный запрос) зелёные при мёртвых
   ключах: запуск скажет «успех», а сервис без модели. Правка кода продукта вне границ задачи,
   поэтому лечится в workflow: вывод `doctor` (в нём только статусы «есть/нет» и тексты ошибок
   источников, значений ключей нет) пропускать через `tee` и падать, если нет строки
   «Готово к работе.» или есть «Схема базы разошлась» (искать подстроку без ANSI: вывод без tty
   цвета не несёт). Без этого заявленный контракт «ожидание healthy → doctor» не проверяет
   ничего сверх `healthy`.

3. **[нет теста на отказные ветки] текстовый страж пропускает мутации, которые обнуляют защиту
   соседей и ворота готовности.** Ставил по одной, прогон обоих файлов
   (`pytest tests/test_deploy_workflow.py tests/test_deploy_server.py -q`), ожидалось ≥1 failed,
   получено **72 passed** (выжили):
   - `fail=1` → `fail=0` в проверке соседнего сайта (`deploy.yml:331`): соседи с 502/000 больше не
     краснят шаг, откат не запускается. Тест смотрит только наличие подстроки `[1-4][0-9][0-9]`;
   - `case … 000|502|504) fail=1` → `fail=0` (проверка JSON-API мимо пароля);
   - убрать `exit 1` после `$DC logs --tail 40 scout` (шаг ожидания healthy становится
     безусловно зелёным);
   - убрать проверку шаблона пути копии в шаге отката (`BAK` из вывода шага не проверяется);
   - убрать `${SCAN:+--scan-host "$SCAN"}` (хост скана не доходит до скрипта);
   - убрать `--force-recreate` у `env-keys` (ключи пишутся, контейнер их не перечитывает);
   - в «Проверке входов» убрать `*..*` и `-*` (остался только базовый шаблон контракта —
     этот пункт совет, но два остальных предохранителя нигде не закреплены).
   Решение: поведенческий тест шага «Коды…» с заглушкой `curl` и `sleep` в `PATH` (я прогнал так же
   вручную: на заглушках шаг даёт rc=0 для 200/301, rc=1 для 502, 000, `www-authenticate: Basic`
   и рабочего хоста с 200 — логика верна, но не закреплена). Тот же приём — для шага ожидания
   (заглушка `docker inspect`).

## Советы (не блокируют)

1. **Идемпотентность.** Из-за соли bcrypt текст файла при каждом `caddy-apply` другой: запись и
   `reload` идут каждый раз (автономное решение (б) исполнителя, в docs описано). Критерий «повторный
   прогон ничего не меняет» держится только на подменённом хэше. Вариант: если пароль не менялся —
   оставлять прежний хэш из области, сверяя его проверяющей командой, а не вторым вычислением.
2. **Хэш пароля через `docker exec -i edge-caddy caddy hash-password` со stdin — не проверено живьём.**
   Риск: версия Caddy в edge-контейнере может не читать пароль из неинтерактивного stdin (по исходникам
   2.x читает строку до `\n`, скрипт её добавляет); либо образ без нужной команды. Отказ безопасен:
   `DeployError`, файл не тронут. Запасной путь без пароля в аргументах: `htpasswd -niBC 14 <логин>`
   (пароль со stdin, bcrypt, вывод `логин:$2y$…`; пакет apache2-utils) — вырезать часть после
   двоеточия и пропустить через тот же `_BCRYPT_RE`; либо ручной хэш по разделу 4 docs/deploy.md с
   записью в `.env` ключа `WEB_AUTH_HASH`, который скрипт предпочтёт вычислению. Не `--plaintext`:
   пароль виден в `ps`. Сообщению об отказе хорошо бы подсказать этот путь (сейчас: «завершился с
   кодом N»). Первый `caddy-apply` — под наблюдением владельца.
3. **Откат при отмене.** Условие шага отката `failure() && …` не срабатывает при отмене запуска и
   при таймауте 45 минут; отмена между записью Caddyfile и `reload` оставляет непроверенный файл
   на диске, который подхватит следующий reload соседей. Добавить `|| cancelled()`.
4. **Запуск с чужой ветки.** Шапка файла говорит «только из ветки по умолчанию», но проверки нет:
   любой с правом записи запустит workflow из ветки с правленым `deploy.yml` и получит секреты
   репозитория. Добавить `if: github.ref_name == github.event.repository.default_branch` и/или
   посоветовать владельцу положить секреты в environment, ограниченный `main` (в раздел 13).
5. **Красный откат из-за выпуска сертификата.** Окно ожидания собственных хостов — 12×5 с. Если
   ACME на новом хосте не успел, шаг краснеет и блоки Скаута откатываются; повторы без паузы бьются
   в лимит ошибок выпуска. И соседи не сравниваются с состоянием до правки: сайт, который лежал
   до правки, вызовет откат. Снять коды соседей до записи и сравнивать с ними.
6. **`env-upsert` создаёт `.env`, если его нет** (`run_env_upsert`, `write_in_place` с `O_EXCL`):
   на чистом сервере `env-keys` породит файл из одних ключей, без `APP_ENV=prod` и пароля, что
   обходит требование compose «env_file обязателен». Лучше отказ при отсутствии файла (docs уже
   называют `.env` условием до запуска).
7. **`request_body max_size 32KB` на хосте скана действует и на `/api/v1/*`** (там `task` до 20 000
   знаков: кириллица в UTF-8 ≈ 40 КБ, в JSON с экранированием больше) — длинную задачу ключом
   приложения через публичный хост не отправить, 413. Форме скана (3000 знаков, до 18 КБ в
   url-кодировке) хватает с запасом. Записать в раздел 13 «API — через рабочий хост» либо ограничить
   предел матчером `path /scan*`. Сверка CSP с `scan_base/form/result/_scan_progress`: встроенных
   скриптов, `style=` и внешних адресов нет, `hx-get … every 4s` без `js:`-выражений; `unsafe-inline`
   для стилей нужен htmx (его индикатор). Шаблон согласован.
8. **Тексты раздела 13.** Не сказано, что с сервисом после красного `healthy`/`doctor`: контейнер
   новой версии остаётся запущенным, автооткатa кода нет, коммит для возврата — в журнале шага
   «Бэкап перед деплоем». Одной фразой — и про то, что при провале сборки сервер уже стоит на новом
   коммите (`checkout` идёт до `build`), а контейнеры старые.
9. `EDGE_NEIGHBOR_URLS` не проверяется на схему: значение, начинающееся с `-`, станет опцией
   `curl`. Источник — переменная владельца, риск малый; `^https?://` в «Проверке входов» закрывает.
10. `git fetch --prune --tags origin` падает на «would clobber existing tag» при переписанном теге —
    безопасный отказ до сборки, но лучше `git fetch --prune origin '+refs/tags/*:refs/tags/*'`.
11. Вывод `caddy validate`/`reload` и `logs --tail 40` попадает в журнал как есть. При публичном
    репозитории фрагмент Caddyfile с хэшем в тексте ошибки Caddy стал бы виден; `actions/checkout@v4`
    закреплён тегом, а не SHA; `REMOTE_PY` из ответа сервера пишется в `GITHUB_ENV` без проверки
    шаблона пути (доверенный сервер).
12. Мелочь: `_BAD_VALUE_RE` пропускает обратную кавычку при тесте-выжившем (compose её не трогает);
    тесты содержат литерал `194.87` — это /16 боевого адреса (так задано критерием 5 плана).
