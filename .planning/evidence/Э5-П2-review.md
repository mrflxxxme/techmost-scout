# Ревью Э5-П2 · сайдкар копии базы: три отказа и лимит журнала · цикл 1
Вердикт: ПРИНЯТЬ (блокирующих 0, советов 3)

## Что проверено по существу (независимый прогон, не по протоколу исполнителя)

1. **Первый запуск, базы нет.** `backup` получил `depends_on: {scout: {condition:
   service_healthy}}`. Прочитан `backend/app/main.py` (lifespan вызывает
   `init_db()` до того, как uvicorn начинает слушать порт, и до первого успешного
   `/health`) — здоровье `scout` физически не может стать зелёным раньше, чем
   файл базы создан. Тест `test_backup_ждёт_живости_scout` закрепляет условие.
   Само тело копии на первом проходе (без задержки в сутки) проверено
   независимым прогоном ниже.
2. **Оборванный проход.** Извлёк тело скрипта сайдкара из `docker-compose.yml`
   (`yaml.safe_load`) и прогнал как обычный Python на временных файлах —
   независимо от тестового харнесса исполнителя:
   - обычная копия: создаёт `scout-<дата>.db`, файл открывается
     `sqlite3.connect` и отдаёт корректные данные (2000 строк тестовой таблицы);
   - при отказе — временный файл `*.part` удаляется в `except`, в каталоге
     копий не остаётся ничего (папка пуста). Файла с именем годной копии
     («пустышки») не возникает.
3. **Удержанная блокировка.** Держал `BEGIN EXCLUSIVE` в отдельном процессе на
   настоящей sqlite-базе и запускал тело скрипта с `LOCK_WAIT_TIMEOUT_SECONDS =
   5` (уменьшено для скорости прогона, механизм тот же): проход завершился
   ровно за ~5 секунд (`elapsed=5s`), напечатал `копия базы не выполнена:
   источник не снял блокировку за 5 с` в stderr, каталог копий остался пустым
   (ни `.part`, ни файла-пустышки). Колбэк `progress=_abort_if_too_slow`
   действительно вызывается во время ожидания снятия блокировки (SQLITE_BUSY),
   а не только по завершении — иначе таймаут не сработал бы вовсе. Это прямое
   опровержение риска, названного в задаче: механизм не является фикцией.
4. **Ротация не трогает чужое и временное.** В каталоге копий положил три
   файла с состаренным mtime (>14 суток): `scout-old.db` (годный шаблон),
   `scout-old.db.part` (временный чужого прохода), `other-file-untouched.db`
   (файл не по шаблону). После прохода ротации удалён только `scout-old.db`;
   `.part` и посторонний файл уцелели — ротация фильтрует по шаблону
   `scout-*.db`, который не матчит `*.part`.
5. **Нормальный путь не сломан.** Копия обычной базы по-прежнему создаётся,
   открывается как рабочая sqlite-база (не обрезок), содержит все строки
   источника.

## Советы (не блокируют)

1. **`service_healthy` как условие старта `backup` — потенциальный «заложник»
   здоровья приложения только в узком случае.** Если `scout` никогда не
   пройдёт healthcheck при первом `docker compose up -d` (или после полного
   `down`+`up`), сайдкар не запустится вовсе и копий не будет, пока приложение
   не станет здоровым. Риск ограничен: `depends_on` в compose управляет только
   порядком **старта**, а не непрерывным мониторингом — уже запущенный `backup`
   переживёт последующую потерю здоровья `scout` (перезапускается независимо,
   `restart: unless-stopped`). Стоило бы явно назвать этот случай в
   `docs/deploy.md` («Копия базы не идёт»), но файл не в списке задачи —
   предлагаю отдельной строкой в задачу волны деплоя, а не мимоходом здесь.
2. **Орфанные `.part` при `SIGKILL`.** Если процесс сайдкара будет убит
   принудительно (не штатное исключение, а `docker kill`/OOM) в момент записи,
   `except` не выполнится и временный файл `scout-<дата>.db.part` останется на
   диске навсегда — ротация его не видит (шаблон `scout-*.db` не матчит
   `*.part`). Не искажает выбор копии по дате (модель разбора имени не видит
   `.part` как валидный), но копится мусор на диске. Вне трёх находок аудита —
   можно закрыть отдельной правкой ротации (`glob("/backups/*.part")` с тем же
   порогом давности).
3. `docs/acceptance.md`/`sources.md` ссылка «п. 8» на Yandex Search API
   (советы 1–2 аудита) этой задачей не тронута — верно, она вне списка файлов
   Э5-П2, но напоминаю, что долг остаётся открытым для будущей волны.
