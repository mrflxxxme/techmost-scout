## Блокирующие

1. **[нет теста на новое поведение] Экранирование текста посетителя на публичной форме не
   закреплено ни одним тестом.** Форма 422/429/503 возвращает введённый `task` в
   `<textarea>{{ task }}</textarea>` и текст отказа в `{{ error }}` (`scan_form.html`). Код
   сейчас верен (автоэкранирование Jinja; вручную проверил ввод
   `</textarea><script>alert(1)</script>"><img onerror=…>` — в теле остаётся только
   `<script src="/static/htmx.min.js">`). Но мутации
   `{{ task }}` → `{{ task|safe }}` и `{{ error }}` → `{{ error|safe }}` проходят **весь
   набор: 1940 passed** (прицельные 79 тоже). Это отражённый XSS на первом входе без пароля,
   охраняемый только умолчанием шаблонизатора. Ожидается: тест, что POST с
   `</textarea><script>…` (и достаточным для 422 хвостом, и коротким) отдаёт страницу, где
   нет сырого `<script>` кроме htmx и нет сырого `<img`; обе мутации после этого должны давать ≥1 failed.

2. **[необработанный отказ на публичном входе] `GET /scan/{token}/status` кладёт сырой путь
   в заголовок `HX-Redirect`.** `scan.py:263`:
   `response.headers["HX-Redirect"] = f"/scan/{token}"`, `token` — любая строка из URL, даже
   для несуществующего токена. Воспроизведено на настоящем `uvicorn app.main:app`
   (httptools, версия 0.54): `GET /scan/a%0d%0aX-Injected:%20yes/status` с `Host` публичного
   хоста → соединение рвётся, в журнале `RuntimeError: Invalid HTTP header value` и
   трассировка (500 вместо 404; каждый такой запрос пишет трассировку). Расщепление ответа
   гасит только проверка сервера; `pyproject` требует лишь `uvicorn[standard]>=0.32`, без
   закрепления версии. Ожидается: токен вне формата `token_urlsafe(32)`
   (`[A-Za-z0-9_-]{43}`) отвечает 404 сразу (до базы и без заголовков со значением из пути) на
   всех трёх маршрутах токена, либо значение заголовка проходит `quote`; плюс тест с `%0d%0a`
   и коротким/длинным токеном. Это же снимает лишнюю нагрузку на базу от любых `/scan/<мусор>`.

## Советы (не блокируют)

1. **Выжившие мутации (полный набор 1940 passed, все шесть):** убрать `X-Robots-Tag` из
   `_PRIVATE_HEADERS` (в тестах проверен только `<meta robots>` формы); `SCAN_NUMBER_LENGTH = 40`
   (номер в письме превращается почти в весь токен, тест проверяет лишь `token[:8] in html` —
   нужен `assert token not in html` и ровно 8 знаков в теме); `READY_STATUSES` + `SEARCHING`
   (тест «идёт» держит запись в статусе `intake`, а не `searching`, где скан проводит почти
   всё время — довести тест до `searching`); охранник схемы ссылки в макросе `source_link`
   (`javascript:` не проверяется; `Evidence.url` — `HttpUrl`, поэтому это защита в глубину);
   нижняя граница длины (`TASK_MIN_LENGTH = 40` не ловится, проверен только «коротко»).
2. `test_другой_адрес_через_прокси_не_делит_лимит` назван неверно: соединение в тестах
   с публичного 8.8.8.8, поэтому `X-Forwarded-For` игнорируется и оба «разных» адреса — один.
   Маршрутного теста с частным peer нет; руками проверил: peer `172.18.0.2` + разные последние
   адреса цепочки — раздельные счётчики, подделка левого адреса не помогает.
3. Докстрока `scan_start` и handoff говорят «между `admit_scan` и `record` нет `await`». Это
   неточно: выход из `async with session_scope()` — `await` (commit/close). Безопасность
   держит `_start_lock` (счётчик читает и пишет только этот маршрут), так что гонки нет;
   формулировку стоит поправить или вынести `check`+`record` в один синхронный вызов.
4. Тело POST разбирается до проверки длины, предела размера нет. В блок Caddy раздела 12
   добавить `request_body { max_size 16KB }`. Там же уместна `Content-Security-Policy`
   (в шаблонах нет встроенных скриптов). Замечание к тексту: Caddy для чужого клиента
   не «дописывает», а заменяет `X-Forwarded-For` — результат тот же, последний адрес = клиент.
5. `HEAD` на GET-маршрутах скана — 405 (в handoff названо); `/scan/` отвечает 307 на
   `http://…/scan` (схема за прокси теряется, нужен `--proxy-headers`/`forwarded-allow-ips`
   либо адрес без хвостового `/`).
6. `_mark_failed(request_id, SCAN_ERROR_FAILED)` в `run_scan` не пишет потраченное: отказ после
   платного интейка занижает суточный потолок (мелкая сумма). Отказ `create_scan_request`
   после `ip_counter.record` тратит попытку адреса.
7. Анонимизация блокирует запуск без обхода (в рабочем интейке есть `accept_risks`). Списка
   компаний нет, регулярка `find_deidentification_risks`: ложные отказы на названиях
   ПО и библиотек — `TensorFlow`, `PyTorch`, `MatLab`, `SolidWorks` дают 422 с текстом про
   «название компании или бренда»; «ИП Проверка» тоже. Поведение как в `/api/v1` (по плану),
   но на публичной форме ложный отказ стоит посетителя; решение владельца: смягчить текст
   или оставить.
8. Номер обзора — 8 знаков токена. Угадыванию они не мешают (остаётся 208 из 256 бит; в письме их
   видит только владелец, а токен-держатель и так знает страницу). Но найти скан по номеру нечем:
   `find_scan` — точное совпадение. Отдельная задача: способ найти строку по префиксу.
9. Лимит по IPv6 считается по полному адресу: сеть /64 обходит лимит адреса (потолок 300 ₽
   остаётся). Код Э6-6а, вне задачи.
10. Посетитель занимает общий замок `_active_runs`: пока идёт публичный скан (до 30 в сутки),
    рабочее место получает отказ «занято». Следствие РЕШ-147, вынести в ворота.
11. `MSG_STOPPED` показывается только при остановке на интейке: при остановке стоп-краном внутри
    пайплайна строку `error` пишет `ScoutPipeline`, страница её не читает (по замыслу), и посетитель
    видит общее «Обзор не получился». Мелочь по тексту.
