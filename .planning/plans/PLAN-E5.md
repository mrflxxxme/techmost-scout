## Чем этап проверяется без демона Docker

Факт среды: `docker` CLI есть (29.3.1, compose v5.1.1), **демона нет** —
`docker build` и `docker run` физически невозможны. Отсюда три уровня проверки,
и каждая задача пользуется первыми двумя:

1. **Машинные стражи на содержимом файлов** — новые тесты `tests/test_docker_*.py`,
   `tests/test_caddyfile.py`, `tests/test_web_api_schema.py`. Они разбирают
   `docker-compose.yml` через `yaml.safe_load` (инвариант №10) и читают
   `Dockerfile`, `.dockerignore`, `Caddyfile` как текст. Это единственный способ
   удержать состав образа и связки без сборки — и он же закрывает инвариант №8
   для артефактов, у которых нет питоновского кода.
2. **Статическая проверка конфигурации compose** — `docker compose config`.
   Сейчас она падает единственной причиной: сервис `scout` объявляет
   `env_file: .env`, а `docker/.env` — файл деплоя, в репозиторий не идёт.
   Ослаблять `env_file` до `required: false` **запрещено**: без `.env`
   приложение поднимется с умолчаниями `WEB_AUTH_PASSWORD=change-me`, и
   отсутствие секретов станет тихим, а не громким. Поэтому проверка делается с
   пустым временным файлом, который тут же удаляется:

   ```bash
   cd /home/user/techmost-scout/docker && : > .env \
     && docker compose config > /dev/null && echo "конфигурация валидна"; rm -f .env
   ```

   Пустой `docker/.env` попадает под `.env` в `.gitignore` (шаблон без слэша
   действует на любой глубине) — в индекс он не уходит. Если команда упала,
   файл всё равно удаляется хвостом `rm -f`; проверить `git status` перед
   коммитом обязан исполнитель.
3. **Живая проверка на VPS — отложенность DLG-1** (РЕШ-226). Выполняет
   владелец по `docs/deploy.md`: `docker compose up -d`, `docker compose ps`,
   `curl -sI https://<домен>/health`, прохождение логина, открытие демо-кейса.
   Вывод присылает оркестратору, тот кладёт его в `.planning/evidence/` и
   ссылается из ворот Э5-1. **Ни одна задача исполнителя от DLG-1 не зависит и
   ждать её не должна.**

   тестом, закрепляющим существо правки, а не её букву.

   `ruff` чист. Критерий «`pytest -q` — падений 0, тестов не меньше 1226 плюс
   новые» стоит в каждой задаче.
8. **Живые прогоны и траты — только оркестратор и владелец.** Бюджет этапа —

11. **Результат существует, только когда он закоммичен** (§13а): коммит идёт

## Контракты, закреплённые планом

Ниже то, что параллельные задачи иначе изобрели бы порознь. Отклонение от этих
контрактов — не «улучшение», а рассинхронизация веток.

### Пути и имена внутри образа

| Что | Значение | Кто владеет |
|---|---|---|
| Рабочий каталог | `/srv/scout` | Э5-И1 |
| Исходники приложения | `/srv/scout/backend` (`PYTHONPATH`) | Э5-И1 |
| База | `/srv/scout/data/scout.db` (том `scout-data`) | Э5-И1, Э5-И2 |
| Выгрузки | `/srv/scout/out` (том `scout-out`) | Э5-И1, Э5-И2 |
| Копии базы | `/backups` в сайдкаре (том `scout-backups`) | Э5-И2 |
| Chromium | `/ms-playwright` (`PLAYWRIGHT_BROWSERS_PATH`) | Э5-И1 |
| Пользователь процесса | `scout`, uid 10001, не root | Э5-И1 |
| Порт приложения | 8000, наружу не публикуется (`expose`) | Э5-И1, Э5-И2 |

**Ловушка, которую обязаны знать обе задачи.** Том `scout-data` монтируется в
`/srv/scout/data`, куда образ кладёт справочник `data/gov_support.yaml`
(читается через `settings.data_dir`, `pipeline/prompting.py:33`). Именованный
том наполняется содержимым образа **только при первом создании** — дальше
обновления справочника в образе до сервера не доезжают. Менять `config.py` ради
этого этап не будет (общий контракт, территория владельца): вместо этого шаг
обновления справочника обязателен в `docs/deploy.md` (Э5-И5) и назван
комментарием в `Dockerfile` (Э5-И1).

### Healthcheck — один на весь этап

Объявляется в `Dockerfile` (`HEALTHCHECK`), а не в compose, чтобы жил вместе с
образом. Проверка — `/health` (авторизации не требует, `main.py:75`),
исполняется штатным Python без установки `curl`:

```
HEALTHCHECK --interval=30s --timeout=5s --start-period=40s --retries=3 \
  CMD python -c "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=3).status == 200 else 1)"
```

`docker-compose.yml` на него опирается: `caddy` ждёт `scout` в длинной форме
`depends_on: {scout: {condition: service_healthy}}`. Второго определения
живости не заводится.

### Сайдкар копии базы (РЕШ-223)

* Образ — `alpine:3` (тег закреплён до мажорной версии; конкретный минорный
  тег в среде без демона не проверить).
* Монтирует `scout-data:/data:ro` и `scout-backups:/backups`. Том копий —
  **отдельный**, не тот же, что у базы: копия на том же томе не переживает
  ошибку с томом.
* Копия — `sqlite3 -readonly /data/scout.db ".backup /backups/scout-<дата>.db"`,
  то есть горячая копия средствами SQLite, а не `cp` файла страниц.
* Ротация — `find /backups -name "scout-*.db" -mtime +14 -delete`.
* Период — сутки (`sleep 86400`), `restart: unless-stopped`.
* **Отказ виден.** Неудачная копия печатает строку в stderr и цикл
  продолжается: молча пропущенная копия хуже отсутствующей (тот же принцип, что
  инвариант №5 для источников).
* `sqlite3` ставится в сайдкаре командой `apk add --no-cache sqlite` при старте
  — контейнеру нужна сеть на старте и перезапуске. Это цена решения «базовый
  alpine» из РЕШ-223 и она названа в `docs/deploy.md`. Альтернатива (тот же
  образ приложения и `sqlite3.Connection.backup` из стандартной библиотеки,
  без сети и без нового образа) зафиксирована ниже как эскалация Э-1 и **без
  решения оркестратора не делается**.

### Плейсхолдеры деплоя — три и только три

В `Caddyfile` ровно три места, которые владелец заменяет руками; они названы
одинаково во всех документах и проверяются тестом:

| Плейсхолдер | Что подставляется |
|---|---|
| `scout.example.ru` | боевой домен |
| `admin@example.ru` | почта для ACME (Let's Encrypt) |
| `ХЭШ_ПАРОЛЯ_ЗАМЕНИТЬ_ПРИ_ДЕПЛОЕ` | вывод `caddy hash-password` |

Тест `tests/test_caddyfile.py` требует, чтобы все три присутствовали, и
запрещает появление в файле подстроки `$2a$`/`$2b$`/`$2y$` — так настоящий
bcrypt-хэш не попадёт в репозиторий (инвариант №3).

### Схема API в боевом окружении (РЕШ-224)

Единственная точка правды — функция в `backend/app/main.py`:

```python
def schema_urls(app_env: str) -> tuple[str | None, str | None]:
    """Адреса схемы API. Открыты только в средах разработки: dev и test."""
```

Правило **закрыто по умолчанию**: схема доступна, только если `app_env` в
нижнем регистре равен `dev` или `test`; любое другое значение, включая `prod`,
пустую строку и опечатку, даёт `(None, None)`. Значения уходят и в
`FastAPI(docs_url=…, openapi_url=…)`, и в
`templates.env.globals["api_docs_url"]`; `base.html` печатает ссылку «API»
только при непустом `api_docs_url`. Второго признака «мы в бою» этап не
заводит.

  2. Передаёт отчёты валидатору: оценка каждой карточки 1–5 и проверка трёх
     случайных фактов по ссылкам в каждой карточке.
  3. Заполняет `docs/acceptance.md`: таблицы оценок, комментарии эксперта,
     фактические время (машинная часть и отдельной строкой окно эксперта,
     РЕШ-227), стоимость, число покрытых типов источников.
  4. Оформляет ворота Э5-2 с порогами §8 п. 4 и ссылками на доказательства.
- **Критерии приёмки (пороги §8 п. 4, менять их нельзя — территория
  владельца):**
  1. В каждом из трёх отчётов не меньше трёх карточек с оценкой ≥4 — факт из
     таблиц `docs/acceptance.md`.
  2. Среди проверенных фактов (три на карточку) нет ни одного
     неподтверждённого ссылкой — инвариант №1, главный критерий продукта.
  3. В каждом отчёте покрыты не меньше 4 типов источников (публикации,
     патенты, гранты, веб) — метрика раздела 2а, РЕШ-173; факт берётся из
     печати прогона, а не со слов.
  4. Машинная часть цикла — не больше суток; окно эксперта записано отдельной
     строкой фактом (РЕШ-227).
  5. Стоимость машинной обработки — не больше 1000 ₽ на запрос (фактическое
     ожидание — единицы рублей: стоп-кран `COST_LIMIT_RUB_PER_REQUEST=20`).
  6. Бюджет этапа соблюдён: суммарно не больше **100 ₽** — три прогона по
     потолку 20 ₽ плюс 40 ₽ резерва на один повторный круг (РЕШ-228). Больше
     одного повторного круга — стоп и разговор с владельцем.
- **Инварианты:** №1 (проверка фактов по ссылкам — критерий 2), №2 (отчёты
  уходят валидатору как черновики, пометка снимается только вердиктом
  человека), №5 (отказ источника не роняет прогон и виден в
  `sources_unavailable` — фиксируется в протоколе, а не заминается), №3
  (в `acceptance.md` не попадают ни ключи, ни адрес сервера).
- **Способ проверки:** заполненный `docs/acceptance.md` со ссылками на
  `.planning/evidence/Э5-П-*`; ворота `.planning/gates/Э5-2.md`.
- **Предел циклов:** один повторный круг прогонов после правок (РЕШ-228);
  провал одних и тех же ворот дважды — стоп и пересмотр подхода с владельцем
  (§4). Вероятные причины провала и куда чинить — `docs/SPEC.md` §8, хвост:
  скоринг (Э2-4), патентные кандидаты (Э2-2), промпт `card_author.md` с
  записью в `prompts/CHANGELOG.md`.
- **Границы:** пороги §8 не смягчаются по ходу; правки промптов и кода по
  итогам приёмки — отдельные задачи с планом, а не «по ходу прогона»;
  исполнителям-агентам живые прогоны не поручаются.

## Отложенности

* **DLG-1 · живой деплой и проверка на VPS.** Причина: демона Docker в среде
  нет, порт 22 закрыт наружу, клиента `ssh`/`scp` нет, закрытых ключей нет и не
  будет (РЕШ-226). Действие владельца: развернуть по `docs/deploy.md` и
  прислать вывод `docker compose ps`, `curl -sI https://<домен>/health` и
  подтверждение прохождения логина. Ложится в доказательства ворот Э5-1;
  блокирует Э5-П (РЕШ-221). Задачи исполнителей от DLG-1 не зависят.

## Эскалации оркестратору (владельцу не выносятся)

Ни одна из них не блокирует волну 1: по умолчанию делается то, что записано в
задачах, а решение принимается до слияния соответствующей ветки.

* **Э-1 · чем делать копию базы.** РЕШ-223 задаёт «базовый alpine и
  `sqlite3 .backup`». Цена: `sqlite3` ставится `apk add` при каждом старте
  сайдкара, то есть контейнеру нужна сеть на старте и перезапуске. Технически
  дешевле и надёжнее взять **образ приложения** и стандартный
  `sqlite3.Connection.backup` (тот же горячий механизм SQLite, ни нового
  образа, ни сети, ни установки). Рекомендация: оставить как в РЕШ-223 на этом
  этапе (решение принято сознательно), риск описать в `docs/deploy.md`;
  переход — отдельным решением, если сайдкар начнёт падать на рестартах.
* **Э-2 · отметки готовности Э4 в `docs/SPEC.md` §6.** Задачи Э4-1…Э4-3 стоят
  с меткой `⬜` при закрытом этапе и подписанных воротах. В шести расхождениях
  РЕШ-225 этого пункта нет, поэтому в Э5-И5 он не заложен. Если оркестратор
  подтверждает — правка добавляется к Э5-И5 одной строкой на задачу.
* **Э-3 · `.env.example`, строки 29–31.** Абзац про сертификаты НУЦ Минцифры
  относится к выпиленному провайдеру (РЕШ-171), рядом живёт
  `PATENTSVIEW_API_KEY` при отклонённом источнике (РЕШ-172) и обрывок блока
  Google без имён переменных. В РЕШ-225 файл не назван, поэтому Э5-И5 его не
  трогает. Отдельная мелкая правка — по решению оркестратора.

## Чего этап не делает

* Не собирает образ и не поднимает контейнеры силами агентов — демона нет
  (проверка только статическая, DLG-1 у владельца).
* Не заводит CI/CD, автодеплой, мониторинг, метрики, алерты, внешнее хранилище
  копий, вторую реплику приложения, Postgres, Redis, оркестраторы контейнеров
  (инвариант №9, «Вне скоупа MVP», РЕШ-223).
* Не меняет `backend/app/config.py`, `schemas.py`, промпты и схему базы.
* Не трогает поведение пайплайна, скоринг и качество карточек: если приёмка
  Э5-П найдёт слабое место, чинится оно отдельной задачей по §8 (Э2-4, Э2-2,
  `card_author.md`), а не правкой «по ходу».
* Не публикует ничего наружу и не заводит путей автоотправки отчёта клиенту
  (инвариант №2).
