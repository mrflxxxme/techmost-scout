# Правила работы в этом репозитории

Читай этот файл перед первой правкой. Здесь то, что нельзя вывести из кода.

## С чего начать сессию

Порядок чтения — пять файлов, дальше по необходимости:

1. **этот файл** — правила кода и языка;
2. **[docs/team/CONVENTIONS.md](docs/team/CONVENTIONS.md)** — как устроена работа
   команды: цикл из семи шагов, шесть ролей, ворота, эскалация. Читается целиком
   один раз за сессию;
3. **[docs/team/INVARIANTS.md](docs/team/INVARIANTS.md)** — десять «никогда» со
   способами проверки. Нарушение блокирует работу;
4. **[.planning/STATE.md](.planning/STATE.md)** — где мы сейчас и что дальше;
5. **[docs/SPEC.md](docs/SPEC.md)** — раздел своего этапа. Обязательно раздел 0.1
   «грабли, на которые уже наступили».

Работа ведётся командой агентов, а не одной сессией: `/team-start <этап>`
поднимает полный цикл, `/team-status` показывает, где мы остановились. Роли
описаны в `.claude/agents/`, состояние — в `.planning/`.

**Сессия работает в своём git worktree** (РЕШ-29). Прочитал состояние — создай
рабочую копию инструментом `EnterWorktree` и дальше правь только в ней: копии
лежат в `.claude/worktrees/`, в репозиторий не попадают и друг другу не мешают.
Основной каталог остаётся за веткой `main`: он всегда пригоден для прогона и
показа. Ветка сессии вливается в `main` на воротах этапа, после подписи.
Разговор без правок и чтение состояния worktree не требуют.

## Что мы строим

«ТехМост Скаут» — внутренний инструмент компании по коммерциализации научных
разработок. По обезличенному описанию технологической задачи промышленного
заказчика система находит **5–7 вариантов научных решений разной зрелости** и
оформляет карточки: суть, стадия готовности, разработчик, чем подтверждено,
применимая господдержка, следующий шаг.

Пользователи: основатель и научный со-основатель. Клиент видит только
готовый отчёт после научной валидации — в систему он не входит.

**Полная спецификация — [docs/SPEC.md](docs/SPEC.md), единственный источник
требований (РЕШ-11).** Продуктовые требования и критерии приёмки — раздел 2а
SPEC; прежний PRD лежит в `docs/archive/` и требований не содержит. Не начинай
задачу, не открыв соответствующий раздел спецификации.

## Три правила, нарушение которых ломает продукт

1. **Ни одного факта без ссылки.** Любое фактическое утверждение в карточке
   живёт в поле `evidence` вместе с URL первоисточника. Чего нет в источниках —
   «не найдено». Выдуманный факт в отчёте у клиента дороже, чем пустая
   карточка: главный критерий приёмки — эксперт не находит ни одного
   неподтверждённого утверждения.
2. **Система не заменяет эксперта.** Выдача пайплайна — всегда черновик.
   Пометка «ЧЕРНОВИК — не проверено экспертом» снимается только после вердикта
   человека. Не добавляй режимов автоотправки клиенту.
3. **Качество данных первично; себестоимость — требование, а не пожелание.**
   DeepSeek — основной провайдер для всех стадий (дёшев, кэш префикса удешевляет
   вход в разы); YandexGPT — резерв на случай его отказа (РЕШ-171). Прежде чем
   добавить вызов модели, спроси: можно ли решить это кодом? Целевая стоимость
   запроса — до 1000 ₽, фактическая ожидается в десятки раз ниже.

## Технические договорённости

- **Python 3.12, FastAPI + Jinja + HTMX в одном процессе.** Отдельного
  фронтенда нет и не планируется: меньше движущихся частей — меньше поводов
  для рассинхронизации.
- **Все внешние вызовы — через слои.** Модели только через `app.llm.LLMRouter`,
  источники только через классы `app.search.base.SearchAdapter`. Прямой
  `httpx.post` к API модели в бизнес-логике — ошибка ревью.
- **Промпты живут в `prompts/*.md`**, не в коде. Изменил промпт — добавь запись
  в `prompts/CHANGELOG.md`.
- **Данные в промпт попадают только через `render_prompt`.** Промпты содержат
  метки вида `{{BRIEF_JSON}}`; заполнять их обязательно. Один раз код этого не
  делал — модель получала метку текстом вместо данных, карточки собирались, но
  проверяющая стадия не видела источников и занижала уверенность всем подряд.
  Добавил метку в промпт — добавь её и в вызов, и в `EXPECTED_PLACEHOLDERS`
  теста `tests/test_prompts.py`.
- **Содержательное — в системном сообщении, а не в пользовательском.** Так
  DeepSeek кэширует префикс и вход дешевеет в десятки раз.
- **Стадии пайплайна — чистые функции** в `app/pipeline/stages.py`: данные на
  входе, данные на выходе, никакой работы с базой. Работа с БД — в
  оркестраторе. Так стадии тестируются на фикстурах без сети.
- **Отказ источника не роняет запрос.** Адаптер возвращает пустой список, а
  отчёт честно пишет в `sources_unavailable`, чего в нём не хватает.
- **Файлы до 500 строк** — правило про код продукта (`backend/app`, `scripts/`):
  за ним стоят машинные стражи (`tests/test_backend_layout.py`,
  `tests/test_scripts_layout.py` и точечные `test_pipeline_layout.py`),
  раздутый файл дробится, а не получает исключение по умолчанию. Публичные
  функции — с типами и докстрокой. Тестовые файлы (`tests/*.py`) под этим же
  пределом не ходят: тест на сквозной сценарий или на матрицу подмен законно
  длиннее модуля, который проверяет, — но здравый смысл всё равно решает
  «стоит ли дробить», а не «можно расти бесконечно»: рост держит страж
  `tests/test_tests_layout.py` (список уже выросших файлов заморожен парами
  имя/размер, новый тестовый файл выше предела без записи в список — красная
  строка).

- **Секреты только из окружения.** В коде, тестах и коммитах ключей нет.
  Не выводи значения секретов в логи и в вывод команд.

## Язык

Код на английском, **всё человекочитаемое — на русском**: докстроки,
комментарии, сообщения об ошибках, интерфейс, отчёты, тексты промптов.
Тон — деловой, без канцелярита и англицизмов там, где есть русское слово
(«стадия зрелости», а не «TRL-левел»; «доращивание», а не «скейлинг»).

Комментируй только то, что не видно из кода: лимиты источников, причины
неочевидных решений, ловушки внешних API. Не пиши комментарии-пересказы
следующей строки.

## Как проверять работу

```bash
scout doctor          # ключи, модели, источники — с этого начинается разбор любой проблемы
pytest                # тесты не обращаются к сети: внешние вызовы подменяются respx
ruff check . && ruff format --check .
scout run "текст задачи" --no-interactive   # сквозной проход
```

Перед тем как сказать «готово»: команда из DoD задачи выполнена и её вывод
показан. Не отчитывайся о выполнении по факту написания кода.

## Чего не делать

- Не добавляй личные кабинеты клиентов, биллинг, интеграции с CRM,
  автомониторинг по подписке, английский интерфейс — это бэклог версии 2, в
  MVP их нет сознательно.
- Не заменяй SQLite на Postgres «на будущее» и не вводи Redis, Celery,
  Kubernetes: на десятки запросов в месяц это лишние отказы.
- Не переходи на платные API там, где работает бесплатный источник.
- Не расширяй скоуп задачи по своей инициативе. Нашёл проблему за границами
  задачи — напиши о ней в ответе, не правь молча.
