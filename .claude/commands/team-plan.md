description: Шаг 1 цикла: составить закреплённый PLAN.md по этапу
argument-hint: "<этап, например Э2-1>"
---

Выполни только шаг 1 цикла (§1 `docs/team/CONVENTIONS.md`) для этапа
`$ARGUMENTS`: получить `.planning/PLAN.md`. Код на этой команде не пишется,
исполнители не запускаются.

Прочитай сначала: `docs/team/CONVENTIONS.md`, `docs/team/INVARIANTS.md`,
`.planning/STATE.md`, `.planning/DECISIONS.md` и раздел `docs/SPEC.md` по этапу
`$ARGUMENTS`. Если идентификатор этапа в SPEC.md не найден — остановись и назови
допустимые.

Если по этапу остались открытые вопросы, которых нет ни в SPEC.md, ни в
DECISIONS.md, — не планируй наугад: скажи владельцу, что нужен
`/team-grill $ARGUMENTS`, и остановись.

Вызови `planner`. Передай ему: идентификатор этапа, раздел SPEC.md по этапу,
относящиеся записи DECISIONS.md, текущее состояние из STATE.md. Требования к
плану:

- задачи атомарные, у каждой — id, исполнитель, зависимости, файлы, критерии
  приёмки, способ проверки (конкретная команда), предел циклов;
- критерий приёмки проверяем командой или чтением файла, а не оценкой «хорошо»;
- границы «не делать» из SPEC.md перенесены в задачу дословно;
- явно помечено, какие задачи можно вести параллельно: до трёх исполнителей, и
  только если их наборы файлов не пересекаются (§11);
- задачи, меняющие общие контракты (`backend/app/schemas.py`,
  `backend/app/config.py`, `prompts/`), идут по одной, остальные ждут слияния;
- по каждому применимому пункту `INVARIANTS.md` указано, чем он проверяется.

Приняв план, проверь его сам, а не на слово (§10): файл `.planning/PLAN.md`
существует; у каждой задачи заполнены все семь полей; наборы файлов у задач,
помеченных как параллельные, действительно не пересекаются; сумма задач
покрывает раздел SPEC.md по этапу и ничего лишнего в неё не добавлено (§9,
пункт про скоуп). Расхождение — возвращаешь планировщику, не правишь сам.

План закреплён: после этой команды он не переписывается на ходу (§6). Изменение
плана возможно только новым прогоном шага 1 с записью причины в
`.planning/DECISIONS.md`.

Обнови `.planning/STATE.md`: этап `$ARGUMENTS` спланирован, столько-то задач,
следующая — такая-то.

Выведи владельцу:
- таблицу задач: id, что делает, файлы, критерий приёмки, способ проверки;
- какие задачи идут параллельно и какие последовательно, с причиной;
- задачи, где ожидается его участие (ключи, данные, тексты для клиента);
- одна строка: с какой задачи начинать, команда `/team-build <id>`.
